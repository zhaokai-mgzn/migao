# Product Skill — 正确执行示例

> 🔴 **本域写面（issue #5303 / #7040 / #7048）**：**可写的动作只有改名、改价**（字段级，可逆 + 幂等，
> **必须先预览再写、必须发确认卡**）；
> 建品 / 改图 / 上下架 / 调库存 / 分类与加工项增删改**都不在能力内** —— 这类示例一律是
> 「查到位 + 如实说明 + 引导到后台」，**不得**出现代办的写轨迹、**不得**发写确认卡。
> 🔴 **边界口径（用户 2026-10-16 裁定「能力边界 终版」，issue #5247 / #7040）**：
> **变更类 ✅ 支持**（改已存在对象：改价 / 改名 / 通知标记已读 / 定时提醒的建与取消）、**非单据对象创建 ✅ 支持**；
> **创建商品 / 订单 / 其他单据类 ❌**、**删除 / 停用 / 作废 ❌（含上下架）** —— 这两类才是「如实告知 + 引导到后台」。
> ⚠️ 本域**只接线了改名/改价两个写 action**（其余写动作**仍未接线**、下面逐条**仍然成立**），
> 但**不要**把它表述成「黄金策整体只读」——那是被 2026-10-16 裁定推翻的旧口径。


## 示例 1：商家要创建商品（能查的都查清楚，再引导后台）

用户: "帮我创建一个遮光窗帘，50 元一米"

### 轮次 1 — 先查分类与同类商品（只读工具都可用）
```
→ category_manage(action="tree")   // 获取分类树（分类 ID 是后台建品归属的前提，先备好给商家）
→ product_search(keyword="遮光窗帘") → 看店里已有同类商品与库价
→ 💬 "建品不在我这边能力内（本域写面只有改名/改价），请在后台「商品管理」页点「新增商品」；我可以先把分类和参考价格查给您。"
```
🔴 **不得**承诺"我帮您创建"、**不得**发建品确认卡；也**不得**含糊甩一句"这个功能不存在"——要说清"只能查、创建在后台"。

### 轮次 2 — 商家问要填哪些字段（讲解口径，商家自行填写）
```
→ 按后台建品页的字段口径逐项讲清楚：商品名称、单价、售卖方式（散剪/整卷，商品级基础属性）、门幅、货号、颜色
  // 后台建品页的 SKU 组合只有 颜色 × 门幅；售卖方式不参与 SKU 组合
→ 💬 "货号可以按色号提取，或用品牌缩写/拼音首字母，如 ZG-001。"
```
🔴 建品流程没有加工项多选卡（issue #4371：加工项是店铺级目录，与商品无关）——
   不要调 processing_item_query 问加工项，也不要说建品要传加工项参数。

### 轮次 3 — 汇总（只汇总给商家看，不发起写操作）
```
收集齐全部字段后：
→ 把字段清单整理成一张对照表交给商家（含推理属性，标注"（推测）"）
→ 说明后台新增页可直接照填；**本域不代填、不提交**（建品参数里也没有 processing_item_ids / processing_item_configs 参数）
```

### 轮次 4 — 商家自己建完后想核对
```
→ product_search(keyword="遮光窗帘") → 确认已入库 → 展示商品档案与价格
→ ✅ "已查到这条商品（ZG-001），价格与分类都在。"
→ ❌ 不得说"已为您创建/已上架"（创建动作不由黄金策执行）
```

## 示例 2：图片识别 + 属性整理（不建品）

用户上传窗帘图片: "创建这个商品"

```
→ Vision 识别结果：名称="雪尼尔遮光窗帘"，颜色="3610-28 奶茶色、5112-03 灰色"
→ 按后台建品页的**预填**口径把识别结果整理成字段清单，不要求用户重复输入
→ 列出（标注"（推测）"）：名称、颜色、货号（色号 3610 + 雪尼尔首字母 → XNE3610）与推理属性（克重/材质/风格等）
→ 💬 "图片识别到名称'雪尼尔遮光窗帘'、2 种颜色。价格和售卖方式还需您补充。
   请在后台「商品管理」页点新增，这些字段可以直接照填；推理属性填到 `specifications`
   （商品属性）里，如 specifications={"材质":"雪尼尔","克重":"300-400g"}——黄金策不代填、不建品。"
```
关键点：识别结果**以字段清单呈现（供商家照填后台表单）**，不要跳过呈现直接建品；
已识别字段不重复反问，缺失字段引导补充；**不得**承诺"我帮您创建"、不得发建品确认卡。

## 示例 3：信息不完整的引导流程

用户: "创建一个商品"

```
→ 💬 "建品请到后台「商品管理」页点新增。先告诉我商品名，我可以把该准备的字段和参考口径列给您。"
用户: "简约窗帘" → 💬 "价格是多少？另外售卖方式是散剪还是整卷？"
用户: "38 一米" → category_manage(tree) → 💬 "窗帘分类如下：[分类树]。您在后台新增时归入哪个？"
→ ❌ 不得因为信息不全就自己开始"收集—校验—确认—创建"的写流程（本域没有创建能力）
```
关键点：只讲解与查询，不代填、不编造。

## 反例

**❌ 序号表格**
```
| 1 | 打孔加工 | ¥8/米 |
请输入序号
```
🔴 用户输入 "1,2" → 序号无法映射 UUID。正确：用 interact choice，value=真实UUID。

**❌ 汇总后假装执行（本域不可能执行）**
```
→ 💬 "确认创建遮光窗帘，50元/米，货号 ZG-001…" → 接着回"已创建"
```
✅ 正确：汇总只给商家照填后台表单；建品等写操作一律如实说明不在能力内 + 引导后台「商品管理」页。

**❌ 把查询说成写能力** → 例如承诺"我帮您上下架"（本域写面只有改名/改价）

**❌ Vision 结果不利用** → 识别到 "2699-01 白色" 还反问 "什么颜色"

## 示例 4：改价格请求（发确认卡预览，点卡后真做）

用户: "把遮光窗帘价格改成 199"

```
→ product_search(keyword="遮光窗帘") → product_detail 拿当前库价（如 ¥168）
→ interact(component=confirm, fields=[商品/改前价/改后价]) 展示 168 → 199
→ 商家点卡 → product_update(product_id, price=199, before_price=168)
→ ✅ "已把遮光窗帘价格从 ¥168 改为 ¥199。"
→ ❌ 不得无预览直接写；❌ 不得只在文字里写"请点击确认"而不发卡
```
关键点：**改名/改价都有工具可调**（改名走 `product_update(name=…)`）；上下架/建品/改图/调库存/分类·加工项增删改才没有工具 —— 那些只查真实数据 + 给具体页面路径，不要假装走确认卡。

## 示例 4b：改商品名称（改名 —— 真做，不是引导后台）

用户: "把「米白遮光窗帘」改名成「米白遮光窗帘（加厚款）」"

```
→ product_search(keyword="米白遮光窗帘") → 拿真实 product_id
→ product_update(product_id, name="米白遮光窗帘（加厚款）")
→ ✅ "已把商品名称改为「米白遮光窗帘（加厚款）」。"
→ ❌ 不得答"改名不在能力内"、不得只给后台页面路径
```
关键点：改名属**字段级变更（✅）**，与改价同一条路。

## 示例 5：多步请求（只做查询，写的一律引导）

用户: "查遮光窗帘，改成 199"

```
轮次 1:
→ product_search(keyword="遮光窗帘") → product_detail
→ 💬 "找到 1 件：米白色遮光窗帘 ¥168；改价我先发确认卡给您过目改前价。"
```
关键点：**不承诺代办**；一次回复里只做查询与说明。

## 示例 6：店铺加工项目录（与商品无关，只读）

用户: "有哪些加工项？"

```
→ processing_item_query()   // 🔴 店铺级目录：不带商品、不带商品分类
→ 💬 如实列出名称与单位（可多选展示，不要"等X项"省略；目录不含单价，不要编造加工费）
```
关键点：加工项是**店铺级目录**（issue #4371），与具体商品无关；商品上不再关联加工项。
**增删改加工项不在能力内**：商家要新增加工项时，如实说明并引导到后台「企业基础设置 → 加工项与加工费」页操作。
