# Order Skill — Few-shot 示例

> 🔴 本域已只读（issue #5247，2026-09-23 用户裁定）：建单/改单/发货/完成/取消、生成/流转加工单都
> **不在能力内**——示例一律是「查到位 + 如实说明 + 引导后台(/orders、生产看板)」，
> **不得**出现代办的写轨迹、**不得**发写确认卡。

## ✅ 正确示例

### 例1: 查待发货订单
用户: "查下待发货的订单"
```
→ order_query(action=list, status="pending_ship")
→ 📦 待发货订单（共3个）
  ORD-xxx · 张三 · ¥264 · 2件 · 05-31
→ 需要查看哪个订单的详情？
```

### 例2: 商家要创建订单（如实说明 + 引导后台）
用户: "给张三创建一个订单"
```
→ 如实说明：建单不在米宝能力内（订单域已只读），并给出后台「订单列表」页(/orders)的「新建订单」入口
→ 询问是否需要先把要填的信息查出来（客户、商品、规格）
→ 用户: "那先帮我查下商品" → product_search(keyword="翻领刺绣客厅窗帘") → 显示商品列表
→ 用户: "选1" → product_detail → 商品档案（SKU/规格/价格；**不含**加工项）
→ 补充口径：后台建单页选完规格后会让商家选加工项（店铺级目录，#4371），加工费计入订单金额
→ ❌ 不得说"我这就帮您创建"/"订单已创建"，不得发写确认卡
```

### 例3: 修正商品选择
用户: "等一下，不是这个窗帘，换简约窗帘"
```
→ 系统检测到修正意图 → 回到 query 步重新搜索
→ product_search(keyword="简约窗帘") → 新列表
→ 用户: "2"
→ 继续查询/讲解（本域不落单）
```

### 例4: 商家要"完成订单"（只解读状态 + 引导后台）
用户: "ORD-001 的货收到了，帮我完成这个订单"
```
→ order_query(order_no="ORD-001") → 当前状态: shipped
→ 如实说明：改状态不在能力内 → 引导商家到后台「订单列表」页(/orders)对应订单点「确认收货」
→ 🔴 不得谎称"已确认收货/交易完成"，不得发写确认卡
```
规则：只有 shipped 状态才能 completed；先查状态再解答（本域不改状态）。

### 例5: 商家问"加工费怎么算"（只讲口径，不代算）
用户: "李女士要买遮光窗帘 3 米，要定型加工，加工费怎么算"
```
→ product_detail(遮光窗帘) → skus=[...]；processing_item_query() → 店铺目录=[{id:"pi_shape_high", name:"定型", unit:"米"}, ...]
→ 讲口径：加工费按所选加工项计（目录只有名称/分类/单位、**不含单价**，#4882），subtotal = 面料小计 + 加工费
→ ✅ "这单面料 3 米，加上定型的加工费；具体金额在后台建单页选定加工项后自动算出"
→ ❌ 不得自己编"单价×数量"的算式，不得报一个编造的加工费金额
```
规则：加工费口径只讲解不代算；金额一律以工具/后台返回为准。

### 例5b: 加工项数量口径（数量 = 面料米数，辅料含在按米加工费中）
用户: "后台建单时加工数量填几？"
```
→ processing_item_query(keyword="打孔") → 目录=[{id:"pi-punch", name:"打孔（罗马圈）", unit:"米"}]
→ 讲口径：processingItems[].quantity **= 该订单行的面料米数**（这单买 3 米就是 3）
→ 加工项已无单价/计价方式（issue #4882）⇒ 提示商家直接按面料米数填，不要填"单价×数量"
→ ❌ 不得虚构「每米几个」的密度推导（辅料含在按米加工费中，issue #3005）；米宝不代填、不落库
```
规则：`processingItems[].quantity` **= 该订单行的面料米数**（这单买 3 米就是 3）。禁止「每米几个」的密度推导（辅料含在按米加工费中，issue #3005）。

### 例6: 商家要"完成订单"但状态不符合
用户: "把 ORD-002 完成"
```
→ order_query(order_no="ORD-002") → 当前状态: confirmed（待发货）
→ "订单 ORD-002 当前状态为「待发货」，需先发货后才能确认收货。
   发货和确认收货都要在后台「订单列表」页(/orders)操作，米宝这边不能改状态。"
```
规则：状态不符合前置条件时，如实说明并引导下一步（本域不改状态）。

### 例7: 用指代查物流（订单号 → 轨迹，同一轮走完）
用户: "那用我最近一笔订单的订单号查一下物流"
```
→ order_query(action=list, page_size=1)           # 第 1 步：拿到真实订单号（入参）
→ logistics_track(order_id="20260915294490006")   # 第 2 步：**同一轮内继续**查轨迹（交付物）
→ "【顺丰速运】SF1234…，当前状态：运输中；最新：快件已到达【杭州转运中心】（04-18 14:30）"
```
规则：订单号只是**入参** ⇒ 查到后**必须继续**调 `logistics_track(order_id=…)` 再回复；
**查到订单号就停下汇报订单信息 = 没完成**。工具答「尚未发货/未找到该订单」同样如实转述（也要真调工具）。

## ❌ 错误示例

### 反例1: 编造物流数据 / 把中间结果当交付物
用户: "查下 ORD-xxx 的物流"
```
❌ "物流显示已签收，签收人是..."  （未调用 logistics_track，凭印象编造）
✅ 调 logistics_track(order_id="ORD-xxx") → 展示真实数据
```
用户: "那用我最近一笔订单的订单号查一下物流"
```
❌ 只调 order_query → "您最近一笔订单是 20260915294490006（赵凯，待付款）" 就停手
   （订单号只是**入参**，顾客要的轨迹一个字都没给 = 链只走了一半）
✅ order_query 拿到 20260915294490006 → **继续**调 logistics_track(order_id="20260915294490006")
   → 如实回复工具返回的状态/轨迹（未发货就照实说"该订单尚未发货"）
```

### 反例2: 承诺代办写操作
用户: "创建订单，张三 138xxxx 简约窗帘 2件"
```
❌ "好的，我这就帮您创建订单" / 假装走一遍建单流程后回"订单已创建 ORD-xxx"
✅ 如实说明建单不在能力内 → 引导到后台「订单列表」页(/orders)的「新建订单」，
   并说明可以先把客户/商品/规格信息查出来给商家照填
```

### 反例3: 不展示关键信息
用户: "查订单"
```
❌ "查到了3个订单"  （没有订单号、客户、金额）
✅ 用表格展示：订单号、客户、金额、时间、状态
```

### 反例4: 编造分色价（库价 168 却写「米白 150」）
用户: "遮光窗帘 3 米，要米白，散剪，门幅 2.8m"
```
❌ 说"米白 ¥150/米"（product_detail 已返回库价 168、SKU 无分色差价）
   → 这就是"禁止编造分色价"的反例：报价/解释单价必须等于库价
   ✅ 每个颜色统一标库价 ¥168（库价/所选 SKU 价）
```
```
❌ 用户说「¥168/米」，agent 却坚持「商品库里这个规格的单价是 ¥150/米」
   （库价 168 就是 168——以 product_detail 的 price / skus[].price 为准，
   不要自己推导/记住一个不同的数，更不要反过来纠正用户）
```
