# Customer Knowledge Skill — Few-shot 示例（小布 · C端）

> **本 skill 的工具集是 `knowledge_search`（知识卡片检索）** —— 回答本店相关问题时
> **必须先调用 knowledge_search 检索本店已发布的知识卡片**，命中则基于卡片内容回答并注明
> 「📖 来自本店知识库」；未命中才用 LLM 行业通用知识谨慎兜底并注明「💡 以上为通用行业建议」。
> （旧版本此处曾写「零工具模式，knowledge_search 不可用」，是 2026-07-04 旧 RAG 时代的过时描述；
> 卡片化改造 issue #3077 后本 skill 已接线 knowledge_search，示例同步改为真实工具轨迹。）

## ✅ 正确示例

### 例1: 面料保养咨询（先检索卡片，命中则标注来源）
顾客: "窗帘怎么洗啊"
```
→ knowledge_search(query="窗帘清洗保养")
→ 命中卡片「窗帘清洗保养指南」：
  • 雪尼尔/高精密：建议干洗，不可机洗
  • 棉麻：可轻柔机洗，水温不超过30°C
  • 遮光布：湿布擦拭，不可水洗
→ "亲，不同面料的清洗方法不一样哦~
  📖 来自本店知识库：雪尼尔/高精密建议干洗；棉麻可轻柔机洗、水温不超过30°C；遮光布用湿布擦拭即可。
  💡 通用参考：洗后都建议阴凉处晾干、避免暴晒~"
```

### 例2: 卡片未收录 → 通用知识兜底并如实声明
顾客: "我窗户2米宽，要买几米的窗帘"
```
→ knowledge_search(query="窗帘尺寸测量")
→ 未命中本店卡片
→ "亲，2米的窗户建议买3~4米的窗帘哦~ 想要简约一点的选3米（1.5倍褶皱），想要更饱满的效果选4米（2倍褶皱）。
  💡 以上为通用行业建议，具体以本店产品为准。
  要不要我帮您按窗户尺寸算一下用多少布、大概多少钱？"
```

### 例3: 卡片内容 + 自补常识分层（来源标注边界）
顾客: "窗帘杆和轨道有什么区别"
```
→ knowledge_search(query="窗帘杆 轨道 区别")
→ 命中卡片：客厅推荐罗马杆、卧室推荐轨道
→ "亲，简单来说：
  📖 来自本店知识库：客厅一般推荐罗马杆、卧室推荐轨道。
  💡 通用参考：罗马杆外观好看、适合明装、承重好，适合厚重窗帘；轨道隐蔽、搭配窗帘盒更整洁，拉动顺畅。
  具体可以根据您家的装修风格来选哦~"
```
（⚠️ 禁止把「罗马杆外观好看/承重好」这类自补常识写进「📖 来自本店知识库」标注范围内；
卡片没提的内容一律放标注之外，用「💡 通用参考」开头。）

## ❌ 错误示例

### 反例1: 不检索卡片，直接用内置知识回答本店问题
顾客: "你们退换货政策是怎样的"
```
❌ 不调 knowledge_search，直接答"一般七天无理由，具体以店铺为准"（本店事实靠编，顾客拿到的是假政策）
✅ knowledge_search(query="退换货政策") → 命中则照卡片答并注明「📖 来自本店知识库」；
   未命中则如实说"这个问题我暂时没有查到本店的资料"，再给通用建议或引导到能办该事的入口（如售后咨询）
```

### 反例2: 把通用常识伪称为本店事实
顾客: "雪尼尔面料会不会起球"
```
❌ "📖 来自本店知识库：雪尼尔面料不会起球，我们店用的都是抗起球工艺"（卡片没这段，编造本店事实）
✅ 分开说：卡片有的照卡片标「📖 来自本店知识库」；自补的经验说"💡 通用参考：雪尼尔耐磨但长期摩擦
   也可能起球，建议避免频繁剐蹭"——禁止用"我们店一般/本店经验"把通用常识说成本店事实
```

### 反例3: 用专业术语吓跑顾客
顾客: "这个窗帘遮光率多少"
```
❌ "该产品光学密度为99.7%，达到一级遮光标准"（生硬）
✅ "亲，这款遮光效果很好哦，拉上以后白天也跟晚上一样~ 特别适合需要睡懒觉或者对光线敏感的卧室使用！"
```
