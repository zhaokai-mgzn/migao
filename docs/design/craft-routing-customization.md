# 工艺路线「商家可配」决策记录（issue #4308 / #4307）

> 一句话结论：**支持企业自定义工艺路线，但形态是「参数 / 信号 / 序列可配 + 护栏」，不是「从零画路线」的自由编排器。**
> 本文件记录裁定依据、冻结契约、明确不做项与已知缺口。相关：#4261（待客户确认 5 项）、#4316（种子只覆盖 1 号租户）。

## 1. 裁定（2026-09-19）

用户裁定「支持企业设置工艺路线的自定义」。落到实现上的形态由三条既有事实钉死：

1. 真值源 `docs/curtain-production-rules.md` §2/§3 的自述标注是 **【默】= 经验默认值（需商家可配置）** —— 「需商家可配置」是**既有承诺**，不是新需求；只有「布帘·韩褶 11 道」是【标】行业实证。
2. `V49__create_production_operations_and_work_logs.sql` 从建表起就是**按租户**设计（`production_routings` 唯一键 `(tenant_id, curtain_type, craft)`、`production_operations` 唯一键 `(tenant_id, name)`）⇒ 存储层本就为「每企业一套路线」准备。
3. 但改前只有**读面**（`GET /production/routings`、`GET /operations-catalog`）与**改参数面**（`PUT /production/operations/{id}`，#4204）⇒ 「企业设置工艺路线」在系统里**无路可走**，只能开 issue 让研发改常量。

## 2. 行业事实：路线**同构**，差异在**少数开关**

「行业里是不是都固定」的答案是：**不是固定，但差异不是"整条路线重画"**。差异的实证就登记在本仓库里：

| 差异点 | 证据 | 性质 |
|---|---|---|
| `裁剪-布/裁剪-纱` 与 `精裁-布/精裁-纱` 是**一道还是两道** | `routing.py::PENDING_CUSTOMER_CONFIRMATION_OPERATIONS` 显式挂起；「取决于裁床流程」 | **设备差异** → 企业差异 |
| `质检` 是否**每单必做**、插在哪 | 同上；真值源 §8 只说定型「联动…质检/包装」，没说它必做 | **管理差异** → 企业差异 |
| `腰靠垫` 属另一产品还是某选项产物 | 同上 | **产品线差异** |
| **罗马帘**整套工序 | 真值源 §3 把罗马帘列进工艺清单、算料引擎 `curtain_calc.py` 有 roman 分支、顾客端 `mounting` 枚举有它，**唯独工序库里一道罗马帘工序都没有** | **能力缺口**（非企业差异） |

⇒ 所以「自定义」的真实需求是：**让商家能处置这几处开关与缺口**，而不是给一个可以任意重排 11 道的编辑器。

## 3. 改前分层（现状）

| 层 | 改前 | 证据 |
|---|---|---|
| 存储 | **已按租户**（唯一键含 `tenant_id`） | V49 |
| 工序库参数 | **可配**（单价版本化 / 必完 / 开始标记 / 单位 / 分组 / 停用 / 排序） | `ProductionOperationCommandService`（#4204） |
| 路线拓扑 | **只读**（只有 `GET`，全仓无路线写端点） | `ProductionController` |
| 路线真值源 | Python `ROUTINGS` 只是**种子**，运行时读库；读不到 fail-closed | `ProcessingOrderService` + `ProductionOperationQueryService.findRouting` |

## 4. 四条冻结问题（改前实证）

### P1 · 静默回落：派生不中 ⇒ 默认路线，**成功路径零可观测**（P0，直接错工资）

三层回落语义（`resolveRoute` @9673df68 逐行核对）：

| 层 | 条件 | 改前行为 | 用户侧可见性 |
|---|---|---|---|
| **T1** | 信号**全不命中** | 直接取默认键 `布帘×韩褶`，`findRouting` 命中种子 | **连日志都没有**（最隐蔽） |
| **T2** | 派生键命中但**库中无该路线** | `log.info("…回落默认路线…")` 后回落 | 仅一行 info |
| **T3** | 默认路线也没有 / 路线引用工序缺行 | **fail-closed 中止生成**（#4116） | 有错误码 + suggestion |

**后果（可复现）**：商品名含「罗马帘」的订单 —— 帘种关键字（帘头/纱/布）不中 ⇒ 取默认「布帘」；工艺关键字不中 ⇒ 取默认「韩褶」⇒ **罗马帘订单拿到布帘·韩褶的 11 道工序** ⇒ 工人按布帘工序报工、按布帘单价计件。与 #4246 已实证缺陷**同机制**；#4246 只补了 3 条纱帘路线，**没治"回落是静默的"这个机制**。

### P2 · 派生靠硬编码中文子串表，商家自定义加工项名即错配
信号 = 加工项名 > 加工项 options > 商品名 > 销售方式；匹配 = `contains`。而**加工项目录是可自定义的**（POC 已建过「POC-加工工艺」这类名字）⇒ 把「商家可配的业务数据」的判据绑在「研发改的常量表」上，商家每加一个自定义加工项就多一分静默错配。

### P3 · 路线拓扑无写面
路线是**计件工资**（`Σ(报工数量 × 工序单价)`）与**完工判定**（必完工序全绿）的唯一输入，且工序的 `unit` 决定应做数量读哪个算料键（`fabric_meters`/`pleat_count`/…）⇒ 写面**必须有护栏**，不能裸奔。

### P4 · 4 道「待客户确认」工序与罗马帘缺口**不可见**
缺口只活在代码注释里 ⇒ 商家看不到、无法自行处置。

## 5. 冻结契约（实现依据）

### 5.1 路线来源落库（三列）

| 列 | 语义 |
|---|---|
| `processing_orders.route_key` | **实际使用**的路线键（T1/T2 时 = 默认 `布帘×韩褶`） |
| `processing_orders.route_requested_key` | **派生出的**键（可能库里没有）；两维全不命中时为 `NULL` |
| `processing_orders.route_source` | **四态**：`derived` / `partial` / `missing_route` / `default` |

**为什么是四态而不是三态**：T2 与「只命中一维」的**补救动作不同** —— T2 要「建路线」、半命中要「配信号」；合并成一个值就给不出可行动的提示语，而那正是 P1 要治的「不可行动」。**为什么必须有 `route_requested_key`**：没有它，`missing_route` 的提示说不出「识别的 X 在库里没有路线」。

多部位订单取**最需关注的一条**：`default > missing_route > partial > derived`（`severity()`；未知取值按最需关注处理，不静默降级）。

### 5.2 端点集

| 端点 | 用途 |
|---|---|
| `GET /api/admin/production/routings` | 路线模板列表（既有） |
| `POST /api/admin/production/routings` | 新建路线 `{curtain_type, craft, operations?}` |
| `PUT /api/admin/production/routings/{id}` | 改序列 `{operations: string[]}` |
| `GET/POST/PUT/DELETE /api/admin/production/route-signals[/{id}]` | 信号 → 路线键映射（**商家可配**，替代硬编码常量表） |
| `POST /api/admin/production/operations` | 新增工序（建新路线时必须有工序可选） |
| `GET /api/admin/production/routing-gaps` | 缺口：未进任何活跃路线的活跃工序 + 无路线的信号组合 |

权限统一 `processing:manage`（既有权限，V29/V32 已种子；与 #4204 工序库写面同口径）。

### 5.3 路线写面五条护栏（每条必须有红证）

1. 序列非空；2. 引用的工序必须**存在于工序库活跃行**；3. 无重复工序；4. **至少一道必完工序**；5. `seq` 归一化为 `1..N` + 每次变更落 `production_routing_versions` 版本账。

### 5.4 错误形状（**复用**既有结构，不新造字段）

护栏失败 = HTTP **422** + `{success:false, error:{code, message, details:[{field, message}]}, suggestion}`。
- `error.details[].message` = **逐条**理由（主口径）；`field` = 违规维度（`operations[2]` / `must_finish`），**只用于定位、不展示给商家**；
- `ApiResponse.ErrorInfo.details` **本来就存在** ⇒ 实现只需 `BusinessException` 加可选 `details` + `GlobalExceptionHandler` 透传（纯追加）。

> **实证教训（假绿）**：前端曾按**虚构形状**读理由（顶层 `error_messages` + 把 `error` 当字符串）⇒ 交付测试 21 条全绿，而对**真实**信封 **2/2 红**、商家只看到「Request failed with status code 422」。修复后原探针**转正为回归守卫** `production-routings-guard-envelope.test.ts`（`case_ids: PP-014`）。

## 6. 明确不做（YAGNI）

- ❌ **自由拖拽编排的通用路线编辑器**（v1 = 从工序库选 + 上移/下移/删除）。
- ❌ **发明罗马帘/新课工序的行业数据**：库里一道罗马帘工序都没有，构造（固定式/升降式/穿孔式/气球帘）与单价都不能编 —— **单价会直接算成工人工资**。正确解法 = 商家用本单写面**自己建**（工序不存在时先建工序）+ 缺口在 UI 可见。
- ❌ **无条件 fail-closed**：无信号订单（多数正常单）仍走默认路线，但必须**可观测**（P1）；只有 T3（默认路线也没有）才中止。
- ❌ **路线版本回滚 UI**（版本账先落数据）。
- ❌ 改 `.agent-presets/**`。

## 7. 已知缺口（如实登记）

1. **种子只覆盖 1 号租户**（#4316）：V54/V56/V58/V59 **四个**种子迁移都是字面量 `tenant_id = 1`（`FROM tenants` 出现 0 次），而同仓权限种子（V43）是按租户循环的范式 ⇒ `tenant_id ≠ 1` 的租户工序库/路线库为空、建单 **fail-closed（422）**。**本单的写面正是它的补救路径**（在此之前 `production_operations` 只有 `PUT …/{id}`，非 1 号租户连工序都建不出来）。是否改成循环播种 / 开租模板复制 —— 待裁定（两者语义不同：循环会把 1 号租户被客户改过的工艺复刻给新租户）。
2. **5 项待客户确认**（#4261）：罗马帘整套工序 / 纱帘熨烫定型 / 裁剪vs精裁是否两道 / 质检是否每单必做 / 腰靠垫归属。本单**只提供写面，不发明数据**；`routing-gaps` 是它们在系统里的可观测面。
3. **信号表 `priority` 撞档**：同一用途下两行同 `priority` 时按 `id`（uuid）tie-break ⇒ 「谁先命中」对商家不可预测。写面应拒绝同用途重复 priority，或在 UI 上显式提示；**未处理前**该语义以本文件为准（不是"保证语义顺序"）。
4. **§15.2 真实浏览器走查**：属合并后动作（`scripts/ui_smoke_merchant.sh` 自起栈 + 真浏览器），见交付 PR 的证据节。

## 8. 什么时候才做「更多自由」（触发条件，数据驱动）

出现下列任一信号，才考虑把路线拓扑的自由度再放大（如拖拽编排、路线模板跨租户复制）：
- 生产环境 `INCIDENT_PRODUCTION_ROUTE_DEFAULTED` / `INCIDENT_PRODUCTION_ROUTE_FALLBACK` 出现**真实客户**的重复记录（说明信号映射覆盖不足）；
- 有 **≥2 家**真实客户提出**同一类**序列差异需求（说明同构假设在某细分市场不成立）。

在此之前，「支持自定义」的正确形态就是本单交付的这一层：**参数可配（已有）+ 信号可配 + 序列可配 + 缺口可见 + 护栏**。
