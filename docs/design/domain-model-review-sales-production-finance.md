# 领域模型评审：订单 → 加工单 → 加工项 → 工艺 → 工序（2026-09-19）

> **目标口径（用户 2026-09-19 裁定）**：去其糟粕、取其精华，结合互联网与 AI Agent 的技术优势，打造**智能销售 / 智能生产 / 智能财务**、**最短最优路径**的智能 ERP —— 米高系统。
> 本文件回答「**是否需要重构**」，并给出「留什么 / 改什么 / 加什么」。相关：#4343（路线与实证不一致）、#4344（部位级缺失）、#4347（工人自主推进 + 结算）、#4351（**P0 计件静默少算**）、#4261（待客户确认）。

## 0. 结论（先说答案）

**不推倒重来。主干保留，补 3 处结构性缺口 + 1 处 P0 缺陷 + 4 处载体缺失。**

- **主干（订单 → 加工单 → 工序实例 → 报工 → 计件）是被实证正面验证过的**，动它是净损失；
- **真正的缺陷是「销售侧信息丢失」与「维度划分错误」**，不是"表设计得不好"；
- 「最短最优路径」的差距**不在功能多少**，而在**同一份信息被反复猜/反复搬运**。

## 1. 三个域的现状 × 最短路径差距

### 1.1 智能销售

| 项 | 现状（证据） | 差距 |
|---|---|---|
| 订单行存什么 | `order_items`：`product_name / quantity / unit_price / width / height / **processing_info(JSONB)** / subtotal` | **生产所需的下单行要素全不在此** |
| `processing_info` 实际装什么 | `skuId / colorId / colorName / sellingMethod / doorWidth / processingItems / processingFee`（`order_create.py` 的 schema 描述逐字） | **只有"卖什么规格 + 加什么工"** |
| 部位 / 工艺 / 开数 / 加工类型 / 定型 / 褶倍 / 褶距 / 对花 / 转角 | **订单行一个都没有** | 真值源 §1 明明列了这些「下单行字段」（来自 ERP 订单录入实证）⇒ **我们丢了** |
| AI 采集 | C 端 `curtain_checklist.py` **已经会问**「平开/落地/飘窗/转角/L窗——转角影响开数与片数」 | **问到了却不落库** ⇒ 到生产只能靠关键字事后猜（`deriveRouteKey` + 今天的信号表） |

⇒ **这是"最短路径"上最大的一次信息丢失**：AI 在销售端辛苦采集的要素，生产端拿不到，只能猜。**今天的 `production_route_signals` 是"猜"的补丁，桥的那一头就是这些字段。**

### 1.2 智能生产

| 项 | 判定 |
|---|---|
| 工序库 / 路线库（租户级） + 工序实例 + 报工 + 计件 | ✅ **主干被实证验证**：`11.80×11.00=129.8`、`7.00×11.00=77`、合计 `206.80=金额`；报工流水 `人-工序 部位 数量` 与 `production_work_logs` 同构；`用料 12.300 ÷ 宽 6.6 ≈ 实际褶倍`、`48 折 ÷ 四开 = 12 折/开` ⇒ 印证 `qty`/`qty_source`/褶数口径 |

| 「工艺」维度 | ❌ **划错边界**：实证里 `安装工艺=韩褶` 与 `穿钩`（四爪钩）**同时出现** ⇒ 「打褶方式」与「挂钩方式」是**两个维度**，我们压成了一维，于是把 `穿钩` 误建成**独立工艺路线** |
| 「部位」 | ❌ **不是一等公民**：订单侧无部位字段，靠关键字派生；`processing_position_operations.position_name` 是字符串，部位级的东西无处挂 |

| 计件金额 | ❌ **P0**：重新实例化软删旧实例后，历史报工被聚合 `continue` 跳过 ⇒ **钱凭空消失且不报错**（#4351），违反真值源 §4「历史报工按当时价，逐笔可追溯」 |
| 载体缺失 | ❌ 部位备注 + **算料依据（公式）**、裁床输出（`精裁输出`）、配料/采购状态、部位级状态（#4344） |

|---|---|---|
| 订单记账 | `finance_transactions` + confirmPayment/cancel/refund 流水 | ✅ 有 |

## 2. 重构判断：留什么 / 改什么 / 加什么

### 2.1 保留（实证已验证，动它是净损失）

- 订单 → 加工单（1 订单 1 加工单）→ 工序实例 → 报工 → 计件的**主干与快照机制**；
- `production_operations`（工序库）/ `production_routings`（路线库）**按租户可配**；
- **单价版本化 + 实例快照**（方向对，实现有洞 → 见 2.2-P0）；
- 报工四防呆（幂等/越站/数量上限/非本部位）；
- 必完工序全绿自动完工、`is_start_marker` 触发生产开始；
- 算料数量口径（`qty` + `qty_source`：哪个键供的数）；
- 19 项特殊选项的三类显式登记（加工序/加系数/不计件）。

### 2.2 必须改（加字段解决不了的）

| # | 结构性缺口 | 为什么是"结构"而不是"字段" |
|---|---|---|
| **S1** | **订单行要素结构化**：部位 / 工艺 / 打开方式 / 加工类型 / 是否定型 / 褶倍(理论/实际) / 褶距 / 总褶数 / 是否对花 / 转角 | 这些是**算料与工序的输入**，现在埋在自由 JSONB + 靠关键字猜 ⇒ 每加一个客户/工艺就要加一条补丁，且**猜错会直接算错工资**（#4246 已实证）。落成字段后，`deriveRouteKey` 与信号表**降级为"历史数据兼容 + 商家自定义加工项兜底"**（代码注释已给出这条路线图） |
| **S2** | **「工艺」维度拆分**：打褶/悬挂方式（韩褶/打孔/穿杆）**≠** 挂钩方式（四爪钩/穿钩/S钩） | 实证里两者**同时出现**；压成一维 ⇒ `穿钩` 被建成独立工艺路线、`deriveRouteKey` 的工艺表混了两个维度 |

> ✅ **S1 / S2 的裁定与落地状态**（2026-09-19，见 #4362 / #4365）：
> - **S1 已落地**：`order_items` 新增 11 个 nullable 列（V62）+ 两个采集端落库 + 三层推导链
>   （`显式字段 > 加工项推导 > 信号派生兜底`）。
> - **S2 阶段 1 已落地**：`craft` 冻结为「安装工艺＝打褶/悬挂方式」且**单值**；
>   「四爪钩/四叉钩」是**加工项（配件）不是工艺** ⇒ 信号映射层指向主线工艺（V62）；
>   `production_routings` 的键**不改**（阶段 3 等 #4261 客户清单）。
> - 🔴 **「降级为兜底」不等于「退场」**：用户裁定「**部位不是必填的**」⇒ 派生 + 信号表是
>   **长期兜底**（不是临时桥）。原文里"本来就设计成临时桥"的表述**已作废**。
| **S3** | **「套」成为一等公民**：第 N 套/共 M 套 + **组合单**（跨套视图） | 实证「第14套/共22套」「查看组合单」；我们 `processing_orders` **无套号列**，22 套工程单无处表达「这是第几套」，也无法按套对账 |
| **P0** | **计件金额在报工那一刻固化**（`production_work_logs` 存单价/系数快照） | 现在聚合回查实例 ⇒ 实例软删即归零（#4351）。固化后"重算历史工资"变成**不可能**，正是 §4 要的「逐笔可追溯」 |

### 2.3 必须加的载体（小，但缺了就无法追溯）

- **部位备注 + 算料依据（公式）**：实证 `部位备注: 公式--48个折` ⇒ 回答"这个数字怎么来的"。我们已有折数（`pleat_count`）与口径来源（`qty_source`），**缺公式本身**（如罗马帘 `M=(W+0.2)×(H+0.3)` 只活在 `curtain_calc.py`）。
- **裁床输出**（`精裁输出`）：真值源 §2 写了「精裁（含裁床输出）」，无字段 ⇒ 现场裁床数据无处落。
- **配料 / 采购状态**（`整套配料` / `未配料` / `未采购`）。
- **部位级状态**（实证部位行上有 `已确认`）。

### 2.4 智能财务要补的闭环

- **工人账**：计件（修 P0）→ **结算单（period × worker，快照 + 锁定）** → 补报走调整单；
- **客户账**：保证金 / 余额 / **结算状态**（实证三件套）。

## 3. 「AI-native 智能 ERP」的差异化（这才是"全新"的地方，不是照抄 UI）

| 差异点 | 传统 ERP（实证形态） | 米高（AI-native） |
|---|---|---|
| 要素采集 | 人在多屏之间手工录入 | **AI 在销售对话里一次问全并直接落库**（S1 之后不再猜） |
| 工艺配置 | 研发/实施改常量或后台配 | **自然语言描述 → AI 生成路线草案 → 五条护栏机器校验**（#4308 写面） |
| 缺口发现 | 出错工资后人工回头查 | **系统自己喊**：`routing-gaps` + `INCIDENT_ROUTE_DEFAULTED/FALLBACK` 可 grep |
| 工人侧 | 打印纸质单 + 扫码报工 | 扫码即见**本期计件累计**、自主推进（打包/发货）、结算锁定 |
| 路径长度 | 建单→生成加工单→打印→报工→管理端完工→管理端发货→财务对账（**7 段人工搬运**） | 目标：把**人工搬运环节压到最少**，每段都可由事实/事件自动推进 |
| 可追溯 | 靠人记 | 每个数字可追到**公式 + 口径来源 + 快照单价** |

## 5. 明确不做

- ❌ 不推倒主干（订单/加工单/工序实例/报工/计件/快照机制）。
- ❌ 不照抄实证 ERP 的 UI 与三 Tab 结构。
- ❌ 不为"补齐"而**发明行业数据**（工序名/单价/路线一律等客户确认，#4261）。
- ❌ 不在修复 P0（#4351）之前做「结算」——结算建在一个会静默少算的合计上，等于把错账锁死。
