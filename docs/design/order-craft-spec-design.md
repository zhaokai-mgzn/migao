### 2.1 三段链：登记 ✅ → 消费 ✅ → 生产 ❌

19 项特殊选项（含加铅块、抱枕、拼1/2/3次、布绑带/纱绑带）的完整链路：

| 段 | 状态 | 证据 |
|---|---|---|
| ① **登记**（选项 → 条件工序 / 计件系数 / 不计件） | ✅ | `routing.py` 的 `SPECIAL_OPTION_ROUTINGS`（工序）/ `OPTION_FACTOR_SCOPES`（系数）/ `NON_PIECEWORK_OPTIONS`（不计件）；三类全登记有结构门禁防「静默黑洞」 |
| ② **消费**（订单 → 加工单快照 → 条件工序 + 系数） | ✅ | `ProcessingOrderService.java` 的 `buildPositionPayload`（插条件工序 + 落系数）、`buildSnapshot`（快照透传 `specialOptions`） |
| ③ **生产**（下单时**写入** `specialOptions`） | ❌ | 前端 `specialOptions` **0 命中**；ai-agent `order_create` **0 命中**；唯一写入者是 `ProcessingOrderServiceTest.java` 的 `orderItemHanzheWithOptions` 测试桩 |

⇒ 用户说的「订单上都没体现」，是**结构性事实**，不是错觉：车间拿不到勾选，工人也拿不到那笔计件。

### 3.2 拼色部件层术语：主布 / 配布 / 配布边 / 接高

用户口径（2026-09-18）：

> 「加窗边布 = **配布边**；还有 **主布 / 主布接高**、**配布边 / 配布边接高** 的说法。」

**「主布 / 配布」不是新概念** —— 真值源 §8 早已登记（但**从未落码**，见 §4.8）：

| 出处 | 原文 |
|---|---|
| §8 术语表 | 部件 = **主布** / 纱 / 加工费（报价与加工单的**明细行粒度**） |
| §8 术语表 | 款式 = 单色 / 拼色（拼色 = **主布+配布分料**、按折加价） |
| quote-rules §10 | 拼色**主布用料** = 0.25×折数 + 0.15（单开口径） |
| quote-rules §126 | 客户纸表含「**主布拼色列**」，拼色计价 0.65 / 1.2 |

**用户裁定（2026-09-18，原文）**：

> 「作为商品明细的**一行数据**，买一个商品，如果需要**双拼**就要选择 **主布、配布边 和 加工项 三个明细行**。」

⇒ **配布边 = 一条面料明细行（买配布）**，**不是**勾选项。原来「配布边 = 加立边」的推断**作废**——
两者是**不同层**，互补而非同物：

| 层 | 对象 | 本系统承载 |
|---|---|---|
| **用料层** | **配布边**（配布，按米买） | 一条**面料明细行** ← 新增（§4.8） |
| **工序层** | **加立边**（做那道立边） | 加工项 / 特殊选项 → 工序 `立边-布`（¥0.5/米）✅ 已登记 |

这与 §8 术语表「**部件 = 主布 / 纱 / 加工费（报价与加工单的明细行粒度）**」完全同构 ——
双拼 = **主布 + 配布边 + 加工项** 三条明细行。§8 的「部件」清单需补 **配布边**。

#### 接高的归属：**本轮暂缓**（用户 2026-09-18 裁定「先不管接高了，就只考虑主布和配布边」）

原提问与已知事实**留档**，本轮**不实现、不裁定**：

- ERP 有两个接高勾选项：「**接高**」与「**双眼皮接高**」
- 客户对「双眼皮接高」的回答是：**「双眼皮是什么概念，我不理解」** ⇒ **不猜**；
  核实路径（留档）：① 问 ERP 供应商该选项定义；② 在既有 ERP 里勾上它，看加工单多出哪道工序
- 现状：`routing.py` 的 `SPECIAL_OPTION_ROUTINGS` 把两者映射到**同一道** `接高-布`（¥1.0/幅），
  且有测试锁死该相等（`test_special_options.py`）

**暂缓不影响主布/配布边建模**：接高在设计里是**明细行级布尔属性**（将来在明细行上加一个键即可），
与主布/配布边两条明细行的结构无关 ⇒ **不需要重构**。

### 3.3 术语表补齐建议（可直接落到 `curtain-production-rules.md` §8）

§8 现有 10 条已覆盖 加工类型 / 打开方式 / 定型 / 款式 / 部位 等，**建议补以下条目**：

| 术语 | 含义 | 标注 |

## 四、设计：订单工艺规格

### 4.1 落位与理由

**落位：`order_items` 的**结构化列**（V63，issue #4362 S1）+ `processing_info`（既有 JSONB）顶层扁平键作为**写入口**。**

> ⚠️ **本节口径已被 issue #4362（S1）更新**（2026-09-19）：原文写的是「**不加新列、不加新表、不写迁移**」
> —— 那是 #4346/#4354 阶段（只要求「先落库」）的取法。S1 的判据升级为「把下单行要素**结构化**落到
> `order_items`」（真值来源 = #4362 + `docs/design/domain-model-review-sales-production-finance.md` §S1）：
> 埋在 JSONB 里的要素**不可查询、不可约束、下游只能按字符串键取**。故：
> 1. **新增 11 个 nullable 列**（`curtain_type` / `craft` / `open_count` / `cutting_mode` / `is_shaped` /
>    `fullness` / `fullness_actual` / `pleat_spacing` / `pleat_count` / `has_pattern` / `corner`，
>    V63 迁移 + `docs/sql/schema.sql` 终态）；
> 2. **写入口仍是 `processing_info` 顶层键**（不新增 DTO 字段 —— 避免第二份定义，
>    `OrderDtoContractTest` 锁死 DTO 形态；两个采集端本来就写 JSONB）⇒
>    `OrderService.createOrder`（三条路径的唯一共享入口）把它**物化**到列上
>    （单一映射点 = `OrderLineCraftFields.materialize`）；
> 3. **读面列优先**：`buildSnapshot` 在 JSONB 键之后叠加列值（`OrderLineCraftFields.toSnapshotKeys`）
>    ⇒ 推导链最高层「显式字段」有了结构化载体。
>
> 下面 1./2./3. 三条理由对**写入口**仍然成立（扁平键 = 零改动即有通路），故保留原文。

理由（按「最少代码阶梯」）：

1. **既有消费者全部读顶层** —— `buildSnapshot` 用 `copyIfPresent(pi, entry, key)` 从 `processing_info` 顶层逐键取
   （`ProcessingOrderService.java` 的 `buildSnapshot`），`calcInfo(entry)` 也从 `entry` 顶层按 `CALC_INFO_KEYS` 取（`ProcessingOrderService.java` 的 `CALC_INFO_KEYS` / `calcInfo`）。
   扁平 = 零改动即有通路。
2. `specialOptions` 已是顶层扁平键且已接线（`ProcessingOrderService.java` 的 `buildSnapshot`），新字段与它同层最一致。
3. JSONB 加键**无需迁移**（#4230 v1a 已确立该模式），存量单不受影响（缺键 = 未携带，不是错值）。

> **粒度对齐（ERP 实证）**：ERP 的「部位行」（布帘 / 纱帘 / 帘头 各一行）**就是**本系统的 `order_items` 一行。
> 故 §4.2 的字段全部落在 **order_item 级**，与 ERP 一一对应。
> 另注：ERP 特殊选项按 **部位 tab（全部/布帘/纱帘/帘头）** 过滤 ⇒ 选项是**部位级**的，
> 落在 order_item 级 `specialOptions` 上**语义正确**（不是订单级）。

### 4.2 字段表 A：工艺规格（本方案新增键）

| key | 类型 | 取值 | 真值来源 | 消费方（落码后） | ERP 对应列 |

### 4.8 ⚠️ 拼色的结构缺口：订单行装不下两种布（用户已裁定建模方向）

**现状事实**

| 事实 | 证据 |
|---|---|
| `order_items` 只有**一个** `productId` / `productName` | `OrderItem.java` 的 `productId` / `productName` 字段 |
| 「部件」层（主布/配布边/纱/加工费）**从未落码** | `部件` / `bom` 在 `backend/**` **零命中**；仅 §8 术语表有词条 |
| `processing_info.processingItems` 是**加工项**（收费项：打孔/韩褶），**不是面料部件** | 二者语义不同，**不可混用** |

#### 用户裁定（2026-09-18）

- 双拼 = **主布 + 配布边 + 加工项** 三条明细行
- 拼色建模取 **两行 `order_item`**（主布行 + 配布边行）；加工项沿用既有 `processing_info.processingItems`

#### 设计：一扇窗 = 一个「工艺行组」

```
主布行（order_item #1）   ← 承载全部工艺规格（§4.2）+ 算料输出（§4.3）+ processingItems
  └─ craftLineId ────────┐
配布边行（order_item #2） │  ← 只承载：货号/色号/门幅/米数 + componentRole=配布边
  └─ craftLineId ────────┘     **不携带工艺规格、不独立成加工部位**
```

**新增三个键（落在 `processing_info` 顶层，零迁移）**

| key | 类型 | 取值 | 作用 |
|---|---|---|---|
| `componentRole` | string | `主布` / `配布边` / `纱` | 明细行角色；缺省视为 `主布`（存量单兼容） |
| `craftLineId` | string | 主布行的 `order_item.id` | **把同一扇窗的多行绑成一组**（`craftLineId` 自指亦可） |
| `metersSource` | string | `跟随主布` / `人工指定` | 配布边米数的**取值来源**（§8 口径纪律：折数/用料必须带来源，防多渠道不一致） |

> ⏸ **接高暂缓**：原设计的 `spliceHeight`（接高落行）**本轮不实施**（§3.2）。
> 接回来时在本表加一行即可，**不改已有键语义**。

> ⚠️ **语义扩展（issue #4387，用户裁定 2026-09-19）**：`craftLineId` 从「把配布边行吸收进主布行」
> 扩展为「**标识同一樘窗**（一个窗户）」—— 部位 = 一行明细 = 一件帘 ⇒ **布行与纱行各自成部位**，
> 只有 `componentRole=配布边` 的行**不独立成部位**。樘窗是**套级工序**（#4384）与**加工费**（#4386）
> 的归属层级。权威口径见 `position-instance-routing-model.md` §5.9（R-a / §5.6）。
>
> ⚠️ **写侧（issue #4395）**：下单页此前**只在拼色时**写 `craftLineId` ⇒ 「布 + 纱」两行都缺该键
> ⇒ 消费端按行回落 `itemId` ⇒ **两行各成一樘窗**（套级工序被算两遍）。现下单页每行有**「樘窗」窗号**：
> **同一扇窗的多条部位行填同一个窗号 ⇒ 同一个 `craftLineId`**（取该樘窗**主布行**的行标识，§4.8 口径）；
> 留空 ⇒ 本行自成一樘窗（**存量语义不变**）。⚠️ 写侧只负责**让分组成立** —— 加工单侧的
> **套级去重**属 #4384 A2（未实现前，`外帘装袋` 仍按部位实例化 2 次）。

#### 为什么必须「工艺规格只挂主布行」

折数 / 开数 / 幅数 / 褶距 是**一樘窗**的属性，不是每块布的属性。
若**配布边行**也带工艺规格 ⇒ 加工单会多算一个部位 ⇒ **工序与计件翻倍**、用料双算。
故：消费端按 `craftLineId` 判定**配布边行是否被同组主布行吸收**（`buildSnapshot` / `buildPositionPayload`
的分组逻辑）—— ⚠️ 这不是「同组只保留一个部位」（布行 + 纱行同组时是两个部位，见上「语义扩展」）。

**加工单展示**：配布边作为同一部位下的**部件行**（§1「部件 = 明细行粒度」），
部位行字段（部位·类型·型号·批号·单价·用料·褶数·幅数·小计）照旧。

#### ✅ 已裁定（用户 2026-09-18）：加工费米数按主布算

> 「加工费是按米算的，**米数都按主布来算**；配布边米数和主布一样**但是可以编辑**。」

| 口径 | 裁定值 |
|---|---|
| **加工费米数** | = **主布行米数**（与配布边米数**无关**） |
| **配布边米数** | **默认 = 主布米数**，但**可手工编辑** ⇒ 需标 `metersSource ∈ {跟随主布, 人工指定}` |
| **面料米数** | = Σ 各面料行米数（主布 + 配布边 + 纱） |

⇒ **两个米数会分叉**：改配布边米数只动**面料费**，不动**加工费**。
这正是 ERP 订单头把「**面料米数**」与「**加工费米数**」做成**两个独立字段**的原因
（§10 此前只登记「两个口径目前同值，未分别展示」，现给出成因与口径）。
`curtain_calc` 现在只有一个 `meters` 同时算面料费与加工费 ⇒ 需**拆成两个**（口径已裁定，见 §6.1）。

> ⚠️ **一致性硬约束**：报价单展示的工艺参数，必须**就是**下单时落库的那一份对象。
> 否则会出现「报价单写双开、订单记单开」——**对顾客的承诺与履约不一致，比不展示更糟**。
> 实现上：`curtain_calc` 输出补上 `curtain_type` / `craft` / `is_shaped` / `style` / `special_options` 后，
> 报价卡直接渲染它，`order_create` 把**同一个 dict** 原样落库（**不重新拼装、不二次推导**）。

#### 加工单快照必须扩白名单（否则第 ③ 处永远拿不到）

`ProcessingOrderService.java` 的 `buildSnapshot`（`copyIfPresent` 段） 用 `copyIfPresent(pi, entry, key)` **逐键**取顶层键 ——
**新键不加进这个列表就不会进快照**。需补：`curtainType` / `craft` / `cuttingMode` / `openCount` /
`isShaped` / `pleatSpacing` / `style` / `room` / `hasPattern` / `patternRepeat` + §4.3 的全部算料输出键。
（加工单快照是**加工单的固化真相**，生成时的条件工序与计件系数都从快照读 ⇒ 漏一个键 = 车间少一道活。）
