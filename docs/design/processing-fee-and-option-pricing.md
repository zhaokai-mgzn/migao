## 0. 一句话结论

**ERP 的「加工项」= 组合价目（特征集合 → 元/米），不是「单价 × 数量求和」。**
因此本方案把计价切成两层账：

```
对客加工费(每订单行) = 组合价(元/米) × 加工费米数
                     + Σ 选中特殊选项( 单价(元/套) × 套数 )       套数 = 本行所属**樘窗**的计费套数
                                                                  （1 套 = 1 樘窗 = 一个 craftLineId 组，
                                                                   issue #4725；同一樘窗内同名选项只收一次）
                     + 拼色加价(元/米) × 该款面料米数             ← #4855 追加的**第三个分量**
                                                                  （`款式=拼色` 才计；一樘窗只收一次）
订单总价             = Σ 用料行金额(面料 / 配布边 / 纱帘) + Σ 加工费
```

> 🔴 **#4855 改判（用户 2026-09-21 裁定，最高优先）**：**`拼1次` / `拼2次` 这两项特殊选项
> 不再按「元/套」计**，改按**拼色加价（元/米 × 该款面料米数）**计 —— 与报价侧
> （`curtain_calc.build_quote`）**同源同价**。落码 = `ProcessingFeeCalculator` 的
> `MIXED_COLOR_SURCHARGE_PER_METER` / `PER_METER_MIXED_OPTIONS` / `billing=per_meter`；
> 跨语言同源判据 = `tests/unit_ci_workflows/test_mixed_color_surcharge_cross_side.py`。
> ⚠️ **只动这两项**：其余 15 项特殊选项的元/套价一字未动（同一份 V82 种子里的
> `双眼皮接高` / `布绑带` / `纱绑带` … 照旧）；`拼3次` 也不在本裁定范围（纸表未登记其用料系数 ⇒
> 仍按元/套）。⚠️ **数据面未动**：V82 那两笔元/套价仍在库里（改口径 ≠ 改数据，已发布迁移不可改）；
> 取价侧把这两项记为 `billing=per_meter`（**`priced=true`** ⇒ 不会落进「未定价」状态）。

   + 自动推导特征：超高 / 超宽 / 倒幅（见 §5）

L3 价目层（对客账 · 两套账分离，与 L1 绝不互读）
   ① 组合价目  processing_fee_combinations          特征集合 → 元/米（92 行）
   ② 选项价目  production_route_rules.customer_unit_price  特殊选项 → 元/套（新增列，V77）

L4 单据层
   订单 order_items + processing_info（费用明细快照，R13 快照冻结 ⇒ 改价不回算历史）

**R9 的语义**：`是否定型 / 超高 / 超宽 / 倒幅` 从「工艺规格字段」搬到 **L2 特征**，

### 4.2 取价公式（`ProcessingFeeCalculator` 唯一实现）

```
fee(行) = comboUnitPrice(元/米) × processingMeters        // 既有 #4406 口径，不变
        + Σ_{opt ∈ 选中特殊选项} customerUnitPrice(opt) × 1  // 新增（R5 + R8）
```

- `processingMeters` 键族不变（`processingMeters` / `fabric_meters`）；缺米数 ⇒ `unpriced`（不猜）。
- 组合未命中 ⇒ 整体 `fee_source='unpriced'`、金额 = 0、**不回落** Σ 加工项（既有纪律）。
- 组合命中 ∧ 某选项未定价 ⇒ `fee_source` 仍 `matched`（组合那半有效），
  **该选项在 `special_options[]` 里 `priced:false` + 计 0**，并给**可行动 hint**（指向定价入口）。
  ⇒ 「未定价」有两层，**都必须在 detail 里可判**，不许静默。

### 4.2.1 人工改价（行级 override）与「建单回写组合价目」（2026-09-21 用户裁定，issue #4872 / #4874）

> 用户原话：「订单中加工费组合**未配置**的情况下，**允许更改该单价**，并且在**加工项下面添加具体的组合名**」；
> 「当订单**创建成功后**，同步**新增加工费组合&单价**到加工费配置中」。

背景：V77 的 92 行合成组合价目**全部 `status='disabled'`**（§1 已登记「组合价目等 ERP 导出后再做」）
⇒ 今天**任何订单都取不到组合价**。本次给商家一条**自建价目**的通路（不是回落、不是默认价）。

```
fee(行) = processingFeeOverride(元/米) × processingMeters   // 仅当组合未命中 ∧ override 为正数
```

- **采用条件（唯一）**：该行组合**未命中**活跃价目（`pricedCombinations` 查不到 `composition_key`）
  **且**组合键非空 **且** `processingInfo.processingFeeOverride` 是正数 ⇒ 记 `fee_source='manual'`、
  `unit_price` = override、`amount` = override × 米数、`price_source` = `manual`。
- **命中时忽略 override**（既有组合价不受影响）—— 「商家改了价但取价还是命中价」是**静默错价**，
  故命中一律不采 override（有红证）。
- **无 override 且未命中** ⇒ 与改前**逐字不变**：`unpriced`、组合那半 0、不回落 Σ 加工项。
- **缺米数** ⇒ 仍是 `unpriced`（override 也救不回来：米数是另一个因子，不猜）。

**建单成功后的回写**（同一事务内）：对每条 `fee_source='manual'` 的行
`upsert processing_fee_combinations`（`composition_key` 走 `ProcessingFeeCombinationCommandService.compositionKey`
**同源口径**、`items` = 规范化特征名、`unit_price` = override、`status='active'`、`source='实证'`
+ 追加版本台账）：
- 已存在同键 **active** 行 ⇒ **不覆盖它的价**（该行本该命中，走到 override 说明是历史/竞态）；
- 已存在同键 **disabled** 行 ⇒ **复活为 active 并写新价**（V77 那批正是 disabled ⇒ 这是主路径）；
- 都不存在 ⇒ 新建。

⇒ 商家的「这一单收多少」与「配置里这个组合多少钱」从此**同一份真值**，不会各说各话。
⚠️ **缺选配信息（组合键为空）⇒ 不给改单价入口**：没有 key 就没有可同步的对象，
界面如实报「没有可匹配的组合（缺选配信息）」，不假装能定价。

## 5. 术语与自动识别（D6）

### 5.1 倒幅 / 正幅（用户已确认，落成**推导**）

| 术语 | 含义 | 推导 |
|---|---|---|
| **正幅** | 定高买宽：布门幅 = 帘**高**方向，花型**正着**用 | `cuttingMode == 定高买宽` |
| **倒幅** | 定宽买高：布旋转 90°，门幅变成**宽**度方向，花型**倒了** | `cuttingMode == 定宽买高` |

⇒ **由 `cuttingMode` 唯一推导，不设手选项**（设手选项 = 制造与 `cuttingMode` 冲突的第二份口径）。

### 5.2 超高 / 超宽（**与门幅比较，自动识别**）

**推理证据链**（都来自 §1 读准的行）：

1. **定价对称**：`韩折+超高` 9.00 = `韩折+超宽` 9.00；`韩折+超高+定型` 10.00 = `韩折+超宽+定型` 10.00
   ⇒ 同一类加价的**两个维度**；
2. `韩折+超高+**接高**+定型` **同时存在** ⇒ **超高 ≠ 需要接高**（否则「接高」冗余）
   ⇒ 超高是**尺寸超限的加价维度**，「接高」是**具体工序**；
3. `韩折+**超宽+超高**+定型` **同时存在** ⇒ 二者**不互斥**（不是「定高买宽 / 定宽买高」二选一）。

**自动识别规则（冻结）**：

```
门幅 G   = SKU.doorWidth（**无缺省值** —— issue #4877 已删除「缺省 2.8 米」；窄幅布 1.4）
卷边常量 = **高方向**上下卷边 `HEM_MARGIN`（**复用** curtain_calc 既有常量，不新造第二个数）
褶倍 N   = 该行的名义褶倍（档位 / 款式值）

超高 = (成品高 + HEM_MARGIN) > G          # 只属「定高买宽」
超宽 = (窗宽 × 褶倍) > G                   # 只属「定宽买高」；= 算料引擎分幅条件的布尔形态
```

- 🔴 **2026-09-21 改判（用户裁定，issue #5030）**：订单行 `width` = **净窗宽**、`height` = **净窗高**
  ⇒ **成品宽 = 净窗宽、成品高 = 净窗高**；宽度用料 = `窗宽 × 褶倍`
  ⇒ **超宽判据里没有任何宽方向余量**（改前写的 `(成品宽 + 0.3) > G` 里的 `0.3` 是**左右覆盖余量**，
  该常量与配置键 `side_margin` **整体退场**，新迁移 `backend/admin-api/src/main/resources/db/migration/V112__drop_craft_calc_side_margin.sql`）。
  **高方向仍用上下卷边 `HEM_MARGIN`**（与改前同值，但**语义不同，不得混用**）。
- 🔴 **两个方向按加工类型分流，不是「两者独立可同时为真」**（issue #4661 / #4664 改判，本条 2026-09-21 同步订正）：
  `定高买宽` ⇒ **只判超高**（宽按米买、无上限）；`定宽买高` ⇒ **只判超宽** + 倒幅；
  加工类型缺失 / 表外取值 ⇒ **两个方向都不判**（保守，不猜朝向）。ERP `韩折+超宽+超高+定型` 的
  「同时出现」由**一个推算 + 一个强制加**达成（**不是**同一次判定里两条独立阈值为真）。
- ⚠️ **超宽判据必须含褶倍**（issue #4662，用户 2026-09-20 裁定 A「含褶倍，与算料引擎一致」）：
  只比 `宽 > 门幅` 会**漏报韩褶大窗**（1.5 宽 × 2.0 倍 = 3.0 米要分 2 幅，而 1.5 ≤ 2.8 会判「不超宽」）
  —— 分幅才是多花钱的地方。判据与 `backend/ai-agent-service/app/tools/curtain_calc.py` 的
  `ceil(窗宽 × 褶倍 ÷ 门幅)` **同源**（前端副本 = `frontend/admin-web/src/lib/craft-auto-features.ts`，
  跨语言守卫 = `tests/unit_ci_workflows/test_panels_formula_split_audit.py`）。
- 阈值 `G` 按真值源 §2【默】「经验默认值，需商家可配置」处理：**给默认值 + 商家可配**；
- ⚠️ **照实登记**：本条是**推理，非实证**（未从 ERP 供应商处取得判据）。
  按 #4261 的做法标注 `source='推算'` + 可配，**不假装定论**。

### 5.3 特征集合的构成（进组合键的输入）

```
特征集合 = 手选特征（来自 L2 加工项目录）
         ∪ 自动特征（超高 / 超宽 / 倒幅，按 §5.1~5.2 推导）
         ∪ 工艺特征（韩褶 / 打孔 / 四爪钩 / 穿杆 / 平幔，来自工艺规格 `craft`）
         ∪ 定型（来自 `isShaped`）
⇒ composition_key = 归一化(特征集合)   // TreeSet 升序 + '+' 连接（**复用既有唯一实现**）
```
