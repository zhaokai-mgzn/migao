## 0. 一句话结论

1. ✅ **客户说的「宽 > 6 / 高 > 4」不是行业通用定义，也不是本系统在用的判据。**
   本系统用的是**几何硬约束**（与**门幅**比）：超宽 = `窗宽 × 褶倍 > 门幅`、超高 = `成品高 + 上下卷边 > 门幅`。
2. ✅ **行业里没有可引用的国标 / 行标规定「超高 / 超宽」的阈值** —— 这一点**本仓库自己的行业核查已经下过结论**
   （见 §2.4，真值源 `docs/design/door-width-auto-selection.md` §5.1）。行业里**硬的只有几何约束**，
   其余是**弱经验建议**（且三处口径互相不一致）。
3. 🔶 ⇒ 「6 米 / 4 米」几乎可以确定是**该商家自定的业务阈值**（加价档 / 工艺分档 / 特殊单标记），
   与几何约束**不在同一层**，**不能拿来替换**现有判据。
4. ✅ **用户已裁定（2026-09-22）**：D1 = **工艺分档**（超阈值时加工费与标准档不同）、
   D2 = `6/4` 是**客户口径** ⇒ 做成**企业参数**、D3 = **替换**当前判定公式、
   D6 = 落点 = **新建统一「企业参数」页 / 表**。裁定登记见 §7.1。
5. ✅ **「替换」可行，且爆炸半径比预想小**：几何层（管**用料**）与特征层（管**加工费**）在代码里
   **是分离的**（§4.4 已读源核实）⇒ **替换只改加工费组合键，不改用料米数、不改加工类型**。
6. 🔴 **但替换会把「超高 / 超宽」从高频特征变成罕见特征**：2.8 门幅下今天「成品高 > 2.5 米即判超高、
   窗宽 > 1.4 米即判超宽」，替换后要「窗高 > 4 / 窗宽 > 6」才判 ⇒ **大量原本按高价档的单会落到
   更便宜的档（或 `unpriced` 恒 ¥0）**，方向与「超宽 / 超高 = 更贵一档」的直觉**相反**。
   §4.4 的表格**必须客户书面确认**（D9）。
7. 🔴 替换会**连带退役三条既有裁定**（#4661 加工类型分流 / #4662 超宽含褶倍 / #4877 判定面门幅），
   需**显式改判留档**（§4.4 / D10）。
6. 🔴 「整合到一块」建议新建**企业参数**统一配置，但**成本与风险被严重低估**：
   加一个算料配置键今天要**同步 6 处**（§3.4），统一表会把这件事的守卫面**扩大而非缩小**。

## 1. 先把术语摆正（这是商家与系统「各说各话」的根因）

✅ 真值源：`frontend/admin-web/src/lib/craft-calc-glossary.ts`（页面「口径与术语说明」的单一真值模块）
与 `backend/ai-agent-service/app/tools/curtain_calc.py`。

| 术语 | 谁判 | 判据（现状） | 影响什么 | 当前落点 |
|---|---|---|---|---|
| **超高** | 系统**推算** | 加工类型 = `定高买宽` 且 `成品高 + 上下卷边 > 门幅` | ①进加工费组合键；②引擎改走定宽买高 ⇒ **米数会变** | 引擎 `detect_auto_features` |
| **超宽** | 系统**推算** | 加工类型 = `定宽买高` 且 `窗宽 × 褶倍 > 门幅` | ①进组合键；②**真正多花钱的是分幅**（幅数向上取整） | 引擎 `detect_auto_features` |
| **倒幅** | 系统**推算** | 加工类型 = `定宽买高`（唯一推导，无手选项） | 进组合键；每幅长按「成品高 + 上下卷边」 | 同上 |
| **正幅** | **不推导** | —— | 不在加工项目录里 ⇒ 推它会让每张默认单的组合键匹配不到价 | 有意不做（#4592 的 P0） |
| **拼接** | **手选** | 系统不推算 | 进组合键；当前**只影响加工费、不触发工序** | 特殊选项 / 加工项 |
| **接高** | **手选** | 系统不推算 | 插「接高」工序 + 加工费（按幅 / 按套）；**不改用料米数** | 特殊选项（`接高` / `双眼皮接高`） |

🔴 **本报告要守住的第一条**：「超高 / 超宽」在本系统里是**两个会进加工费组合键的特征名** ——
它们不是「描述性标签」，是**取价键的一部分**。给它们**加一个触发条件**（哪怕名字不变）
就等于**改变取价**（见 §3.2 的 P0 实证）。

## 2. 行业背景：超高 / 超宽到底有没有「通用定义」

### 2.1 行业里**硬**的只有一条：几何约束

✅🔶 真值源 `docs/curtain-fabric-quote-rules.md` §2 / §3；`docs/design/door-width-auto-selection.md`
的「定高买宽不可行的判据与行业标准的有无」一节同判：

```
定高买宽不可行  ⟺  成品高 + 上下卷边 > 门幅有效值
定宽买宽要分幅  ⟺  ceil(窗宽 × 褶倍 ÷ 门幅) ≥ 2
```

这不是「行业惯例」，是**物理硬约束** —— 布做不出就是做不出，**无需来源、不可配置**。

### 2.2 门幅的行业标准值（这一层是行业标准值【标】）

🔶 来源见 `docs/curtain-fabric-quote-rules.md` §2，以及
`docs/curtain-selling-method-industry-research.md` 的门幅一节（下面的数值取自这两处）：

| 门幅 | 常见品类 | 对应买法 |
|---|---|---|
| **2.8 ~ 2.9 米**（大门幅；亦有 2.7 / 3.0） | 遮光布、纱帘 | **定高买宽**（横挂，按宽度买米） |
| **1.4 ~ 1.45 米**（小门幅） | 棉麻、真丝、部分雪尼尔/绒布 | **定宽买高**（竖挂，按高度买米） |

⇒ 几何约束换算成「成品高上限」（`hem_margin` 取引擎默认值）：**1.4 → 1.1 米 / 2.8 → 2.5 米 / 3.0 → 2.7 米 / 3.2 → 2.9 米**。
**注意：这些数没有一个接近 4 米。** 一扇 4 米高的窗，**任何**门幅都做不出定高买宽 ⇒ 必然走倒幅或接高。

### 2.3 「选型经验阈值」这一层**弱且自相矛盾**

🔶 同一件事（层高多少该换买法）在三处出处里给了**三个不同的数**：`≤2.7` / `>2.75` / `≤2.8`。
证据强度最强只到「媒体 / 从业者」，且其中引用的《国家住宅建筑设计规范》层高条文，
调研文档**自标「未溯源 · 待确认」**。

### 2.4 🔴 **行业结论：没有国标 / 行标**（本仓库已核查过）

✅ `docs/design/door-width-auto-selection.md` §5.1 的结论**逐字**是：

> **结论：没有一条可引用的国标 / 行标规定「定高买宽何时不可行」。** ①②可编码，③**不编码**（只作话术背景）。

同一节把行业口径分成三层，并明确**只有第一层是硬的**：

| 层 | 内容 | 性质 | 证据强度 |
|---|---|---|---|
| ① 几何约束 | `成品高 + 卷边 ≤ 门幅` | **物理硬约束** | 无需来源 |
| ② 门幅标准值 | 定高布 2.8（亦有 2.7/3.0）；窄幅 1.4 | 行业标准值【标】 | 中 |
| ③ 选型经验阈值 | 「层高 ≤ 2.7 / 2.75 / 2.8 ⇒ 用定高布」 | **经验建议，非约束** | **弱**（三处互不一致） |

### 2.5 「超高窗怎么办」的行业实践：**走倒幅，不走接高**

🔶 来源 `docs/curtain-selling-method-industry-research.md` §3.3（S16 = 媒体 / 从业者，**证据强度中，非实证**）：

> 层高不超过 2.7 米时用 2.8 米定高布最合适；**若层高超过 2.75 米，用定高布做上下拼接拼痕明显，
> 建议改用定宽买高做左右拼接、把拼接藏进褶皱**。

⇒ 即 **接高 = 上下拼接、横缝可见**；**倒幅 = 左右拼接、竖缝藏进褶皱**。
这正是 #5013 裁定「**接高不参与自动比较**」的依据：自动选接高 = 系统性推荐可见横缝。

🔶 而接高**唯一「必须」**的场景是**花型 / 纹理有方向**（竖条 / 大花型 / 提花 / 绣花 / 绒布顺毛 ⇒ 不能倒幅）。
✅ 但本系统今天**会对有方向的花型照样倒幅，且无任何告警**（`docs/design/door-width-auto-selection.md` §5.1
「接高**没有自动触发条件**」一节**已登记**该缺口；用户 2026-09-21 裁定「暂不加『不可倒幅』输入」）。

### 2.6 §2 的来源与证据强度汇总

| # | 结论 | 出处 | 强度 |
|---|---|---|---|
| 1 | 门幅分两档：大门幅（定高买宽的基准）与小门幅（定宽买高的基准）—— 数值见本节上面的门幅表 | `docs/curtain-fabric-quote-rules.md` §2；`docs/curtain-selling-method-industry-research.md` 的门幅一节 | 中（多源一致） |
| 2 | 定高买宽不可行 = 几何约束 | 物理推理 + ERP 加工单实证锚点 `CSO260915-02615` | **硬** |
| 3 | 「没有国标 / 行标规定超高阈值」 | `docs/design/door-width-auto-selection.md` §5.1 | **已核查结论** |
| 4 | 超高窗走倒幅、接高横缝可见 | `docs/curtain-selling-method-industry-research.md` §3.3（S16） | 中（**行业实践推理，非实证**） |
| 5 | 6 米 / 4 米 这两个数 | **任何真值源里都没有** | —— **无出处** |

> 🔴 **第 5 行是本报告最重要的读数**：我们**找不到** 6 / 4 的行业出处。
> 它极可能来自该客户自己的 ERP / 报价习惯 —— 这恰恰**印证了用户的判断**「每个企业的参数可能不一样」。

## 3. 代码真值（现状核实）

### 3.1 判据的唯一实现

✅ 唯一真值源 = `backend/ai-agent-service/app/tools/curtain_calc.py` 的 `detect_auto_features`。
前端副本 `detectAutoFeatures` 已随 #5035 **删除**（`frontend/admin-web/src/lib/craft-auto-features.ts`
的模块头**逐字**登记「本模块已不做判定」）。服务端入口 = `POST /api/admin/orders/auto-features`
（Java `AutoFeaturesController` → `CraftCalcClient` → 引擎 `/api/internal/production/auto-features`）。

判据要点（**改任一条都是改钱**）：

- **按加工类型分流**：`定高买宽` ⇒ 只判超高；`定宽买高` ⇒ 只判超宽 + 倒幅；**缺省 / 表外 ⇒ 一个都不判**（保守不猜朝向）。
- **门幅无缺省值**：门幅 = **该 SKU 的门幅**；SKU 未维护门幅 ⇒ **不判**（#4877 已删除「缺省 2.8 米」）。
- **订单宽高 = 净窗宽 / 净窗高**（#5030）⇒ 成品宽 = 净窗宽、成品高 = 净窗高；
  **宽方向没有任何余量**（`SIDE_MARGIN` 与配置键 `side_margin` 已整体退场，见
  `backend/admin-api/src/main/resources/db/migration/V112__drop_craft_calc_side_margin.sql`）；
  **高方向只剩 `HEM_MARGIN`**（配置键 `hem_margin`）。
- 命中项标 `source="推算"`（判据是**行业推理、非 ERP 实证**）。

### 3.2 为什么「改判据 = 改钱」（P0 实证）

✅ 自动特征进**加工费组合键**：`processingInfo.processingItems[]` → 服务端 `ProcessingFeeQueryService.featureNames()`
只读该数组 → 与商家配的「加工费组合」（如 `韩折+超宽+定型`）匹配 → **匹配不到 ⇒ `fee_source='unpriced'` ⇒ 加工费 ¥0.00**。

**已发生的 P0**（#4592）：自动推导里多了个 `正幅`，而加工项目录里**没有**「正幅」⇒
商家永远配不出含它的组合 ⇒ **每一张默认订单加工费恒 ¥0**。

⇒ 推论（本报告的核心风险读数）：**给「超高 / 超宽」这两个名字加一个触发条件 = 多标特征 = 组合键变 = 改价**。
「参数化」在这里**不是**中性的重构。

### 3.3 现有的**企业级**算料配置（这就是「整合到一块」的现成地基）

✅ 表 `craft_calc_configs`（`backend/admin-api/src/main/resources/db/migration/V80__create_craft_calc_configs.sql`，
bootstrap 终态同步在 `docs/sql/schema.sql`）。**9 个配置键**：

| 键 | 语义 |
|---|---|
| `per_fold_single` | 单色每折吃布（米） |
| `per_fold_mixed_times` | 拼色「拼次 → 每折吃布」（JSONB） |
| `margin_single` / `margin_multi` | 单开 / 多开余量（米） |
| `min_fullness` | 褶倍下限（**护栏，可配不可关**） |
| `tiers` | 工艺档位（JSONB：档位 → 名义褶倍） |
| `default_formula` | 兜底用料公式（`pleat` / `fullness`） |
| `hem_margin` | 上下卷边（米）—— **超高判据就用它** |
| `meters_rounding_step` | 用料向上进位步长（米） |

两条**已固化的重要口径**（会约束任何新方案）：

- **缺行 = 用引擎默认值**，**不做开租播种** —— 默认值唯一来源是引擎的 `DEFAULT_CRAFT_CALC_CONFIG`，
  库里再种一份 = **第二份会漂的默认值**（`V80` 的注释**逐字**登记了这条理由）。
- **结构化列，不是一整块 JSON** —— 列名与引擎配置键**逐字同名**，读写两侧零映射
  （「映射表」= 第二份键名口径的滋生地）；JSONB 只用于嵌套结构。

### 3.6 接高的**可达性**现状（照实登记）

✅ `docs/design/door-width-auto-selection.md` §6 与 issue #5040 复核结论：

- 引擎里**有**接高口径（`CUTTING_MODE_SPLICE`，口径 A：加高条按**片宽**另买、同一段布内并排裁），
  但**只在引擎 API 层可达** —— 工具 schema（`CurtainCalcTool.parameters`）、
  `CurtainCalcTool.execute` 签名、admin-web 的加工类型 chips **都没有**「接高」这一档。

- issue #4341 已把**接高整块暂缓**（用户 2026-09-18 裁定「先不管接高了」）。

⇒ 🔴 **用户提到的「接高参数（窗高 − 最优门幅 ≤ 0.1 米）」目前没有可挂靠的活路径** ——
它需要先补「接高」的入口（产品裁定），才谈得上参数化。

## 4. 客户口径 vs 现状：逐项对齐

### 4.1 客户说法的三种可能读法

🔴 用户已确认**量纲**：**净窗宽 / 净窗高，单位米**（6 米宽窗、4 米高窗）。**但「用途」未确认**：

| 读法 | 含义 | 与现状的关系 | 判据形态 |
|---|---|---|---|
| **R1 · 加价档** | 窗宽 > 6 或窗高 > 4 ⇒ 这张单**另收一笔**（或归入某价档） | **新增**，不影响现有组合键 | 新的加价规则，**不是**特征 |
| **R2 · 特征触发（同名）** | 窗宽 > 6 ⇒ 标「超宽」、窗高 > 4 ⇒ 标「超高」，进**同一个**组合键 | **替换**（同名冲突，见 §4.3） | 改 `detect_auto_features` 判据 |
| **R3 · 工艺分档** | 超过阈值 ⇒ 走特殊工艺（如强制拼接 / 强制接高） | **新增**工艺分支 | 新的工艺触发条件 |

🔶 从行业看，**R1 最可能**：6 / 4 在行业真值源里**没有任何出处**（§2.6 第 5 行），
而「大窗单独计价」是**商家自定**的常见做法 —— 正好对应「每个企业的参数可能不一样」这句话。

### 4.2 数值上的直接冲突（供客户确认时对齐）

| 客户说法 | 本系统现状 | 冲突性质 |
|---|---|---|
| 超宽 = 窗宽 > **6 米** | 超宽 = `窗宽 × 褶倍 > 门幅`（门幅通常 2.8 / 3.2） | **量纲不同**：现状比的是「所需幅宽 vs 门幅」，客户比的是「窗宽 vs 常数」 |
| 超高 = 窗高 > **4 米** | 超高 = `成品高 + 上下卷边 > 门幅`（2.8 门幅 ⇒ 成品高 > 2.5 米即触发） | **阈值量级差一个档**：现状在 2.5 米就判超高，客户说 4 米才叫超高 |
| 6 米 / 4 米 | **任何真值源里都没有** | **无行业出处** ⇒ 商家自定值 |

🔴 **反直觉但必须说清的一点**：如果**按字面**把现状判据换成 6 / 4，那么
**2.5 米高的窗在今天会判「超高」，改完就不判了** ⇒ 大量原本会进组合键的「超高」消失 ⇒
**加工费组合键变了 ⇒ 改钱**（而且是**减少**标记，方向与客户的「我要更多分档」诉求相反）。
这**几乎肯定不是**客户的本意 —— 所以 §4.3 的同名冲突必须先解决。

### 4.3 🔴 **同名冲突**（本报告最关键的一处判断）

「超高 / 超宽」在本系统是**进加工费组合键的特征名**。因此：

- 若客户口径要**沿用这两个名字** ⇒ 它与现状判据**不能并存**，只能**替换**（＝改钱，且如上文方向可能相反）；
- 若要**并存** ⇒ 客户口径**必须用新的特征名**（如「大窗」「超大窗」）或**不进组合键**（只做加价档 / 提示）。

⇒ **「参数化」在这里的真实形态是「加一层，不是换一层」** —— 但「加一层」要**先决定这层的名字与归属**
（特征？价档？提示？），这**必须客户书面回答**（见 §7 的 D3）。

### 4.4 替换的**精确爆炸半径**（✅ 已核实，2026-09-22；用户裁定 D1=R3 / D3=替换后补测）

**最重要的读数：几何层与特征层在代码里是分离的。**

✅ 证据（读源 `backend/ai-agent-service/app/tools/curtain_calc.py`）：`build_quote` 里
`auto_features` 是**在用料与全部金额算完之后**才写进返回字典的**纯输出字段**
（`meters` / 各类 `cost` / `total` 在此**之前**已定稿）；加工类型来自 `resolve_fabric_plan`
（**纯几何**：`成品高 + hem_margin` vs 有效门幅），**不读** `detect_auto_features` 的任何输出。

⇒ 🔴 **替换判定公式 = 只改「加工费组合键」，不改用料米数、不改加工类型。** 这比预想的小得多。

| 面 | 是否受影响 | 说明 |
|---|---|---|
| 用料米数 / 幅数 / 加工类型 | ❌ **不受影响** | 走 `resolve_fabric_plan` 的几何判据，与特征名无关 |
| 加工费组合键（**改钱**） | ✅ **受影响** | 特征名进 `processingInfo.processingItems[]` → `ProcessingFeeQueryService.featureNames()` → `compositionKey()` → 匹配组合价 |
| 前端展示（系统识别块 / 尺寸行徽标 / 依据文案） | ✅ 受影响 | 判定结果与依据文案随判据变 |
| 门幅选择规则（#4877） | ❌ 不受影响 | 走几何可行性，不读特征名 |

**会被「替换」一并推翻的既有裁定（必须显式确认，不能顺手删）**：

| 既有裁定 | 内容 | 替换后的状态 |
|---|---|---|
| #4661 | **按加工类型分流**（定高买宽 ⇒ 只判超高；定宽买高 ⇒ 只判超宽） | 🔴 **失效**：绝对阈值与加工类型无关 ⇒ 分流无对象；且两者**可同时为真** |
| #4662 | **超宽须含褶倍**（`窗宽 × 褶倍 > 门幅`） | 🔴 **失效**：新判据是 `窗宽 > 阈值`，**不含褶倍** |
| #4877（**判定面**） | 门幅无缺省值 ⇒ **缺门幅不判** | 🔴 **判定面失效**（新判据不用门幅）；门幅仍是**几何层**输入（管用料）⇒ **保留** |
| #4592 | 自动特征清单 ↔ V83 目录**逐值对齐** | ✅ **保留**（清单不变，仍是 超高 / 超宽 / 倒幅） |
| #5030 | 宽方向无余量 | ✅ 保留（新判据本就没有余量） |
| #4976 | `hem_margin` 可配 | ⚠️ **失去一个消费点**（超高判据不再用它）；定宽买高每幅长 / 罗马帘仍用 ⇒ 键**保留** |

**改钱的形态（照实登记 —— 这一格必须客户确认）**：

以 2.8 米门幅、`hem_margin` 取默认值的商家为例，替换后（阈值 = 客户口径 6 / 4）：

| 窗（宽 × 高） | 今天判什么 | 替换后判什么 | 后果 |
|---|---|---|---|
| **3.0 × 2.7**（家用常见） | 定高买宽 ⇒ **超高**（2.7+0.3 > 2.8） | **都不判**（宽 ≤ 6、高 ≤ 4） | `韩折+超高+定型` → `韩折+定型`（**价变**） |
| **1.5 × 2.0**（定宽买高） | **超宽**（1.5×2 = 3.0 > 2.8） | **都不判** | 超宽消失 ⇒ 组合键少一项（**价变**） |
| 6.6 × 2.6（定宽买高） | **超宽**（13.2 > 2.8） | **超宽**（6.6 > 6） | 恰好同结果（巧合，不是等价） |
| 4.0 × 4.2 | **超高**（4.5 > 2.8） | **超高**（4.2 > 4） | 恰好同结果 |

🔴 **前两行是本报告最需要客户确认的**：替换后「超高 / 超宽」从**高频特征**（2.8 门幅下
成品高 > 2.5 米即判超高、窗宽 > 1.4 米即判超宽）变成**只在大窗出现的罕见特征**。
若商家给「含超高 / 超宽的组合」配了**更高**的价（D1 说「加工费和标准的不一样」），
那么替换后**大量原本按高价的单会落到更便宜的档（或 `unpriced` 恒 ¥0）** ——
这与「超宽 / 超高 = 更贵的一档」的直觉**方向相反**。**必须在落码前拿到客户对这一格的书面确认。**

## 5. 方案对比

| | **A · 替换**（改成绝对阈值） | **B · 分层并存**（**推荐**） | **C · 企业可选切换** |
|---|---|---|---|
| 形态 | `detect_auto_features` 判据换成 `窗宽 > 6` / `窗高 > 4` | 几何层**不动**；新增**商家阈值层**（企业参数），决定加价档 / 特殊标记 | 新增配置键 `oversize_rule`，在「门幅相对 / 绝对阈值」间切换 |
| 影响面 | 引擎 + 6 处配置同源 + 8 个守卫测试 + 用例库 + 真值源文档 | 新增配置键（6 处同步）+ 新页面 + 取价链新增一层 | 引擎加分支 + 配置键 + 两套判据都要维护 |
| 改钱风险 | **高**（且方向可能与客户诉求相反，§4.2） | **低**（默认 = 不启用 ⇒ 零回归） | **中**（切换即改钱，需灰度） |
| 推翻既有裁定 | **是**（#4661 / #4662 / #4877 / #4976 / #5013 / #5030 全部涉及） | 否 | 部分（等于承认两套口径都"对"） |
| 符合「每个企业不一样」 | 否（变成**全平台统一**的绝对阈值） | **是** | 是 |
| 结论 | ❌ 不建议 | ✅ **建议** | ⚠️ 备选（若客户坚持"切换"语义） |

**为什么不建议 C**：C 会让「超高 / 超宽」这两个名字在**不同租户下含义不同** ——
而它们进的是**同一张加工费组合表**。同一个组合名（`韩折+超宽+定型`）在不同租户下由**不同判据**产出，
出问题时**无法从组合名反推判据**（仓库纪律：**标注一律按实际端别 + 证据，禁止从判据反推**的同族病）。
B 把两件事**分成两个名字**，可反推、可审计。

## 6. 「企业参数」统一配置的设计建议

### 6.1 三层模型（建议的收敛形态）

```
第 1 层 · 几何层（不可配 · 系统推算）
   └ 判据 = 与门幅的几何关系（成品高 + 卷边 > 门幅；窗宽 × 褶倍 > 门幅）
   └ 决定：用料米数、加工类型（定高买宽 / 定宽买高 / 倒幅）
   └ 现状：不动。这一层「参数化」在物理上没有意义（布做不出就是做不出）

第 2 层 · 商家阈值层（企业参数 · 可配）        ← 本报告建议的落点
   └ 决定：加价档 / 特殊单标记 / 特殊工艺触发
   └ 候选键（均为「新增」，默认 = 不启用）：
        oversize_width_threshold   窗宽阈值（米）
        oversize_height_threshold  窗高阈值（米）
        splice_gap_tolerance       接高容差（窗高 − 最优门幅 ≤ 该值 ⇒ 判接高）

第 3 层 · 通用企业配置（非算料）
   └ 今天的 tenant_ai_configs（自动转人工关键词 / 营业时间 / 机器人名称 / 渠道配置…）
   └ 与算料无关，不建议与第 2 层混表（混表 = 把「算料口径」的守卫面扩大到无关配置上）
```

### 6.2 落点对比：整合 vs 新建统一表

| | **整合进 `craft_calc_configs`** | **新建统一「企业参数」表**（用户倾向） |
|---|---|---|
| 迁移成本 | 低（新迁移加列 + 6 处同步） | **高**（存量 9 键 + 端点 + Java 实体 + 前端页 + 6 处同源守卫**全部重做**） |
| 契约风险 | 低（既有守卫继续生效） | **高**（迁移期两套读取路径并存 = 第二份会漂的口径） |
| 守卫面 | 不扩大 | **扩大**（新表的「缺行 = 默认值」纪律要重新建立） |
| 符合「未来很多配置参数」 | 部分（算料参数天然内聚） | **是**（但通用键值表与本仓「结构化列」纪律冲突，见下） |
| 建议 | ✅ 第 2 层走这里（**省**） | ⚠️ 若坚持统一，**必须先出一份独立设计 + 迁移方案**（不属本报告范围） |

🔴 **与既有纪律的一处正面冲突**（必须先解决）：本仓的算料配置**明确选择了「结构化列」而非「一整块 JSON」**
（理由见 `V80` 注释：列名 = 引擎配置键，读写两侧零映射，SQL 可审计）。
一个**通用键值**（`key` / `value_json`）的企业参数表**天然是 JSON 形态** ——
两者混用会让「列名 = 引擎键名」这条契约**失效**，而它正是 6 处同源守卫的锚。
⇒ **若走统一表，必须回答**：算料键是「结构化列 + 通用表外挂」还是「全部键值化」？（后者要重写全部守卫）

### 6.3 若坚持新建统一表：必须保住的四条纪律

1. **缺行 = 引擎默认值，不做开租播种**（否则造第二份会漂的默认值）；
2. **键名 = 引擎配置键逐字同名**（否则出现「映射表」= 第二份键名口径）；
3. **读面显式给出 `source`**（`stored` / `default`），让「用的是谁的数」可观测；
4. **迁移期不允许两条读取路径并存**（先切读面、再删旧面；否则同一租户两个米数）。

### 6.4 零回归红线（任何方案都适用）

🔴 **新增阈值参数的默认值必须与现状等价** —— 即 **默认「不启用」**（`NULL` / 不判），
**不能**把默认写成 6 / 4。理由：写死 6 / 4 等于**对所有存量租户**立刻改变判定（§4.2 的改钱形态），
且会把一个**未经行业验证**的数变成**平台级默认口径**（§2.6 第 5 行：6 / 4 无出处）。

### 6.5 配置类页面 UX 原则（用户 2026-09-22 强调：「配置类页面务必要考虑配置复杂度和用户体验」）

**问题的真实形态**：本仓配置面今天散在 6 处（基本设置 / AI 客服设置 / 通知设置 / 算料配置 /
加工费组合 / 工序库 / 计件），而**算料参数直接改钱**（§3.2）。
⇒ 商家的真实痛点不是「参数太多」，而是：① **不知道改这个会变什么**；② **找不到**。

**已有先例（应推广，不是另起一套）**：`frontend/admin-web/src/lib/craft-calc-glossary.ts`
已经是本仓最成熟的配置页 UX 实践，它的**三条纪律**应当上升为**所有配置页的规范**：

1. **文案里不出现数字** —— 数值一律由真值渲染（写死一个数 = 造第二份口径；改了参数说明不跟着变 = 说明变假话）；
2. **口径与引擎同源** —— 说明里的算例**逐字转发服务端**判定（不前端自拼，不自己判）；
3. **键集必须覆盖引擎全部配置键** —— 加参数而不补说明 ⇒ **守卫红**（机械保证说明不腐烂）。

**七条原则**：

| # | 原则 | 反面形态（今天真实存在） |
|---|---|---|
| **P1** | **一处入口，按域分组**：企业参数中心，分组 = 算料 / 加工费 / 工艺 / 接单 / AI 客服 / 通知；组内再分「常用（默认展开）」与「高级（默认收起）」 | 参数散在 6 个页面，靠记忆找 |
| **P2** | **每个参数必带三件套**：`label` + 一行 `hint`（口径）+ `impact`（改它影响什么） | 只有 label，看不出口径 |
| **P3** | **默认值可见**：显式区分「当前值 / 引擎默认值」，并标出「未配置（正在用默认）」 | 缺行 = 用默认值（本仓口径），但商家**看不出**自己在用默认 |
| **P4** | **改钱的参数给护栏 + 预览**：改动前给「影响面 + 算例」（**服务端真值重算**） | 改完才发现米数 / 加工费变了 |
| **P5** | **术语可就地查**：参数旁「说明」锚点到术语条目（复用 `glossaryAnchorOf` 先例） | 术语与参数在两个页面 |
| **P6** | **变更留痕**：谁在何时把哪个参数从 A 改成 B | 无审计 ⇒ 出问题无法归因 |
| **P7** | **复杂配置可交给 AI**（复用 `docs/design/ai-craft-config.md` 阶段 2 的「AI 对话式改条件」） | 全靠表单手工点 |

🔴 **P4 是本行业的关键**：算料参数的每一项都直接改米数 = 改钱（§3.2），而商家**没有能力**心算
「把上下卷边从 0.3 改成 0.25 之后，我那些 2.7 米高的单会怎样」。
⇒ 「改完能预演」**不是锦上添花，是防错钱的必要条件**。

✅ **落点（用户 2026-09-22 裁定）**：这七条要写进**研发模式技能 `.agent-presets/migao`**
（「**结实的强制力**」—— 对后续所有会话与子 agent 生效，而不是只躺在一份文档里等人读）。

### 6.6 PR 2 的形态（✅ 用户 2026-09-22 裁定 **D6′ = 方案 A**）：**整合落在「页面 / 信息架构」，不落在「表结构」**

| 方案 | 商家体验 | 存储 / 契约风险 | 结论 |
|---|---|---|---|
| **A · 页面统一 + 存储保持结构化列** —— 算料键仍在 `craft_calc_configs`，其他域各自成表；对外只暴露**一个「企业参数」中心 + 一套读写端点** | ✅ 一处配置、一套分组与说明 | ✅ **零风险**：6 处同源守卫、`列名 = 引擎键名`、SQL 可审计 **全部保留** | ✅ **已裁定采用** |
| B · 全部键值化（单表 `key` / `value_json`） | ✅ 一处配置 | 🔴 **高**：要重写全部同源守卫；契约失效；SQL 不可审计 | ❌ 否决 |
| C · 结构化列 + 通用表外挂 | ✅ 一处配置 | ⚠️ 中：两套读取路径 | ❌ 否决 |

⇒ **「整合」用信息架构解决，不用并表解决。** 既满足「整合到一块」与 UX 原则，
又**不动**本仓最贵的那套契约（6 处同源 + 结构化列），并把原本风险最高的 PR 2 **降为低风险**。
