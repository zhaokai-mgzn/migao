## 0. 一句话结论

扫码端是**工位终端**（工人自主推进），不是「只报工」的被动端。
行业通用做法把这条链切成**五段**：`报工计件 → 配料 → 打包 → 发货 → 工资结算`。
**今天只有第一段落码**（报工 + 自动计件 + 自动完工），后四段缺。
其中**配料 / 打包 / 发货**三段在行业里都是「**工人扫码驱动的动作 + 一个留痕产物**」，
本方案按这个共性设计，**不新增状态机**（复用既有加工单状态 + 报工事实）。

## 1. 行业通用做法（ERP 实证 + 行业知识）

依据：客户现用 ERP（壁达 5.40.0）加工单实证（issue **#4343** 逐字记录）+ 布艺/软装制造通用流程。

| 段 | 行业动作 | 产物（留痕） | 驱动者 | 与计件的关系 |
|---|---|---|---|---|
| **① 报工** | 扫单 → 本部位待做工序 → 点完成 | 报工流水（人/工序/数量/时间） | 工人 | **直接产生计件金额** |
| **② 配料** | 「外帘配料」：按樘窗配齐**主料 + 配件**（钩/环/绑带/铅坠） | 配料单（逐件勾选） | 配料工 | 配料本身可计件（它是工序） |
| **③ 打包** | 「外帘打包」+ 打印标签（水洗标/条码/余料用途） | 包件 + 标签 | 打包工 | 打包工序计件；标签是**物理世界与系统的锚点** |
| **④ 发货** | 「外帘发货」：录入货运单号 | 发货记录（承运商 + 单号 + 时间） | 仓管/工人 | 不计件（但结算常按「已发货」口径切） |
| **⑤ 工资结算** | 按（人 × 期间）出结算单 → 确认 → **锁定** | 结算单 + 锁定标记 | 财务/管理 | **把①的金额冻结成应付工资** |

**三条行业共性（本方案的依据，不是发明）**：

1. **每一段都有一个「留痕产物」**，而不是只有一个布尔状态 —— 因为车间要能回答
   「这一包是谁打的、这一单发到哪了、这笔钱怎么算的」。
2. **打包的判据是「必完工序全绿」**（真值源 §5 已写：「全部『必须完成才可打包』工序完成后 →
   订单自动进入『生产完成』态」）—— 打包不是随便能做的动作，它**受必完工序门禁**。
3. **结算必须能锁定**，否则「结算了没有」无法回答、工资可被事后静默改写
   （真值源 §4 只到「工资报表 = 报工事件聚合」，**没有**结算层 —— 这是真实的缺口）。

## 3. 落地方案

### 3.0 总原则（三条）

1. **不新增状态机**：加工单状态仍是 `generated → in_processing → completed`；
   配料/打包/发货是**动作 + 留痕**，不是新状态。
2. **判据只有一份**：发货门禁（含加工项订单必须有 completed 加工单）**复用同一份**判定，
   工人端与管理端不得各写一份（#4347 §四 明文）。
3. **失败要显式**：配料缺件、打包门禁未过、发货无单号 —— 一律**指名报缺**，
   绝不静默通过（本仓库的核心纪律）。

### 3.1 工人端可见面（先补信息，再做动作）

**这是最小改动、收益最大的一步**：数据全在库里，只是 `getOperations` 没带出来。

`GET /production/orders/{orderId}/operations` 的 `positions[]` 扩展（**只加键，不改既有键**）：

| 新键 | 来源 | 用途（对应截图） |
|---|---|---|
| `width` / `height` | `order_items.width/height` | 「宽高 6.6*2.92」 |
| `craft` / `curtainType` | `order_items.craft/curtain_type` | 「安装工艺 韩褶」「布帘」 |
| `openCount` | `order_items.open_count` | 「打开方式 四开」 |
| `cuttingMode` | `order_items.cutting_mode` | 「加工类型 定高买宽」 |
| `isShaped` | `order_items.is_shaped` | 「部位定型 是」 |
| `fullness` | `order_items.fullness` | 「褶倍 2.00」 |
| `fabricMeters` / `processingMeters` | `processing_info`（算料输出，单一真值=ai-agent） | 「用料 12.3 米」 |
| `positionRemark` | 订单行备注 | 「部位备注：公式--48个折」 |

**硬约束**：这些字段**逐字取库/取快照**，不在 Java 侧重算（算料单一真值纪律）。
**决策 5 已裁定「精裁输出不做」** ⇒ 本节**不新增任何存储**，只做读面接线。

### 3.2 操作记录（读服务端，不读本机）

- 现状：工人端 `workLogs` 来自 `productionOffline` 的**本机 storage** ⇒ 换手机/清缓存就没了，
  且**看不到别人**在这张单上做的工序（截图里「操作记录」是**全单流水**）。
- 改法：`getOperations` 的响应**追加** `work_logs[]`（人/工序/数量/时间，来自
  `production_work_logs`，按时间倒序），工人端优先显示它；本机明细降级为**离线兜底**
  （弱网时显示并显式标注离线 —— 既有纪律不变）。

### 3.3 配料（②，新增动作）—— ⛔ **本节已被裁定否决**（见文首裁定 1：配料就是一道工序，无需单独建模）

**行业形态**：配料 = 按樘窗**配齐主料 + 配件**，逐件勾选，缺件显式。

**最小落码**（复用既有表，不建新表）：
- 配料项 = 该樘窗（`order_item_id`）的**主料**（布/纱，来自 `order_items` + 算料用料）
  + **配件**（来自特殊选项：`加铅块`→铅坠、`扣环`、`绑带`、`加花边`→花边 …）。
- 配件清单**不是新真值源**：它由**既有规则表**（`production_route_rules` 的 `trigger_kind='option'`）
  命中的工序 + `processing_operation_positions` 推导 —— 与工序实例同源。
- 动作：`POST /production/orders/{orderId}/positions/{orderItemId}/prepare`
  body `{items:[{key, qty, checked}], remark}` ⇒ 落**配料记录**（见 §4 数据模型），
  返回缺件清单（未勾选项）。
- **门禁**：配料不阻塞报工（行业里配料是并行动作），但**阻塞打包**（见 3.4）。

> ⚠️ **待你确认**：配料到底**是不是一道工序**（可计件）？行业实证里
> 「外帘配料」出现在工序链上（#4343 截图第 10 项）⇒ 倾向**是工序**。
> 若是工序，它就该走**既有报工链路**（自动计件），本节的「配料记录」只是**明细留痕**。

### 3.4 打包（③，语义落码 + 标签）

按 #4347 §二.3 的 **建议 (b)**（最少代码，且与真值源 §5 同口径）：

- **打包 = 报工 `外帘装袋`**（它本来就是「必须完成才可打包」的必完工序）⇒ **无需新动作**。
- **门禁**：`isMustFinishAllDone` 已由 `ProductionService` 实现 ⇒ 直接复用；
  未全绿时打包动作**明确拒绝**并指出**还差哪几道**（不静默）。
- **标签打印**：作为报工成功后的**可选后续动作**（截图里的 `☑打印标签`）——
  `POST /production/orders/{orderId}/pack-label`（生成标签数据，复用既有 `TaskCardPrint` 口径）。
  标签内容 = 单号 + 套号 + 部位 + 客户 + 收货信息 + 条码（**条码即扫码报工的入口**，真值源 §1 已定）。
- **留痕**：打包时间/操作人 = 该 `外帘装袋` 报工行本身（**不再新开一张表**）。

### 3.5 发货（④，下放到工人端）

按 #4347 §二.2 已冻结的口径落码：

- 扫码端新增「发货」动作 = **录入货运单号** → 订单 `shipped`。
- **守卫复用同一份**（含加工项订单必须有 completed 加工单）—— 变的只是**触发人**。
- 权限走**工人身份**（不是管理端 `processing:update`）。
- 承运商/物流方式**只读带出**（客户常用物流档案，真值源 §6），工人只填单号。
- **留痕**：复用既有 `order_logistics`（单号/承运商/时间/操作人）—— 不建新表。

### 3.6 工资结算（⑤，新增一层）—— ⛔ **本节已被裁定否决**（见文首裁定 2：不需要结算）

**这是「未来要给工人算工资」缺的那一层。** 最小模型：

- **结算单** `production_piecework_settlements`：`(tenant_id, period=YYYY-MM, worker_id)` 唯一。
  字段：`amount`（该期聚合金额，**快照**）、`qty`、`status`（`draft`/`settled`）、
  `settled_at`、`settled_by`、`remark`。
- **明细快照** `production_piecework_settlement_lines`：逐笔 `work_log_id` + 金额
  ⇒ 「逐笔可追溯」（真值源 §4）。
- **锁定语义**（**这是关键，不能省**）：`status='settled'` 后，该 `(period, worker)` 的报工
  **不得再被改动**；补报走**调整单**（新记录 + 留痕），**不回改历史** —— 与
  「快照冻结、不回算历史工资」同一条纪律。
- **可核对（本轮判据）**：报表必须能按 `人 / 期 / 单 / 部位 / 套` 下钻，且
  **下钻合计 === 总额**（真值源 §4 的下钻链：报工 → 工序实例 → 部位 → 套 → 加工单 → 订单）。
- **不加审批环节**（用户裁定）：`draft → settled` 由财务/管理**一步确认**即可，
  不引入多级审批状态机。

> ⚠️ **待你确认**：结算周期按**自然月**（`YYYY-MM`，与既有 `pieceworkSummary` 的 `period` 同口径）
> 是否够？行业里也有按**半月/项目**结算的。默认按自然月。

## 6. 落地顺序与并行边界

```
P2b（#4459）──► ① 工人端可见面 + 操作记录（读面接线，最小改动、收益最大）
                    │
                    ├─► ② 配料（动作 + 留痕）
                    ├─► ③ 打包语义 + 标签（复用必完工序门禁）
                    ├─► ④ 发货下放（复用同一守卫 + order_logistics）
                    └─► ⑤ 工资结算（新表 + 锁定 + 下钻）
```

**并行安全边界**：
- ① 改 `ProductionService.getOperations`（**P2b 不碰 `ProductionService`**）⇒ 可与 P2b 并行。
- ②③④ 改 `ProductionController` / `OrderService`（**P2b 碰 `ProductionController`**）⇒ **必须等 P2b 合并**。
- ⑤ 新增表 + `ProductionService`（结算面）⇒ 可与 ②③④ 并行，但与 ① 同文件 ⇒ **同包**。
