# 商家小程序上架 + 微信支付接入方案（多租户 SaaS）

> 版本 v1.2 ｜ 2026-08 ｜ 状态：方案定稿（未开发，实现项见附录 C TODO 清单）
> 关联文档：[multi-tenant-wechat.md](multi-tenant-wechat.md)（多租户小程序登录）、[commercialization-plan.md](../../product/commercialization-plan.md)（商业化）
> 本文档覆盖：商家如何把小布 agent 上架为自己的微信小程序（模式 A 半自动发布）+ 微信支付接入（平台服务商 + 特约商户直清）。
> v1.1 变更：升级发布改为「升级包 + 商家确认升级」模式（§3.3.1/§3.4）。v1.2 变更：实现项固化为附录 C TODO 清单。

## 1. 背景与目标

MIGAO 是面向布艺行业的多租户 AI 智能客服 SaaS。目标：**每个商家客户拥有自己的微信小程序**，用户在该小程序里与"这家商家的专属小布"对话、下单、支付；**钱直接进商家账户**，平台不碰资金，平台以 **SaaS 年费**为商业模式。

已确认的关键决策：

| 决策点 | 结论 |
|---|---|
| 上架模式（前期 <10 家） | **模式 A：半自动发布** — 平台按租户出包 + miniprogram-ci 远程传包，企业只做注册/认证/点审核发布 |
| 上架模式（规模化 >20 家） | 演进 **模式 B：微信第三方平台代开发** — 模板化一套代码，API 批量发布 |
| 支付模式 | **D2：平台申请微信支付服务商 + 企业为特约商户** — 资金直清到企业结算账户，**不走分账** |
| 平台收入 | **SaaS 年费**，不按交易抽成、不经手资金 |
| 配置边界 | 品牌/业务配置全部服务端化（`tenant_ai_configs`），出包只发生在前端功能迭代 |
| 升级发布模式 | **升级包 + 商家确认升级**：平台出升级包（变更日志/紧急度），商家在后台点「立即升级」后平台才上传（pull 模式） |

## 2. 总体架构

```
商家客户视角：
  用户 → 商家自己的微信小程序（独立 appid）→ 小布对话 → 下单 → 微信支付
                                                          │
资金流：用户付款 → 微信支付系统 → 直接结算到【商家对公账户】（平台不碰钱）

平台视角（共享一套 SWAS 部署）：
  admin-api(:8080) + ai-agent(:8000) + admin-web(:3001)  ← 多租户隔离（5 层）
  ├─ 租户支付配置表：mode/mchid/sub_mchid/appid/APIv3密钥/证书
  ├─ 统一支付服务（下单/查单/关单/退款/回调验签解密）
  ├─ 回调统一入口：按 out_trade_no/sub_mchid 定位租户
  └─ 对账：定时拉微信对账单 vs finance_transactions
```

## 3. 商家上架方案（模式 A：半自动发布）

### 3.1 角色分工

| 事项 | 商家 | 平台 |
|---|---|---|
| 注册小程序（企业主体） | ✅ mp.weixin.qq.com | 提供手册 |
| 微信认证（300 元/年） | ✅ | — |
| 选服务类目 / ICP 备案 / 合法域名 | ✅（域名填平台域名） | 提供类目建议、域名已备案 |
| 出包（appid + tenantId 注入） | — | ✅ 按租户出包，生成升级包（版本号+变更日志） |
| 上传密钥配置 | ✅ 在平台「企业设置 → 小程序发布」页自助配置（微信后台生成 → 粘贴保存） | ✅ 加密保存，驱动自动化上传 |
| 升级决策 | ✅ 在升级包列表点「立即升级」（或忽略；紧急版本平台催办） | 运营跟进滞后商家 |
| 上传新版本 | — | ✅ 商家确认后 miniprogram-ci 自动化上传 |
| 提交审核 / 发布 | ✅ 在微信后台点两个按钮（miniprogram-ci 无此能力） | 版本矩阵跟进 |

### 3.2 商家上架 SOP（8 步，总周期约 1-2 周）

1. **注册小程序账号**：mp.weixin.qq.com，企业邮箱注册，选「企业」主体，营业执照 + 对公账户验证（1-3 天）
2. **微信认证**：300 元/年（支付/类目资质必需，1-2 天）
3. **选服务类目**：按行业选「商家自营-家纺/窗帘」等，营业执照经营范围需匹配（审核时校验）
4. **ICP 备案**：小程序后台提交备案（2023.9 起强制，免费，1-2 周，可与 5-8 并行）
5. **配合法域名**：request 合法域名填平台 `api.migaozn.com` + `ai.migaozn.com`（共用平台域名，无需自购）
6. **配置上传密钥（自助）**：在平台管理后台「企业设置 → 小程序发布」页，按三步引导配置：① 微信后台「开发管理 → 开发设置 → 代码上传密钥」生成密钥（**仅显示一次，需立即复制**）；② 粘贴到平台保存（平台加密存储）；③ 建议在微信后台配置 IP 白名单（平台服务器 IP），仅白名单可上传
7. **导入代码包**：平台按该企业构建 `dist` + project.config.json（企业 appid）→ 微信开发者工具导入 → 上传（首次兜底；密钥配置后走自动化上传）
8. **提交审核 → 发布**：填功能页面/隐私协议 → 提交审核（1-7 天）→ 通过后发布；同步绑定微信支付（见 §4）

> 提示：接支付必须有电商类目 + 认证，**建议首版即带支付**，避免上线后加支付触发二次审核。
>
> 首次上架走完 8 步后，**后续迭代不再走 SOP**，商家在「企业设置 → 小程序发布」页的升级包列表里点「立即升级」即可（见 §3.3.1）。

### 3.3.1 「企业设置 → 小程序发布」页设计（商家自助，P4+P7）

商家管理后台「系统设置」下新增「小程序发布」页，作为上架与升级的自助入口。**核心交互：升级包列表 + 商家确认升级**——平台出包但不直接上传，商家在列表里选择是否升级（尊重商家对用户触点的控制权，避免旺季/促销期被动升级）。

**页面区块：**

1. **小程序绑定状态**：展示 `tenant_apps` 中的 appid、绑定状态、平台 API 域名（指导商家配置 request 合法域名）
2. **上传密钥配置**（三步引导 + 状态机）：
   - 状态：`未配置` → `已配置` → （重置后回到 `未配置`）
   - 引导文案含关键提示：密钥**仅生成时显示一次**；微信后台可设 **IP 白名单**（平台服务器 IP）；重置密钥后旧密钥立即失效
   - 保存后**不回显明文**（脱敏展示 `****` + 末 4 位），仅租户管理员可配置
3. **升级包列表**（页面主体）：
   - 每行一个升级包：版本号 / 发布日期 / **变更日志**（商家能看懂的"新增/修复/影响"，如"新增微信支付""修复订单卡片"）/ 紧急度标记（普通 / 紧急）
   - 商家视角状态机：`待升级` → `已上传(待审核)` → `审核中` → `已发布` → `已是最新`
   - 操作：**[立即升级]** [忽略]；已忽略的包折叠展示，可回头再升
   - **紧急版本**：红色标记 + 平台催办（消息/电话），必要时按服务条款强推
   - **套餐分层**：升级包按商家套餐裁剪（基础版/高级版可见的包不同），与 SaaS 年费分层联动
4. **试传体验版**：触发一次 preview 上传，返回体验版二维码，商家扫码验收后再决定升级
5. **能力边界说明**：平台自动化「上传」，**提交审核/发布仍须商家在微信后台操作**（miniprogram-ci 无此能力；第三方平台模式才可全自动）

**技术要点：**

- 数据模型：`mini_app_release_packages`（升级包：版本号/变更日志/紧急度/套餐可见性）+ `tenant_miniapp_releases`（商家 × 升级包 × 状态：待升级/已上传/审核中/已发布/忽略）
- 密钥加密存储（AES，对齐现有加密规范），不落日志、脱敏展示；重置后强制重新配置
- 发布执行器：管理后台服务端（Next.js route handler）或独立发布服务，调度「出包 → miniprogram-ci upload/preview」；支持 robot 1-30 区分环境、版本号自动递增、备注带平台版本号
- 权限：配置密钥/触发上传仅租户管理员；平台运营可跨租户查看升级漏斗（谁未升级）并催办
- 首次上架兜底：商家仍可用微信开发者工具手动导入上传（密钥未配置时引导此路径）

### 3.4 升级包与版本统一管理（商家确认升级 + 平台防失控）

- **升级包机制**：平台每次迭代产出升级包（版本号 + 变更日志 + 紧急度 + 套餐可见性），发布到各商家「小程序发布」页的升级包列表；**商家点「立即升级」后才触发上传**（pull 模式，非平台强推）
- **数据模型**：
  - `mini_app_release_packages`：平台侧升级包（版本号/变更日志/紧急度/套餐可见性/构建产物）
  - `tenant_miniapp_releases`：商家侧状态（tenant_id/appid/package_id/状态(待升级|已上传|审核中|已发布|忽略)/robot/上传时间/发布时间）
- **平台侧运营视图**：升级漏斗（谁已升级/谁待升级/谁忽略/滞后几个版本），未升级商家催办
- **版本兼容窗口（防失控底线）**：后端对旧包保持兼容（SSE 协议、卡片格式向后兼容），保证"暂不升级"的商家小程序不坏；滞后超过 N 个版本（建议 3 个）标红并升级为运营必跟项
- **微信机制约束**：小程序线上永远是"最新发布版"，商家不升级 = 整体停留旧版（无用户级灰度停留），因此升级决策只发生在商家侧，平台不提供"任意旧版本任选"
- 10 家规模：每次迭代约半天人力；>20 家切换模式 B

### 3.5 演进：模式 B（微信第三方平台代开发）

- 平台申请第三方平台资质 → 维护 1 套模板代码 → 企业授权后 API 批量提交审核/发布
- 租户差异走 **ext.json**（官方配置注入通道），模板代码零租户逻辑
- 支付层与模式 A 完全一致（见 §4），迁移零代码改动；P2 双通道为此预埋

## 4. 微信支付方案（D2：平台服务商 + 特约商户直清）

### 4.1 方案选择与资金流

| 模式 | 商户号 | 资金流 | 结论 |
|---|---|---|---|
| D1 企业直连商户号 | 企业自申请、自管凭证 | 直进企业账户 | 备选（企业要求自管凭证时） |
| **D2 平台服务商 + 特约商户** | 平台进件开通，商户号属企业 | **直清到企业结算账户** | **推荐** |
| D3 统收 + 分账 | 平台商户号 | 先进平台再分账 | ❌ 二清红线，排除 |

资金流：`用户付款 → 微信支付系统 → 按结算周期（T+1）直接结算到企业对公账户`。
平台角色仅"发起交易请求"（服务商凭证 + `sub_mchid`），**不经手、不沉淀资金**。

选择 D2 的理由：企业零支付操作（平台代进件）、平台只保管自己的凭证（安全面最小）、资金仍直清合规、可后续配置服务商服务费。

### 4.2 平台收入：SaaS 年费

- 平台不按交易抽成、不碰资金
- 商家承担：小程序认证 300 元/年 + 微信支付标准费率（约 0.6%，微信收取）
- 平台收取：SaaS 年费（订阅制），上架支持作为增值服务可选

### 4.3 技术架构

**4.3.1 租户支付配置表**（新增，或扩展 `tenant_apps`）

```sql
CREATE TABLE tenant_pay_configs (
    id VARCHAR(36) PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    mode VARCHAR(20) NOT NULL,              -- direct(直连) / partner(特约)
    mchid VARCHAR(32),                      -- 直连：企业商户号；特约：sub_mchid
    sub_mchid VARCHAR(32),                  -- partner 模式的 sub_mchid
    appid VARCHAR(64),                      -- 该租户小程序 appid
    api_v3_key VARCHAR(64),                 -- APIv3 密钥（加密存储）
    serial_no VARCHAR(64),                  -- 商户证书序列号
    private_key TEXT,                       -- 商户私钥（仅直连模式，加密存储）
    notify_url VARCHAR(255),                -- 回调地址（默认平台统一地址）
    status VARCHAR(20) DEFAULT 'active',
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    deleted INTEGER DEFAULT 0
);
```

**4.3.2 统一支付服务**（admin-api，Java）

- 微信支付 v3 客户端：RSA 签名/验签、APIv3 密钥 AES-GCM 解密、按租户加载配置
- 接口（仅内部调用，供 Agent/前端后端转发）：
  - `POST /api/pay/orders/{orderNo}/prepay` → 下单（partner: `/v3/pay/partner/transactions/jsapi`，传 `sp_appid/sub_appid/sub_mchid`）→ 返回 `prepay_id` + 小程序拉起参数
  - `GET /api/pay/orders/{orderNo}` → 查单（供轮询/对账）
  - `POST /api/pay/orders/{orderNo}/close` → 关单
  - `POST /api/pay/refunds` → 退款（partner refund API，带 `sub_mchid`）
  - `POST /api/pay/notify` → **统一回调入口**：验签 → AES-GCM 解密 → 按 `out_trade_no`（含租户前缀）定位租户/订单 → 更新订单 → 登记流水
- Mock 模式：租户未配置商户号时走 mock 支付（延续项目惯例，开发/演示/未上架阶段可用）

**4.3.3 回调 → 订单状态机衔接**

```
微信回调（SUCCESS）
  → 验签解密
  → orders.payment_status: unpaid → paid（启用现有死列，Order.java 补映射）
  → 订单 status: pending → confirmed（原子流转，复用现有 transitionStatusAtomic）
  → 扣库存 + 增销量（复用现有 confirmPayment 逻辑）
  → 登记 finance_transactions：type=income, payment_method=wechat, order_id
  → （可选）触发小布主动回执
```

- 现有「人工确认支付」保留为兜底（线下收款场景），回调驱动与人工驱动共用同一状态流转核心
- `payment_status` 与 `stock_deducted` 列已在 DB（008 迁移），Order.java 实体尚未映射 → 落地时补上

**4.3.4 对账**

- 定时任务拉取 v3 对账单（按 mchid/sub_mchid），与 `finance_transactions` 对平
- 异常流水（微信有/系统无）生成对账差异报表

### 4.4 Agent 侧改造（小布）

| 改造点 | 说明 |
|---|---|
| 新增 `payment` tool | 查待支付订单（order_query 复用）→ 调 admin-api prepay → 下发「支付卡片」；customer 角色专属 |
| 意图路由 | `intent_config.py` 加 `PAYMENT` 意图 + `rule_matcher` 关键词：支付/付款/去付款/缴费 |
| `customer_order` skill | 补支付流程 prompt：下单成功 → 引导支付；查询待支付订单 → 展示支付卡片 |
| SSE 卡片 | `_detect_card_type` 加 `payment` 类型；前端新增 OrderPayCard（含金额/订单号/「去支付」按钮） |
| 小程序端 | OrderPayCard 组件 + `Taro.requestPayment({timeStamp, nonceStr, package, signType:'RSA', paySign})`；支付结果回填对话（成功/失败/取消） |

### 4.5 权限与安全

- 支付卡片仅对**当前登录用户自己的待支付订单**可操作（防越权支付他人订单）
- 商户私钥/APIv3 密钥加密存储 + 脱敏日志
- 回调验签 fail-closed；幂等处理（重复回调不重复扣库存/登记）
- 支付金额以服务端订单 `total_amount` 为准，不回信前端传入

## 7. 风险与合规

| 风险 | 应对 |
|---|---|
| 二清合规 | D2 特约商户直清，平台不碰资金；合同明确平台非收款方 |
| 商户私钥泄露 | 默认 D2（平台无企业私钥）；D1 仅按需，密钥加密存储 |
| 小程序审核打回 | 类目与营业执照经营范围匹配；先用真实企业试走全流程固化 SOP |
| 隐私合规 | 隐私协议模板（收集手机号/收货信息声明）+ 用户隐私保护指引 |
| 版本失控（模式 A） | 商家确认升级（pull 模式）+ 后端版本兼容窗口（旧包不坏）+ 滞后 N 版标红运营跟进；>20 家切模式 B |
| 回调丢失 | 查单兜底（未收到回调时下单后轮询/定时查单补单） |
