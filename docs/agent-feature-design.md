# B 端 Agent 功能设计（能力地图）

> **这是什么**：B 端米宝「**该有哪些能力**」的设计总纲与判据来源。
> 与 [agent-write-boundary](agent-write-boundary.md) 的分工：那份管**写操作的边界（哪些能做）**，本份管**能力的设计（该做什么、做成什么形态）**。
>
> **这是活文档**：§七 的推进状态随落地更新。新增能力先在本表定位、按 §一 判据判定，再动手。

---

## 一、第一原则（一条，其余都是推论）

> **只做「用户用页面做不到、或明显更贵」的事。不满足这条的一律不做 —— 哪怕技术上做得到。**

推论：
- **做不到** → 跨域推理、对话外主动
- **明显更贵** → 批量、培训成本

这条原则是 2026-09 那次复盘的直接产物：#5247 之前米宝尝试覆盖「用户已经会用页面做」的操作（建品、建单），
结果是**可靠性与信任的双输** —— 详见 [agent-write-boundary](agent-write-boundary.md) §一 的判据讨论。

## 二、能力地图

| 族 | 能力 | 用户价值 | 依赖 | 状态 |
|---|---|---|---|---|
| **1** | 主动发现（对话外） | 没提问就拿到价值 | 规则引擎 + 推送面 + **跨域视图内核** | 未启动 |
| **2** | 批量更新（单领域对象） | N 次操作 → 1 次意图 | 批次资源 + 撤销 | 实现中（#5314） |
| **3** | 跨域具名查询（按需消费） | 页面结构上做不到 | **跨域视图内核（与族 1 共用）** | 未启动 |
| **4** | 页面上下文解释与教学 | 培训成本 → 0 | 前端上下文注入 | 未启动 |
| **5** | 页面协同（图片预填 / 草稿桥接） | 创建类体验补足 | 识别内核 + 同页填充 | 未启动 |
| **6** | 善后与补救 | 「卡住了怎么办」 | 依赖 1–5 | 未启动 |

**六族之外的两个独立模块**（不占族位）：
- **迁移助手** —— 拥有「批量**创建**」能力，独立设计见 **#5319**
- **写操作边界** —— 是**约束**不是能力，见 [agent-write-boundary](agent-write-boundary.md)

> 🔗 **族 1 与族 3 共用同一个「跨域视图内核」** —— 二者的真正分界是「**按需 vs 主动**」，不是视图类型。
> 详见 §三 族 3 末的形态图。
>
> 📣 **另有一个跨族关注点：提问引导（§九）** —— 它不属于任何一族，载体分布在族 1 / 族 4 / 对话层。

## 三、逐族设计

### 族 1 · 主动发现（对话外）

**为什么排第一**：这是**唯一在结构上页面不可能有的能力**（页面只能等人来点），也是「智能」二字的唯一定义性来源。且它是只读的 —— 风险远低于批量写。

**但推送的信任成本和写操作一样高**：推 3 条没用的，用户会永久关闭它。硬闸：

- **触发用规则，不用 LLM 自由发挥**。每条规则具名、可复算：低于成本价的订单 / 超 N 天未发货 / 库存告急 / 连续退货 / 改价幅度超阈值。
- **每条推送必须三件套**：① 可复算的判据（为什么推给你）② 影响面（几条 / 多少钱）③ **一键处置入口**。
- 🔴 **没有处置入口的推送不发** —— 只报问题不给出口，等于制造焦虑。
- **疲劳控制**：未处置的不重推；每次扫描有条数上限并按紧急度排序。
- **现成载体**：`briefing_query`（经营日报只读工具）+ `notification_manage` 的端点与权限码。

**验收判据**：给定数据快照，规则扫描必须产出**确定性**的推送集合 —— 不是「AI 觉得异常」。

**日报（`briefing_query`）是现成落点，但有一条铁约束**：**日报要窄，对话要宽** ——
日报只放「**当天有异常的**」，塞满跨域视图就从**简报**变成**报表**，用户不看了。
这与「没有处置入口的推送不发」是同一条约束的两种表现。

**日报还解决一个更根本的问题：「用户不知道该问什么」。** 按需查询要求用户先知道要问什么，
日报把这一步消解掉 —— 正是 §一 判据里那三类价值的第二类：「**用户不知道要做的**」。

### 族 2 · 批量更新（单领域对象）

设计 + 冻结契约见 **#5314**。要点：

- **两段确认**：先勾**集合**（`interact(multiSelect)`）→ 再逐条 **before → after** 预览
  > 不合成一段的理由：「选错对象」与「选错值」是**两类错误**，发现方式与代价不同。
- **撤销是硬前提**（[agent-write-boundary](agent-write-boundary.md) §五 裁定 1）：`old_value` 必须持久化，且**不得复用 `audit_logs`**（审计是 3s 有界 fail-open，丢行允许）。
- **`N > 50` 拒绝并提示分批**。
- **部分失败逐条报告，不做整体回滚**（回滚会掩盖真问题）。
- ❌ **不做通用批量** —— 具名批量的可逆性与预览形态是确定的。

### 族 3 · 跨域具名查询

🔴 **不做「通用 SQL Agent」**。危险（越权 / 扫库）、不可验收（同一问题两次答案不同）、无法归因。

改做**具名跨域视图** —— 一个高频问题固化成**一个工具**：

| 视图 | 组合 |
|---|---|
| 客户画像 | 订单 + 售后 + 标签 + 复购 |
| 商品健康度 | 销量 + 库存 + 退货率 + 毛利 |
| 订单风险 | 逾期 + 欠款 + 客户信用 |

**判据：加一个跨域问题 = 加一个具名工具**，不是让模型自由发挥。
代价是**覆盖速度慢**（每个新问题都要开发），换来的是**可验收、不越权**。

#### 与族 1 的关系（2026-09-24 修正）：同一内核，两种消费形态

族 3 与族 1 **不应并列** —— 二者的真正分界是「**按需 vs 主动**」，
而**同一份跨域数据两种形态都要**：

```
        ┌──────────────────────────────┐
        │  跨域视图（服务端只读内核）      │
        └──────┬───────────────┬───────┘
               │               │
      主动消费（族 1）      按需消费（族 3）
      日报 / 推送           对话查询 / 下钻
      窄：只放今天异常的    宽：什么都能问
```

**日报给「发现」**（今天哪个商品不健康），**对话给「下钻」**（为什么这个商品退货率高）。
两入口共用内核 ⇒ 保证口径一致 —— 与 §四 图片「一个内核、两个入口」是**同一个设计模式**。

**逐个视图的主要消费形态**（分界依据：是否周期性）：

| 视图 | 主要形态 | 理由 |
|---|---|---|
| 商品健康度 | **主动** | 周期性、广覆盖 —— 每天看一次，不需要按需问 |
| 订单风险 | **主动** | 本来就是「该提醒你」的形态（属族 1） |
| 客户画像 | **按需** | 「针对某个对象、在特定时刻」的查询，**不周期** |

### 族 4 · 页面上下文解释与教学

B 端最贵的是**培训成本**，这是唯一能把它降到 0 的形态。

- **页面上下文注入**：用户在哪个页面 → 只回答那一页的事（前端注入 route + 当前实体 id）。
- 🔴 **答案必须引真值源**，不是 LLM 编的解释。
  例：「这单为什么是这个价」要拆到算料口径 + 计价规则，引 `docs/curtain-fabric-quote-rules.md`。
- 两个风险：上下文注入是**新的越权面**（须按角色裁剪）；**猜错页面比不猜更烦** ⇒ 必须有「不确定就问」的降级路径。

### 族 5 · 页面协同（图片预填 / 草稿桥接）

**核心机制**：Agent 把结构化结果**推给当前页面表单**（同页填充），而不是在聊天里渲染表单。

三条落点前提（本族的共同基础）：
1. **米宝是浮动面板** —— `frontend/admin-web/src/components/ai-assistant/FloatingAssistant.tsx` 挂载 `MibaoChatPanel`。
   ⇒ 用户可以在目标页面上直接跟米宝说话，**表单就在屏幕上，不需要跳转**。
2. **页面表单已支持初始值** —— `frontend/admin-web/src/components/products/ProductForm.tsx` 的 `ProductFormProps` 已有 `initialData`。
3. **同页填充零 PII 落盘** —— 走内存/事件通道，不进 URL、不进日志、不进浏览器历史。
   > 反面是裸 URL query（`?phone=…`）：会进 nginx access log / Referer。**已为这件事吃过一次账**（form 卡预填手机号进 `final_text`）。

**跨页面场景**才需要「服务端草稿 + UUID」（`/orders/new?draft=<uuid>`），且**草稿必须从会话状态升格为可寻址的领域实体**。

**铁律**：两个入口都**不落库** —— **提交永远是人的动作**。这是「不把 Agent 当表单」的准确含义：不是不许它填，是不许它替人提交。

写失败 / 卡住时的原因解释与补救路径。依赖前面几族，放最后。

## 四、专项 · 图片单次创建（多入口能力）

### 归属判定：**主要做到页面，Agent 只补页面做不到的三种情况**

判据：「图 → 字段」**不是「模糊 → 明确的收敛」，是单向变换** —— 不需要对话、不需要多轮推理。
**给它套一层 Agent 外壳，是把确定性管道放进不确定性外壳。**

| 理由 | 说明 |
|---|---|
| **可验收性断层** | 页面入口的**管道是确定性的**（固定夹具钉住 vision 输出，断言「字段 → 表单」）；Agent 路径只能写弱断言 |
| **成本** | 页面 = 1 次 vision 调用；Agent = 对话上下文 + vision + 可能多轮 |
| **动线** | 用户要建品，第一动作是打开建品页，不是打开米宝 |

> ⚠️ **不要让 Agent 成为唯一入口** —— 那会把纯技术能力变成「必须有 LLM 才能用」，既贵又不稳。

### Agent 必须保留的三种（页面做不了）

| 情况 | 例子 |
|---|---|
| **歧义消解** | 识别出「雾霾蓝」但目录里没有 → Agent 能**解释为什么这几个最接近**并商量 |
| **领域解读** | 这是什么面料 / 工艺 / 适合什么场景 —— 页面给不了解读 |
| **跨实体追问** | 「照这张图建个商品」但分类、售价未定 → 需多轮澄清才能收敛 |

这三条**恰好是识别准确率之外那 10% 的字段**，也是决定这个功能好不好用的部分。

### 最终形态：一个内核，两个入口

```
        ┌──────────────────────────────┐
        │  识别内核（服务端）            │
        │  vision + 字段映射 + 目录消歧  │
        └───────┬──────────────┬───────┘
                │              │
     页面入口（快通道）     Agent 入口（深通道）
     建品/建单页按钮        米宝（浮动面板，同页）
     图 → 字段 → 填表       图 → 识别 + 解读/消歧/追问
     用户复核 → 提交        → 推给页面 form
```

- **两入口共用内核** —— 保证「同一张图，两个入口给同一组字段」
- **逐字段标注 `[图片识别]`** —— 现有约定（`backend/ai-agent-service/app/graph/skills/product_skill.py`），**务必保留**：它是用户判断「该信哪一格」的唯一依据
- **不确定的字段宁可不填**（留空 + 提示）—— **错填比留空贵得多**

### 落点：**商品与订单两个模块**（缺一不可）

本能力**必须同时落到 `商品` 与 `订单` 两个模块** —— 它们是两个不同的识别 target：

| target | 图片常见形态 | 识别目标字段 |
|---|---|---|
| **商品** | 色卡 / 布料实拍 / 供应商图 | 名称 / 颜色 / 材质 / 工艺 / 门幅 / 售价 |
| **订单** | **手写单 / 微信聊天截图 / 旧系统单据** | 客户名 / 电话 / 商品明细 / 数量 / **帘宽 / 帘高**（推导链的原始输入，issue #5349） |

**共用同一个内核与入口模式**（`targetType` 区分），但**字段 schema 与消歧规则不同** ——
不要做成「一套字段两个页面填」。

⚠️ **订单侧风险更高**（客户信息错 ⇒ 货发错人）⇒ 订单侧的 `[图片识别]` 标注与
「**不确定的宁可不填**」要比商品侧**更严格**。

### 现状偏差（本设计要修的）

`backend/ai-agent-service/app/graph/skills/product_skill.py` 的现有约定是「图片识别后第一步 → `interact(component=form)` 预填识别字段」。
**方向对（复核型 form 是对的），但落点错**：建品 10+ 字段、还有 `SkuMatrix` 这类矩阵交互，**聊天卡片放不下**。

且图片管线目前只在 `backend/ai-agent-service/app/api/chat.py` 的**对话路径**上（多模态 metadata → URL 校验 → CDN 重写）
⇒ **页面入口需要把这段抽成可复用服务**，这是本能力真正的工程量所在。

## 五、专项 · 迁移助手

**拥有「批量创建 / 导入」能力**，独立设计见 **#5319**。此处只记与其他族的关系：

- **与族 2 的分工**：族 2 是「批量**更新**已有对象」；迁移是「批量**创建**」。**两者不共用判据** —— 迁移的 80% 工作量在数据质量（映射 / 试运行 / 逐行报告 / 幂等），不在批量执行。
- **Agent 在迁移里的角色是「错误分类与批量修正助手」，不是执行器**（详见 #5319）。

## 六、负面清单（明确不做）

- ❌ 让 Agent 当表单（多字段逐步收集）
- ❌ 通用 SQL / 自由 join
- ❌ 不可逆写（见 [agent-write-boundary](agent-write-boundary.md) C 档）
- ❌ **无处置入口的推送**
- ❌ **无撤销的批量**
- ❌ 基于猜测页面上下文的强行解释
- ❌ 通用批量 / 自由字段批量
- ❌ 让 Agent 成为识别等确定性能力的**唯一入口**
- ❌ 通用 ETL 平台（见 #5319）

## 九、提问引导（跨族关注点）

> **不是第七族** —— 它的载体分布在**族 1（日报）**、**族 4（页面上下文）**与**对话层**，所以是**跨族关注点**。

### 问题：「B 端用户不知道如何提问」其实是三个不同的问题

把它们混成「给几个示例问题」，就是现状 —— 那**只解决了第 1 类的一半**。

| 类型 | 用户状态 | 该谁治 |
|---|---|---|
| **1 · 不知道系统能做什么** | 能力盲区 | 空白态 + 上下文引导 |
| **2 · 不知道怎么表述** | 知道自己要什么，但说不出来 | **对话层（本关注点起点）** |
| **3 · 不知道自己该关心什么** | 不知道自己有个问题 | **族 1** 主动发现（#5322） |

### 现状盘点（三处载体，都只做了半套）

| 载体 | 现状 | 问题 |
|---|---|---|
| `frontend/admin-web/src/components/chat/WelcomePanel.tsx` | 5 条**静态**示例 | 不管页面 / 角色 / 历史，**永远同样几条** |
| `backend/ai-agent-service/app/suggestions/follow_up.py` | 按 `intent_type × stage` 出预设建议 | **反应式** —— 已问一轮才建议；**首轮词不达意时毫无帮助** |
| `backend/ai-agent-service/app/agents/agents/mibao.py` 问候语 | 「我可以帮您查数据、做分析：订单与物流…」 | **能力罗列** —— 读完还是不知道问什么 |
| `backend/ai-agent-service/app/suggestions/preference_tracker.py` | 已记录 click / top intents | **数据在，但没用于引导** |

### 关键机制：引导必须是「能力事实的机械投影」

本仓**已经跑通过这个模式** —— `backend/ai-agent-service/tests/test_capability_index_prompt.py`（能力索引，issue #4125）的判据：

> 索引内容 = `SkillConfig.tool_names` × 注册表 `read_only` 事实的**机械投影** —— **不写死任何 skill 名/工具名**

且它立了边界守卫：**索引是给模型看的，不是给用户说的**。

⇒ **面向用户的引导是这套投影的「第二条腿」：同源，但渲染成用户语言。**

```
        能力事实（SkillConfig.tool_names × read_only）
                      │
              ┌───────┴────────┐
           给模型看          给用户看
           能力索引(#4125)    提问引导
           域 → 工具名        用户语言的问题
```

**两条投影同源 ⇒ 不会漂移** —— 这是本仓治漂移的标准解法。
⇒ 本关注点是**复用已跑通的模式，不是新发明**。

**判据**：每条引导必须能**追溯到一条真实能力** ——
同 `test_l0_reachability_guards` 守「描述点名的工具必须真实注册」的思路。

🔴 **引导了却做不到，比不引导更伤。**

### 三类分别怎么治

#### 类型 1 · 不知道能做什么
- **不要罗列能力，要按动线给问题**。`frontend/admin-web/src/config/menu.ts`（7 组 / 21 项）就是用户动线的真值源。
- **上下文相关**：在商品页给「这个商品最近退货率怎么样」，在订单页给「这单为什么卡住了」。
  ⇒ 这是**族 4 的一个应用，但用途是引导而不是回答**。

#### 类型 2 · 不知道怎么表述 —— **关注点起点，ROI 最高**
- **模糊输入也要接住**：用户说「我想看看最近的情况」→ **不该回「请问您想查什么」**，
  而应该给出**理解后的猜测 + 可点选项**：
  > 「我理解你想看经营概况，是这个吗？还是 ① 订单异常 ② 库存 ③ 客户」
- 🔴 **给可点击的猜测，不给空白输入框** —— 把「提不出问题」变成「**点一下就行**」。
- **术语桥反着用**：`docs/wiki/agent-design-standard.md` 说 Skill Prompt 放「术语映射」——那是用于**理解**用户；
  反过来，知道用户的口语词就能生成**他看得懂**的引导。
- **落地**（#5329）：投影在 `backend/ai-agent-service/app/suggestions/vague_guess.py`
  （「选哪些能力」与 `_capability_index` 同一份事实；「怎么说」取自工具 `description` 的
  `【触发】` 用户原话），接线在 `backend/ai-agent-service/app/graph/nodes.py`
  （低置信模糊轮 → `direct_reply` 直发 `interact` choice 卡），判据在
  `backend/ai-agent-service/tests/test_vague_guess.py`（每条断言带注入式红证）。
  **未实装（照实登记）**：触发面限「米宝 × 低置信 × 本会话第一次需要澄清」（其后交还既有澄清护栏升级链）；
  引导只覆盖**查得出来**的方向；`settings` / `knowledge` 两域的触发词不落在 L1 关键词表上 ⇒ 不含在引导里。

#### 类型 3 · 不知道自己该关心什么
- 已立项 **#5322**（族 1 包 1）。
- **缝合**：日报每条异常应带**追问入口**。
  > **日报是「替用户提问」，点进去是「用户学会了怎么问」。**
  这是**零新增文案**的引导 —— 日报条目本身就是最好的引导素材。

### 反模式（明确不做）

- ❌ **罗列能力**（「我可以查订单、商品、客户、库存…」）
- ❌ **静态示例**（不管页面 / 角色 / 历史）
- ❌ **开放式反问**（「请问您想了解什么？」）—— 把认知负担**原样还给用户**
- ❌ **推荐答不出来的问题**（违反上面的机械投影判据）
- ❌ 拿系统能力名当引导（「跨域查询」「批量操作」）
