# B 端 Agent 功能设计（能力地图）

> **这是什么**：B 端米宝「**该有哪些能力**」的设计总纲与判据来源。
> 与 [agent-write-boundary](agent-write-boundary.md) 的分工：那份管**写操作的边界（哪些能做）**，本份管**能力的设计（该做什么、做成什么形态）**。
>
> **这是活文档**：§七 的推进状态随落地更新。新增能力先在本表定位、按 §一 判据判定，再动手。

---

## 一、第一原则（一条，其余都是推论）

> **只做「用户用页面做不到、或明显更贵」的事。不满足这条的一律不做 —— 哪怕技术上做得到。**

推论：
- **做不到** → 跨域推理、对话外主动
- **明显更贵** → 批量、培训成本

这条原则是 2026-09 那次复盘的直接产物：#5247 之前米宝尝试覆盖「用户已经会用页面做」的操作（建品、建单），
结果是**可靠性与信任的双输** —— 详见 [agent-write-boundary](agent-write-boundary.md) §一 的判据讨论。

## 二、能力地图

| 族 | 能力 | 用户价值 | 依赖 | 状态 |
|---|---|---|---|---|
| **1** | 主动发现（对话外） | 没提问就拿到价值 | 规则引擎 + 推送面 | 未启动 |
| **2** | 批量更新（单领域对象） | N 次操作 → 1 次意图 | 批次资源 + 撤销 | 实现中（#5314） |
| **3** | 跨域具名查询 | 页面结构上做不到 | 具名视图工具 | 未启动 |
| **4** | 页面上下文解释与教学 | 培训成本 → 0 | 前端上下文注入 | 未启动 |
| **5** | 页面协同（图片预填 / 草稿桥接） | 创建类体验补足 | 识别内核 + 同页填充 | 未启动 |

**六族之外的两个独立模块**（不占族位）：
- **迁移助手** —— 拥有「批量**创建**」能力，独立设计见 **#5319**
- **写操作边界** —— 是**约束**不是能力，见 [agent-write-boundary](agent-write-boundary.md)

## 三、逐族设计

### 族 1 · 主动发现（对话外）

**为什么排第一**：这是**唯一在结构上页面不可能有的能力**（页面只能等人来点），也是「智能」二字的唯一定义性来源。且它是只读的 —— 风险远低于批量写。

**但推送的信任成本和写操作一样高**：推 3 条没用的，用户会永久关闭它。硬闸：

- **触发用规则，不用 LLM 自由发挥**。每条规则具名、可复算：低于成本价的订单 / 超 N 天未发货 / 库存告急 / 连续退货 / 改价幅度超阈值。
- **每条推送必须三件套**：① 可复算的判据（为什么推给你）② 影响面（几条 / 多少钱）③ **一键处置入口**。
- 🔴 **没有处置入口的推送不发** —— 只报问题不给出口，等于制造焦虑。
- **疲劳控制**：未处置的不重推；每次扫描有条数上限并按紧急度排序。
- **现成载体**：`briefing_query`（经营日报只读工具）+ `notification_manage` 的端点与权限码。

**验收判据**：给定数据快照，规则扫描必须产出**确定性**的推送集合 —— 不是「AI 觉得异常」。

### 族 2 · 批量更新（单领域对象）

设计 + 冻结契约见 **#5314**。要点：

- **两段确认**：先勾**集合**（`interact(multiSelect)`）→ 再逐条 **before → after** 预览
  > 不合成一段的理由：「选错对象」与「选错值」是**两类错误**，发现方式与代价不同。
- **撤销是硬前提**（[agent-write-boundary](agent-write-boundary.md) §五 裁定 1）：`old_value` 必须持久化，且**不得复用 `audit_logs`**（审计是 3s 有界 fail-open，丢行允许）。
- **`N > 50` 拒绝并提示分批**。
- **部分失败逐条报告，不做整体回滚**（回滚会掩盖真问题）。
- ❌ **不做通用批量** —— 具名批量的可逆性与预览形态是确定的。

### 族 3 · 跨域具名查询

🔴 **不做「通用 SQL Agent」**。危险（越权 / 扫库）、不可验收（同一问题两次答案不同）、无法归因。

改做**具名跨域视图** —— 一个高频问题固化成**一个工具**：

| 视图 | 组合 |
|---|---|
| 客户画像 | 订单 + 售后 + 标签 + 复购 |
| 商品健康度 | 销量 + 库存 + 退货率 + 毛利 |
| 订单风险 | 逾期 + 欠款 + 客户信用 |

**判据：加一个跨域问题 = 加一个具名工具**，不是让模型自由发挥。
代价是**覆盖速度慢**（每个新问题都要开发），换来的是**可验收、不越权**。

### 族 4 · 页面上下文解释与教学

B 端最贵的是**培训成本**，这是唯一能把它降到 0 的形态。

- **页面上下文注入**：用户在哪个页面 → 只回答那一页的事（前端注入 route + 当前实体 id）。
- 🔴 **答案必须引真值源**，不是 LLM 编的解释。
  例：「这单为什么是这个价」要拆到算料口径 + 计价规则，引 `docs/curtain-fabric-quote-rules.md`。
- 两个风险：上下文注入是**新的越权面**（须按角色裁剪）；**猜错页面比不猜更烦** ⇒ 必须有「不确定就问」的降级路径。

### 族 5 · 页面协同（图片预填 / 草稿桥接）

**核心机制**：Agent 把结构化结果**推给当前页面表单**（同页填充），而不是在聊天里渲染表单。

三条落点前提（本族的共同基础）：
1. **米宝是浮动面板** —— `frontend/admin-web/src/components/ai-assistant/FloatingAssistant.tsx` 挂载 `MibaoChatPanel`。
   ⇒ 用户可以在目标页面上直接跟米宝说话，**表单就在屏幕上，不需要跳转**。
2. **页面表单已支持初始值** —— `frontend/admin-web/src/components/products/ProductForm.tsx` 的 `ProductFormProps` 已有 `initialData`。
3. **同页填充零 PII 落盘** —— 走内存/事件通道，不进 URL、不进日志、不进浏览器历史。
   > 反面是裸 URL query（`?phone=…`）：会进 nginx access log / Referer。**已为这件事吃过一次账**（form 卡预填手机号进 `final_text`）。

**跨页面场景**才需要「服务端草稿 + UUID」（`/orders/new?draft=<uuid>`），且**草稿必须从会话状态升格为可寻址的领域实体**。

**铁律**：两个入口都**不落库** —— **提交永远是人的动作**。这是「不把 Agent 当表单」的准确含义：不是不许它填，是不许它替人提交。

## 四、专项 · 图片单次创建（多入口能力）

### 归属判定：**主要做到页面，Agent 只补页面做不到的三种情况**

判据：「图 → 字段」**不是「模糊 → 明确的收敛」，是单向变换** —— 不需要对话、不需要多轮推理。
**给它套一层 Agent 外壳，是把确定性管道放进不确定性外壳。**

| 理由 | 说明 |
|---|---|
| **可验收性断层** | 页面入口的**管道是确定性的**（固定夹具钉住 vision 输出，断言「字段 → 表单」）；Agent 路径只能写弱断言 |
| **成本** | 页面 = 1 次 vision 调用；Agent = 对话上下文 + vision + 可能多轮 |
| **动线** | 用户要建品，第一动作是打开建品页，不是打开米宝 |

> ⚠️ **不要让 Agent 成为唯一入口** —— 那会把纯技术能力变成「必须有 LLM 才能用」，既贵又不稳。

### Agent 必须保留的三种（页面做不了）

| 情况 | 例子 |
|---|---|
| **歧义消解** | 识别出「雾霾蓝」但目录里没有 → Agent 能**解释为什么这几个最接近**并商量 |
| **领域解读** | 这是什么面料 / 工艺 / 适合什么场景 —— 页面给不了解读 |
| **跨实体追问** | 「照这张图建个商品」但分类、售价未定 → 需多轮澄清才能收敛 |

这三条**恰好是识别准确率之外那 10% 的字段**，也是决定这个功能好不好用的部分。

### 最终形态：一个内核，两个入口

```
        ┌──────────────────────────────┐
        │  识别内核（服务端）            │
        │  vision + 字段映射 + 目录消歧  │
        └───────┬──────────────┬───────┘
                │              │
     页面入口（快通道）     Agent 入口（深通道）
     建品/建单页按钮        米宝（浮动面板，同页）
     图 → 字段 → 填表       图 → 识别 + 解读/消歧/追问
     用户复核 → 提交        → 推给页面 form
```

- **两入口共用内核** —— 保证「同一张图，两个入口给同一组字段」
- **逐字段标注 `[图片识别]`** —— 现有约定（`backend/ai-agent-service/app/graph/skills/product_skill.py`），**务必保留**：它是用户判断「该信哪一格」的唯一依据
- **不确定的字段宁可不填**（留空 + 提示）—— **错填比留空贵得多**

### 现状偏差（本设计要修的）

`backend/ai-agent-service/app/graph/skills/product_skill.py` 的现有约定是「图片识别后第一步 → `interact(component=form)` 预填识别字段」。
**方向对（复核型 form 是对的），但落点错**：建品 10+ 字段、还有 `SkuMatrix` 这类矩阵交互，**聊天卡片放不下**。

且图片管线目前只在 `backend/ai-agent-service/app/api/chat.py` 的**对话路径**上（多模态 metadata → URL 校验 → CDN 重写）
⇒ **页面入口需要把这段抽成可复用服务**，这是本能力真正的工程量所在。

## 五、专项 · 迁移助手

**拥有「批量创建 / 导入」能力**，独立设计见 **#5319**。此处只记与其他族的关系：

- **与族 2 的分工**：族 2 是「批量**更新**已有对象」；迁移是「批量**创建**」。**两者不共用判据** —— 迁移的 80% 工作量在数据质量（映射 / 试运行 / 逐行报告 / 幂等），不在批量执行。
- **Agent 在迁移里的角色是「错误分类与批量修正助手」，不是执行器**（详见 #5319）。

## 六、负面清单（明确不做）

- ❌ 让 Agent 当表单（多字段逐步收集）
- ❌ 通用 SQL / 自由 join
- ❌ 不可逆写（见 [agent-write-boundary](agent-write-boundary.md) C 档）
- ❌ **无处置入口的推送**
- ❌ **无撤销的批量**
- ❌ 基于猜测页面上下文的强行解释
- ❌ 通用批量 / 自由字段批量
- ❌ 让 Agent 成为识别等确定性能力的**唯一入口**
- ❌ 通用 ETL 平台（见 #5319）
