## R1 · 存量库的 RBAC 差集：哪些租户 × 哪些岗位缺那 11 个码

**目的**：回答「**存量租户的 `role_permissions` 到底缺了什么**」。迁移链上 `V43` / `V111` / `V124` / `V125`
四条引入新码时**都没给 `admin` 授码** ⇒ 跑过 `V29` 的老租户里，管理员岗位的授权是「该租户历史跑过的迁移之并集」，
比新租户少 11 个码。本查询把这件事**从推断变成读数**：逐行点名「哪个租户 × 哪个岗位 × 缺哪个码」。

**出处锚**（**注意：不是**「文件头给的现成 SQL」，见下）：

- 迁移与设计：`backend/admin-api/src/main/resources/db/migration/V136__converge_builtin_role_permissions.sql`
  的**终态对账 `DO` 块**（`missing_links` 那段对账查询 = `tenants` × `roles` × `permissions` × `role_permissions`
  四表 + 一段 11 对 `VALUES` 清单）+ 其**文件头**的「现取差集」节
  —— 该文件随 PR **#5730** 落地，**并已在本包落地前合并进 `main`**（合并提交 `1ef347dac`）⇒ 本包引的就是 **`main` 上的路径**；
- 差集的**声明面**推演读数（非真库）：`PR #5730`（**已合并**）的 body §2.1 表（`admin` 清单 31 / 链累计 20 / **缺 11**）；
- 未取证的重启条件原文：`docs/design/rbac-single-source.md` 的 §6「未取证与存疑」条目 1
  （逐字：「接上真库后复算『每个租户每个角色的 `role_permissions`』」）与条目 3（岗位权限页勾选数，见文末「配套现场核对」）。

**🔴 出处诚实说明**：`V136` 的文件头**没有**给出「按租户 × 岗位列缺码明细」的现成只读 SQL
—— 它给的是 ① 一段 **python 复算命令**（推演「清单声明 vs 迁移链累计」，**不连库**）
② 迁移体 `DO` 块里的 **fail-closed 对账查询**。下面两块的**全部谓词与 11 对 `(岗位, 码)` 清单**
逐字取自那个 `DO` 块；**唯一的改动**是：把 `SELECT COUNT(*) INTO …` 改成**明细列 + 排序 + `LIMIT`**（`LIMIT` 不改变结论，见安全说明）。

```sql
-- R1-a 射程：本库有几个租户「已有权限目录」（= V136 的射程口径，同 V124）
--       逐字取自 V136 终态对账块里的 scoped_tenants 查询
SELECT COUNT(*) AS scoped_tenants
  FROM tenants t
 WHERE EXISTS (SELECT 1 FROM permissions p WHERE p.tenant_id = t.id);
```

```sql
-- R1-b 明细：哪些「租户 × 岗位」缺那 11 个码里的哪一个
--       谓词与 VALUES 清单逐字取自 V136 终态对账块的 missing_links 查询（只改成明细返回）
SELECT t.id           AS tenant_id,
       t.name         AS tenant_name,
       r.code         AS role_code,
       want.perm_code AS missing_permission_code
  FROM tenants t
  JOIN roles r       ON r.tenant_id = t.id AND r.deleted = 0
  JOIN permissions p ON p.tenant_id = t.id
  JOIN (VALUES
        ('admin', 'after_sales:view'),
        ('admin', 'agent:session:manage'),
        ('admin', 'customer:create'),
        ('admin', 'finance:create'),
        ('admin', 'inbound:create'),
        ('admin', 'inbound:view'),
        ('admin', 'knowledge:view'),
        ('admin', 'order:create'),
        ('admin', 'order:update'),
        ('admin', 'processing:update'),
        ('admin', 'processing:view')
      ) AS want(role_code, perm_code)
    ON want.role_code = r.code AND want.perm_code = p.code
 WHERE NOT EXISTS (
        SELECT 1 FROM role_permissions rp
         WHERE rp.role_id = r.id AND rp.permission_id = p.id AND rp.deleted = 0
       )
 ORDER BY t.id, r.code, want.perm_code
 LIMIT 500;
```

**预期形状（判读口径）**：

- **事前**（`V136` 还没跑）：返回**若干行** ⇒ 每行 = 一个**确定缺失**的 `(租户, 岗位, 码)`。行数 = 0 ⇒ 该库**本来就没有**这个差集（要么是新库，要么已被补齐）。
- **事后**（`V136` 跑过）：**必须 0 行**（这正是 `V136` 的停止条件：缺任何一对就 `RAISE EXCEPTION` 并回滚整条迁移）。
- **`scoped_tenants = 0`** ⇒ 该库**没有任何租户持有权限目录** ⇒ 按 `V136` 的射程口径**本迁移是空操作**，R1-b 必然 0 行；这**不等于**「差集已补齐」，只能说「不在射程内」。
- **不要**把 R1-b 的 0 行读成「所有租户都没问题」：它只覆盖**已有该权限目录行**的租户 ——
  某个租户若连 `after_sales:view` 这条**目录行**都没有，那一对**根本不在射程**（目录由
  `PermissionService::ensureFullPermissionCatalog` 懒补种，`V136` **不建目录行**）。
- **岗位只点了 `admin`**：`V136` 的差集只覆盖五个原有内置岗位，且现取只有 `admin` 有差集
  ⇒ 若 R1-b 里出现**别的** `role_code`，那不是本包预期形态 ⇒ 先回报，不要据此改任何代码。

**安全说明**：只读（两段 `SELECT`，无写 / 无 DDL / 无临时表 / 无 `SET` / 无 `VACUUM`）。
十亿级表上 `role_permissions` 的 `NOT EXISTS` 走 `(role_id, permission_id)` 唯一索引
（`uq_role_permissions`，`V136` 自己依赖它做 `ON CONFLICT`）⇒ 单对判定的代价是索引探针；
但 `tenants × roles × permissions` 是**逐租户笛卡尔式**扫描 ⇒ 租户多时**可能慢**。
`LIMIT 500` **不改变结论**：它只截断**输出**，不改变「是否存在缺失」这一判断
（若你担心被截断，把 `LIMIT` 调大或去掉 —— 该改动不改变本查询的只读性质）。

**配套现场核对**（不开 SQL，`docs/design/rbac-single-source.md` §6 条目 3 的重启条件）：
在**一个存量租户**上打开「岗位权限页」，看**管理员岗位的勾选数**是否等于
**该库当前权限目录里的码数**（不要拿写死的数字对：目录会随迁移增长）。
勾选数少于目录码数 ⇒ 回填缺码（与该租户在 R1-b 里出现的行数一致）。

**读数回填到**：RBAC 跟踪单 **#5699**（P5 阶段）的评论；附上 R1-a 的 `scoped_tenants` 与 R1-b 的行数。

## R2 · `production:execute` 快照回填的命中面（行数 + 岗位分布 + 越界）

**目的**：`V138` 改挂写码 `production:execute` 后，**有 `users.permissions` 快照**的账号
在 `RoleService::getUserPermissions` 里会**提前返回快照** ⇒ 只补岗位授权**不够**，还要做**等价回填**。
本查询回答三件事：① **命中多少行**（受影响的账号数）；② **哪些岗位**（分布）；
③ 回填后**有没有越界**（出现「有新码、无旧码」= 放宽了不该放宽的人）。

**出处锚**：`backend/admin-api/src/main/resources/db/migration/V138__add_production_execute_permission.sql`
的**文件头**「只读的事前 / 事后核对 SQL」节（与 R1 同：随 PR #5730 落地，**该 PR 已合并** ⇒ 路径现在就在 `main` 上）。
四块 SQL **逐字**取自该节（未改一个谓词）。

```sql
-- R2-a 事前：受影响的账号数（快照含旧码 order:list、不含新码 production:execute）
SELECT COUNT(*) AS affected_accounts FROM users
 WHERE permissions LIKE '%"order:list"%' AND permissions NOT LIKE '%"production:execute"%';
```

```sql
-- R2-b 事前：按岗位分布（受影响面到底是哪些岗位）
SELECT role, COUNT(*) AS accounts FROM users
 WHERE permissions LIKE '%"order:list"%' AND permissions NOT LIKE '%"production:execute"%'
 GROUP BY role ORDER BY 2 DESC;
```

```sql
-- R2-c 事后：持新码的行数（应当逐值等于事前——每行只是多了一个码，行数不变）
SELECT COUNT(*) AS with_new_code FROM users WHERE permissions LIKE '%"production:execute"%';
```

```sql
-- R2-d 事后：越界断言，必须 = 0（「有新码、无旧码」= 给今天本来就过不去的人开了门）
SELECT COUNT(*) AS widened FROM users
 WHERE permissions LIKE '%"production:execute"%' AND permissions NOT LIKE '%"order:list"%';
```

**预期形状（判读口径）**：

- **等价回填的定义 = `R2-c` 的计数与 `R2-a` 的计数逐值相等**（不是「差不多」；回填只做 `+1 个码`，不新增/删除行）。
  两者不等 ⇒ 回填的谓词与迁移文件头写的不一致 ⇒ **回报**（不要在真库上手工补差距）。
- **`R2-d` 必须 = 0**。> 0 ⇒ **越界**（这正是 `V138` 迁移末尾 `DO` 块的 fail-closed 断言会拒绝并回滚的形态）。
- **`R2-b` 的岗位分布**：判断受影响面的**性质** —— 若出现 `NULL` 的 `role`，说明有**无岗位**的账号带快照
  （它们同样被回填，因为它们本来就持 `order:list`）；若分布与「今天能过那 4 个端点的人」不符 ⇒ 回报。
- **`affected_accounts = 0`** ⇒ 该库**没有**「含旧码、不含新码」的快照行 ⇒ 等价回填是空操作（不是失败）。
- 🔴 **口径边界（与迁移逐字同）**：三个计数**都不过滤 `deleted`**（`V138` 的 `UPDATE` 也不过软删）
  ⇒ 计数里**含已软删的账号行**；而 `permissions IS NULL` 的行**不会**出现在任何计数里
  （`LIKE` 对 `NULL` 求值为 `NULL` ⇒ 不匹配；迁移的 `UPDATE` 同样不动它们）。事前/事后**用同一把尺子**，所以可比。

**安全说明**：只读（四段 `SELECT`，无写 / 无 DDL / 无临时表 / 无 `SET` / 无 `VACUUM`）。
扫描量 = `users` 全表（`LIKE '%…%'` **用不上索引** ⇒ 大表上是**顺序扫描**，可能**慢**）。
🔴 **前置条件**：本包假设 `users.permissions` **列存在**（它由建库脚本
`backend/admin-api/src/main/resources/db/init/schema.sql` 的补列段 `ALTER TABLE users ADD COLUMN IF NOT EXISTS permissions TEXT;` 建立，
Java 侧 `User::permissions` 也声明了它）。若 psql 报 `column "permissions" does not exist`
⇒ **停**：这说明你那个库还没补这一列（`V138` 在那种库上同样会失败）⇒ 把这条**当作读数回报**，
**不要**为了跑通本包去改库（本包一行写操作都没有）。本包**没有** `LIMIT`：这几个计数就是结论本身，截断会直接改变结论。

**读数回填到**：**#5699** 的 I4 段评论（附 `R2-a` / `R2-b` / `R2-c` / `R2-d` 四个数）。

## R3 · 回退路径账号普查：谁在走 `RoleService::getPermissionCodesForRole`

**目的**：`RoleService::getPermissionCodesForRole` 是**内置硬编码回退表**，运行时三条路径会用到它：
(a) 角色行存在但**一条 `role_permissions` 都没有**；(b) 该租户**查不到该角色行**；
(c) 员工**没有 `users.permissions` 快照**。**源码只能证明「一旦走回退就必然命中」，证明不了「生产上有没有人走」**
⇒ 必须查真库。本查询回答：**回退路径覆盖的账号在生产上到底存不存在**（这也是「受害者是否真实存在」的取证）。

`https://github.com/zhaokai-mgzn/migao/issues/5683#issuecomment-5851354952`
的「『生产上是否真的存在』—— 源码答不了，只能查真库（只读两条 SQL）」节
（该节同时是 PR #5682 独立复核的转记）。两块 SQL **逐字**取自该节（未改一个谓词）。

```sql
-- R3-a 哪些岗位一条 role_permissions 都没有（⇒ 走回退）
SELECT r.tenant_id, r.code FROM roles r
 WHERE r.deleted = 0
   AND NOT EXISTS (SELECT 1 FROM role_permissions rp
                    WHERE rp.role_id = r.id AND rp.deleted = 0);
```

```sql
-- R3-b 哪些员工没有权限快照（⇒ 回退到岗位映射）
SELECT u.tenant_id, u.id, u.role FROM users u
 WHERE u.deleted = 0 AND (u.permissions IS NULL OR u.permissions = '');
```

**预期形状（判读口径）**：

- **`R3-a` 里出现 `operator` / `product_manager`，或 `R3-b` 里员工的 `role` 是这两个码**
  ⇒ 回退路径的受害者**当时就存在**（用该账号打开「智能派单」可复现第一屏 403）。
- **两块都 0 行** ⇒ 生产上**没有**走回退路径的账号 ⇒ #5683 的 `victims_ack` 可以**真销账**（不是「代码上不会发生」）。
- 🔴 **R3-a 的每一行只是「候选」，不等于「有受害者」**：它证明「这个岗位在授权面上是空的」（走回退），
  要落到「有账号真走回退」还需要**有账号挂着这个岗位**的读数 —— 出处原文给的判据正是
  「① 里出现 `operator` / `product_manager`，**或** ② 里员工的 `role` 是这两个码」（② 就是 R3-b）。
- 🔴 **别把「R3-a 有行」直接读成「生产上有受害者」**：在**只跑建库脚本、没跑迁移链**的库上，
  内置岗位的 `roles` 行在、`role_permissions` 一行都没有 ⇒ R3-a **必然对每个内置岗位各返回一行**
  （本次一次性 PG 语法自检里就是这一形态）⇒ 那是**建库脚本的形状**，不是生产读数；
  生产库跑过 `V29` / `V124` / `V125` … 之后岗位才有授权行。把 R3-a 的**行数**当成受害者数 = 假阳性。
- **岗位分布 = `R3-b` 的 `role` 列本身**（逐行给出）。本包**不另造**按 `role` 计数的 SQL
  —— 那会变成第二份口径（出处只有上面两块，逐字复制是纪律）。
- ⚠️ **时间口径**：这两块的**原始用途**是 #5683 的取证，该单**已 CLOSED**（回退表已按 PR #5690 补齐）。
  今天跑它的意义变成「确认回退路径**没有活账号**」（`docs/design/rbac-single-source.md` §6 条目 2 的重启条件）
  ⇒ 读数请回填到 **#5699**（RBAC 跟踪单），**不要**回填到已关闭的 #5683（会把它重新拉起来）。

**安全说明**：只读（两段 `SELECT`，无写 / 无 DDL / 无临时表 / 无 `SET` / 无 `VACUUM`）。
`R3-a` 的 `NOT EXISTS` 走 `role_permissions(role_id)` 侧（`roles` 全表 × 关联探针）；
`R3-b` 是 `users` 全表扫描（`permissions IS NULL OR = ''` 用不上索引）。**两块都可能慢**，但都不会写。
两块**都没有** `LIMIT`：返回的就是普查全集，截断会让「有没有」这个结论变得不可判。

**读数回填到**：**#5699** 的评论（注明「R3 两块 SQL 的读数，原属 #5683 的取证」）。

## R6（可选）· RBAC 运行时授予值：`customer` / `agent` 账号实际拿到的 authority 集

**出处锚**：`docs/design/rbac-single-source.md` 的 §6「未取证与存疑」条目 7 末尾的重启条件

与条目 2（回退账号的存在性，与 R3 同源）。

**要人做什么**（**真环境登录观察**，不改任何数据）：

1. 用一个 `customer`（或 `agent`）角色码的账号登录一次；
2. 观察该次登录**实际拿到的 authority / 权限集合**（用你们既有的调试通道，例如把主体的 authority 打出来）。

**预期形状（判读口径）**：

## 覆盖边界（**不要把本包读成覆盖面更大的东西**）

- ❌ **SQL 未在真库上验证**：所有 SQL 只在**空的一次性本地 PG** 上验过「语法可通过、列名存在」；
  真库上的**命中行数 / 租户差异 / 行是否真的在那** 一律未知（本包不写任何预计数字）。
- ❌ **只读性是静态判的**：判据 1 是**文本层**检查（两个位置 + 大小写 + 权限码负控）；
  它**不**证明「这段 SQL 在 PG 上真的没有任何副作用」（例如某个函数内部的副作用 —— 本包不用任何自定义函数，
  但这条边界仍然成立）。
- ❌ **判据 1 不覆盖「注释把动词劈两半」**（`UP/**/DATE`）：PG 里注释等价于空白 ⇒ 那不是合法的
  写语句、不构成可执行面（它也不因此放行任何**真的**可执行写语句；边界照实登记，别读成本判据覆盖了它）。
- ❌ **扫描量与耗时未知**：安全说明里给的是「哪张表全扫、哪个谓词用不上索引」的**结构判断**，
  不是**实测耗时**；本包没有在任何真实规模的数据上跑过。
- ❌ **不含任何写操作、也不含「跑完自动修」**：本包给不出「补齐 / 回滚 / 发布」的动作，
  这些都必须各自走 PR（迁移 / 代码改动），本包只负责**取证**。
- ❌ **R5 / R6 是可选**，且 R5 依赖**尚未裁定**的发布通路、R6 依赖**真环境**；两者都不阻塞任何单。
- ❌ **本包不覆盖**「读到的读数对不对」：`V136` / `V138` 的**声明面推演**（不连库的那部分）由
  PR #5730（**已合并**）的判据承接；本包只补它**明确登记为未取证**的那一格（多租户存量库 / 快照命中面）。
