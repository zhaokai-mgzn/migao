### 1.3 HR-010 —— ❌ score 0%（mibao）

**期望**：`must_succeed: employee_manage(action=create)` + `db_verify[employee]`（李四 `13800009999` 落库）；`debug_permissions: "employee:create"`。

**实际**（逐字）：
- R1：`role_manage{action=list}!权限不足[PERMISSION_DENIED]`、`employee_manage{action=list}!权限不足[PERMISSION_DENIED]` → 模型答「⚠️ 当前账号缺少两项能力，导致这个客服账号开不了」
- R2 用户回「确认」→ 模型答「⚠️ 这里没有可确认的动作，李四的账号**还没有创建**」
- 失败行：`❌ must_succeed: employee_manage 从未被调用` + `❌ db_verify[employee]: 找不到 employee_manage 的成功调用`；`rounds=2 score=0%`

**机制（现取代码，非推断）**：
- `backend/ai-agent-service/app/tools/employee_manage.py:193-195 @071245c08`：action 级权限 —— **读取类 action 要 `employee:list`，写 action（create/update）要 `employee:create`**。
- `debug_permissions: "employee:create"` 是**单码**身份 ⇒ `employee_manage(list)` 必拒；`role_manage(list)` 要 `role:list` ⇒ 也必拒。
- 而 `staff_skill.py` 的 prompt 第 2 步逐字要求「建员工账号 → **先用 `role_manage(list)` 查到真实岗位**，收集…发确认卡，用户确认后调 `employee_manage(create)`」⇒ **合规流程的第一步必被拒**。
- 模型随后把「读被拒」外推成「写也会被拒」，**从未尝试 create**（trace 里 R1/R2 的 `tools` 只有 `role_manage,employee_manage` 的 list）。

**判定：A —— 真行为失败**，且**2026-11-04 的审计已事先裁定过这种事该怎么算**：

> `docs/testing/case-rot-audit-2026-11-04.md` §5 逐字：「`HR-002` / `HR-010` un-skip 后会在**下一次 B 端评测自然被跑到**（不是由本包触发）；**若红了，按裁定开产品单，不重新 skip**。」

本次就是「那一次」。行为缺陷 = **「有能力时不得误拒」被违反**：该身份**确有** `employee:create`，但模型只凭一次 list 拒绝就宣布"开不了"，连一次 create 都没试。

**加重项（夹具面，必须同批修，否则行为修好后仍会被挡）**：单码身份使任何前置查询都必拒。
**建议修法**：
1. 夹具：`debug_permissions: "employee:create,employee:list,role:list"`（先确认 `_inject_permission_scope` 支持逗号多码；单码假设是 #4189 第 4 项登记的未解决身份矛盾）。
2. 行为：在权限拒绝的返回里补一句权威指引（「查询无权限 ≠ 写无权限，写操作必须真的尝试一次，由系统给结论」）——`base_skill.py` 的 `_inject_permission_scope` 已有同族话术（PR #4164），把生效面从「注入块」扩到「**一次 tool 级 PERMISSION_DENIED 之后**」。
3. 按审计裁定：**开产品单，不要重新 skip**。

## 2. B 族之一：CU-004「前置未复位」的真正含义与污染半径

### 2.1 它到底为什么红（不是"共享状态没回滚"）

**真实失败（逐字）**：
- 首跑 R2：`customer_manage{action=update}!缺少更新数据` ×4 → 模型答「❌ 手机号修改未能执行成功…手机号**仍是**…」
- 重试 R2：`customer_manage{action=update}!write_blocked_masked_phone` ×2 → 模型答「⚠️ 系统校验拦住了：`139****1111` 被判定为掩码填充形态的号码，不允许写」
- `rounds=2 score=0%`；`❌ must_succeed: customer_manage 共 1 次调用无一成功（R2:failed）`

**根因**：模型把**掩码形态**的手机号填进了写工具参数。三层叠加：
1. `backend/ai-agent-service/app/tools/customer_manage.py:332 @071245c08` 的 detail 响应**对外脱敏**（`138****8000`）；
2. 确认卡 `confirmValue` 里也是掩码（`interact{confirmValue:"确认将张三…的手机号改为 139****…"}`）；
3. 用例第 2 轮 `auto_respond.fallback: "确认"` ⇒ harness 用**卡自带的 `confirmValue`** 回话 ⇒ 掩码值被当成"用户刚给的新号"再喂回模型 ⇒ 模型照着填。

`_masked_phone_write_block`（`backend/ai-agent-service/app/graph/skills/base_skill.py:3124 @071245c08`）**正确地**拦下了，并在报文里给出了真号（「顾客的真实号码是 **13900001111** —— 请直接用这个完整号码重新调用」）；但模型**没有重试**，直接回用户「没落库」。⇒ **这条的病灶是产品行为面（写不进去 + 拦截后不重试），不是夹具。**

### 2.2 哪一步"没有回滚"

`post_clean: customer_profile_restore(customer_keyword: "13900001111", phone: "13800138000")`。
复位**按本用例"写出去的新号"去定位目标**；写入被拦 ⇒ 新号不存在 ⇒ `⛔ PRECONDITION_NOT_RESTORED: post_clean: 客户「13900001111」不在库里（复位目标不存在）`。

**这是用例自己设计的「假成功探针」，不是"谁把共享夹具改坏了"** —— 用例 `data_checks` 逐字：
> 「`post_clean` 的 `customer_profile_restore` 按本用例写出的手机号定位并复位回种子号 —— **复位找不到目标即暴露「工具说改了、库里没改」的假成功**」

### 2.3 污染半径

**本次实测污染半径 = 0。** 三条独立证据：
1. 首跑 R2 四次 `缺少更新数据`、重试 R2 两次 `write_blocked_masked_phone` —— **没有任何一次 `success=true`**；
2. 若写入成功，`13900001111` 就会在库里（复位会**成功**而不是"目标不存在"）⇒「目标不存在」本身就是"没写进去"的**反向证明**；
3. R2 之前 `pre_clean` 逐字：「客户「13800138000」的档案字段本就是 13800138000，无需复位（幂等）」⇒ 种子号未被改动。

⇒ 同批其它用例（尤其共享同一手机号的命名空间组 `customer_phone:13800138000` → `AS-003/AS-005/AS-016/CH-009/CU-003/OR-013`）**没有被这条污染**；**C 族结论不需要打「可能被污染」标记**。

**但隔离面确有缺口（这才是"下次跑之前要处理"的那件事）**：
CU-004 在 2026-09-21（`issue #4992`）把 `namespaces[customer_phone:13800138000]` **换成了** pre/post_clean ⇒ 它**不再参与命名空间串行**（本次隔离分组逐字只列 `AS-003/AS-005/AS-016/CH-009/CU-003/OR-013`，**CU-004 不在其中**），而它写的正是那位共享客户。
⇒ **一旦哪次写成功**，它就会真的与那 6 条并发修改同一客户；那时的污染半径 = 同命名空间的 6 条 + 任何按该手机号读客户档案的用例。

### 2.4 「下次跑之前必须解决」的理由

不是因为这次脏了（没脏），而是因为该标记**把两种真相压进了同一个桶**：
- 真相甲：「**写没落库**」= 产品缺陷，要开单修；
- 真相乙：「**共享夹具被改坏**」= 基础设施缺陷，整批读数不可信。

现在两者共用 `PRECONDITION_NOT_RESTORED` ⇒ 本次把一条**产品缺陷**误记成**基础设施缺陷**，而基础设施标记又给整批读数打上"不可信"。下次跑如果仍然这样，同类产品缺陷会被继续吞掉（这次 mibao 17 条里就有 1 条被吞）。

**修法（不属于本包射程，登记给 harness 隔离面）**：
1. 把两种真相拆成两个标记：`db_residue_missing`（写未落库 ⇒ 归 case-level 产品失败）vs `PRECONDITION_NOT_RESTORED`（夹具真脏 ⇒ 归基础设施）；
2. 把 `namespaces[customer_phone:13800138000]` 补回 CU-004（pre/post_clean 不能替代互斥）；
3. 判别式：复位前先读一次**种子号是否仍在** —— 在 ⇒ 本次没改成，是"写失败"而不是"没复位"。

## 3. B 族之二：OR-017 的形状不兼容

**逐字失败行**：
```
❌ harness_incompatible(no_fillable_payload): 待答 **form** 卡而本轮用例**没有可填载荷**
   —— harness 拿不出这张卡的答复、只能发 fallback 文本，卡没人答（流程可能就此卡死）；
   本次红是 harness/用例形状不兼容，**不代表 agent 行为失败**
```

**具体位置**：
- 命中轮 = **R2**（首跑与重试都是 R2）。
- 用例侧（`.github/cases/order.yml:1439-1442 @071245c08`）第 2 轮**只声明纯文本**：
  `auto_respond: {fallback: "我是张三，手机13800138000，地址杭州市西湖区文三路1号"}` —— **没有** `form_values`，也没有用例级 `auto_fill`。
- agent 侧这一轮发的是 **form 卡**：`interact(component="form", title="请确认收货信息（可直接修改）", formFields=3, submitLabel="确认收货信息")`（逐字在 trace 里）。
- harness 规则：`form` 卡只能用 `auto_respond.form_values` / `auto_fill` 填（`FORM_FIELD_GROUPS` 管别名）；两者都缺 ⇒ `harness_incompatible(no_fillable_payload)`（`tests/agent_eval/local_runner.py:9369 @071245c08`）。

**不是** `order_before` DSL 的问题，**不是** `required_args` 的问题，**不是**交互卡断言的问题 —— 是「**harness 的答复载荷形状**（纯文本 vs form 字段）」与 agent 当轮卡片类型不匹配。

**后果（为什么是 0 分而不只是掉一项）**：R2 被吃 → R3 的 `auto_select: true` 去答一张**不存在的 choice 卡** → 整条轮次错位；`order_before` 的 `interact[choice:processing_items] before interact[confirm]` 后半段没发生。**注意首跑其实把订单建出来了**（R7 `order_create` 成功，`orderNo=20261106641680004`）⇒ 能力没问题，红的只是形状。

**两条修法的代价（我不替你选）**

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **甲：改用例** | 在 R2 补 `auto_respond.form_values`（收货人/手机号/地址）或用例级 `auto_fill` | 一条 YAML 改动；但**必须重跑一次验证**（¥135–295 那一档）—— form 卡字段由模型决定，本地零成本验不了；别名已覆盖 name/phone/address，实现成本低 | **中**：用例从此依赖"agent 发 form 卡"这一形状；下次模型改发 choice/confirm 又会红（且又得重跑） |
