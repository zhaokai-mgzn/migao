# AI 可执行验收协议（acceptance-protocol）

> **一句话**：让「AI 验收通过」等于「复核也能通过」。
> 适用对象：agent 会话验收 / 功能交付验收 / 修复回归验收 / 评测 case 设计评审。
> 配套技能：DSH `migao-acceptance`（执行本协议）；本文件是协议的单一事实源（rules 以本文件为准）。
> **v1.1（AI Native 去人工化）**：验收全流程**零人工执行步骤**——体验类判定由 AI
> **扮演用户代理**完成（声明视角 + 证据引用 + 双 AI 交叉验证）。人的角色只保留
> 两处且均非执行动作：① 定义验收标准/可懂度基准（标准制定）② 对双 AI 不一致的
> 最终裁定（仲裁）。任何把"待人工"写进验收流程的版本均为缺陷。
> **v1.2（2026-09-09 知识库 UI 复盘固化）**：补 **B 端 UI 旅程验收**——凡涉及
> admin-web 页面级改动（新页面/改版/布局/交互流），验收必须含**真实浏览器操作旅程**
> （起服务 → 打开页面 → 逐 Tab/逐按钮走查 → 每个写操作断言"成果物可见"）+ 截图/
> DOM 几何证据，AI 扮演"商家运营"persona 执行，禁止以"CI E2E + vitest 全绿"替代
> 浏览器旅程证据。详见 §2.3。

人工重点验收 3 个 agent 发起的会话（`sess_7f27137647e14b1e` / `sess_50ff3e3c824c4a70` / `sess_c1fce183dae24f22`），发现的问题此前评测与验收**全部判过 OK**：

| 2 | 订单/售后换货选商品后全程不引导加工项 | case 里"必须主动询问加工项"是**自然语义 data_checks，不计分** |

| 5 | 卡片渲染一会可操作一会只读、刷新后卡片消失 | 评测是 API 直连，**前端渲染/历史重放完全不可见** |
| 6 | 会话自动关闭（空闲判定时间点错） | 评测每用例开新会话，**会话生命周期从未被测** |
| 7 | 澄清能力"强化没体现" | 验收判的轴是"模糊意图弹卡时机"，用户在乎的轴是"明确流程主动引导"——轴错了 |

**2026-09-09 知识库 UI 复盘（v1.2 补充）**：从 0 建设的功能（LLM WIKI，P1~P9 一天堆完、
前端 P8 一次性堆叠）交付后，人工一次发现 **5 个 UI 问题**（面包屑/样式与全局不一致、
分页被米宝浮动按钮遮挡、模板套用/候选采纳后成果物不可见）——此前验收报告自认
「零 UI 证据」（kb-closed-loop REPORT 复核栏原文），L1/L2 全在 API/Agent 行为层，
UA 只扮演了 C 端顾客 persona，B 端商家后台的浏览器操作旅程一条未验；单测断言停留在
「API 被调用」而非「用户看到结果」。根因与 §0 机制原因 1/6 同构（断言对象错位 + 前端盲区），
在 UI 层重演。⇒ 本协议 v1.2 新增 §2.3「B 端 UI 旅程验收」强制章节 + 研发侧前置拦截
（migao-dev-flow §15）。

### 六个机制性原因（每条附证据位置）

1. **断言对象错位**：评测断言"工具被调用"，人工验收看"用户看到的对话"。
   `tests/agent_eval/local_runner.py` 的 `check_expectation` 只匹配 tool 名 + 关键 args；
   `final_text` 只判"有无"，不判"内容"；**`send_message` 不采集 `interactive`（卡片）事件**
   （只处理 text/tool_call/tool_result/error/done）——卡片里装了什么完全不可见。
2. **"任意一轮命中即过"**：`for r in results: if ok: passed=True`——只要最终某个轮次
   出现匹配即得分，**无轮次锚定、无顺序断言**（OR-016 的 bug 场景照样 score 1.0）。
3. **关键断言全在自然语义 data_checks（不计分）**：OR-016/AS-007 的核心行为
   （"confirm 前必须主动询问加工项"、"processingFee 计入 subtotal"、"禁止只取第一个"）
   全是 data_checks；runner 明确只有含 `success=true`/`error.code=`/`未被调用` 的
   data_checks 才计入评分，其余"仅在最后轮错误守卫中参与"。→ **即使重跑，同类问题仍会漏**。
4. **金额/数据正确性无机器断言**："面料小计+加工费=subtotal"这类数学没有可执行断言。
5. **验收视角同源**：场景 AI 自己写、自己跑、自己判"优秀/通过"（`acceptance_runner.py` +
   scenarios_*.json 同一手笔）；且验的是实现者关心的轴，不是用户关心的轴。
6. **前端/持久化/生命周期结构性盲区**：刷新重放、会话列表、close_idle、多轮 UI 状态
   都不在 API 级评测覆盖内；**agent 测试时留下的会话本身就是产品数据**，评测从不
   以产品视角复核自己留下的会话。

> 结论：现有评测体系证明的是"工具链路通"，不是"用户看到的会话好"。本协议补齐后者。

## 1. 核心概念

### 1.1 验收剧本 ≠ 评测用例

| | 评测用例（cases/*.yml） | 验收剧本（acceptance scenarios） |
|---|---|---|
| 视角 | 功能正确性 | 用户旅程 |
| 输入 | 脚本化台词（user_inputs） | 用户真实会走的路（点卡/刷新/换窗口/打岔/中途离开） |
| 断言对象 | tool 调用 + 关键 args | 用户可见行为：回复文本/卡片内容/时序/终态/持久化/生命周期 |
| 环境 | 每用例新 session | 真实会话 + **复核 AI 自己留下的会话** |
| 判定 | 机器打分 | L1 机器 + L2 证据引用 + UA 用户代理判定（零人工执行） |

### 1.2 L1/L2/UA 断言降级阶梯

| 档 | 内容 | 判定者 | 证据要求 |
|---|---|---|---|
| **L1** | 机器可判：tool+args、error 事件、卡片事件字段、时序 before/after、final_text 正反关键词、金额计算、字段内容（脱敏/数量/状态） | runner 自动 | 断言命中即证据 |
| **L2** | 半自动语义：候选 grounded（引用真实商品/订单）、上下文延续正确、"不编造" | AI 判，**必须引用 transcript 原文**（轮次 + 原文片段） | 引用缺失 = 判定无效 |
| **UA** | 用户代理层：话术可懂度、表达是否自然、低学历用户视角体验 | **AI 扮演用户代理判定**：① 声明扮演 persona（如"低学历顾客"）② 判定必须引用原文 ③ 对照可懂度基准（短句/给例子/给出口/不编造）逐条给分 | 视角声明 + 原文引用 + 基准对照，缺一不可 |

**降级原则**：能升 L1 的绝不留在 L2；能 L2 的绝不留给 UA。UA 点越少，验收越确定。
**AI Native 铁律**：全流程零人工执行步骤——UA 不是"留给人判"的档，而是 AI 以用户
视角判定的档；每条 UA 判定可被另一 AI（复核验收）交叉复核。

### 1.3 可执行断言铁律（本协议最硬的一条）

> **关键行为（必须/禁止/金额/时序/内容）禁止只写进自然语义 data_checks。**

写 case / 验收剧本时自查：
- 断言包含"必须/禁止/应/不能"等义务词 → 必须是 L1 可执行断言（或可映射到机器判定），
  禁止躺在 data_checks 里充当"看起来有覆盖"；
- 断言包含金额/数量/字段结构 → 必须能对 tool_call args / tool_result / 卡片事件做结构断言；
- 现状 case 里已存在的自然语义 data_checks（如 OR-016/AS-007）→ 视为**未覆盖**，
  直到升级为可执行断言（见 §6 Phase 2 与 §5 沉淀）。

### 1.4 证据链与重放

- 每次验收输出 **transcript artifact**（每轮：用户输入 → 全部 SSE 事件原文 → 最终文本/卡片），落盘可复核；
- 每条判定（通过或问题）必须引用证据位置：`R<轮次> / <事件> / <原文片段>`；
- **修复 = 重放同剧本**：修前失败证据 + 修后通过证据成对出现，缺重放 = 未修复。

### 1.5 独立验收与双 AI 交叉验证（防同谋）

- 验收 agent 与开发 agent 分离：验收者只拿「验收剧本 + 断言规范 + 被测环境」，
  不拿实现细节、不拿开发者自测结果；
- **双 AI 交叉验证**：主验收（按 spec/剧本判定）+ 复核验收（**不看 spec**，独立视角
  抽样判定，防合谋）——两者都是 AI 执行，无人工步骤；
- 两者结论一致 → 采纳；不一致 → 以证据引用更充分者为准，并输出差异清单；
  仍不一致 → 标记"待裁定"（由标准定义者裁定，裁定是仲裁不是执行）；
- 验收者报告"全部通过"时，必须附**抽验证据**（复核验收独立抽样的完整 transcript 原文），
  复核方不需要重跑全部，但必须能基于证据独立复核每条结论。

## 2. 验收执行流程

> 完整流程由 DSH 技能 `migao-acceptance` 驱动；本节约为七个步骤与完成判据。

| 步 | 动作 | 完成判据 |
|---|---|---|
| 1 | **定对象**：本次验收什么（功能交付 / agent 会话 / 修复回归）；从 issue 验收标准或会话清单取"被验收对象" | 对象清单可枚举（会话 ID / 功能点） |
| 2 | **写剧本**：按用户旅程写验收剧本（见 §2.1 模板），**必须含"复核 AI 留下的会话"条目** | 每个验收点都有期望的用户可见结果（verbatim 或可判定谓词），禁止"表现正常/差不多" |
| 3 | **声明验收矩阵**：对象 × 断言（每条标注 L1/L2/UA） | 每条验收点都有判定档位与证据要求；出现"待人工"即不合格 |
| 4 | **执行采集**：跑 runner / 会话遍历，产出完整 transcript artifact | 证据可复现（同环境重跑能再产出） |
| 5 | **判定**：L1 机器结论；L2/UA 逐条引用证据（UA 附 persona 声明与基准对照） | 每条判定都有证据引用 |
| 6 | **出报告**：按 §4 模板，问题分级 P0（阻塞功能）/P1（体验缺陷）/P2（优化项） | 报告含对象清单、矩阵结果、问题清单（含证据）、复核验收抽验 |
| 7 | **沉淀**：每个问题 → ① 补/改 case（断言必须是可执行的）② 用"旧失败会话重放"验证新 case 能拦住该问题（case 有效性验证）③ 提 issue 关联修复 | 新 case 在旧失败场景下必 fail、修复场景下必 pass（无此验证 = 沉淀无效） |
| 7 | **沉淀**：每个问题 → ① 补/改 case（断言必须是可执行的）② 用"旧失败会话重放"验证新 case 能拦住该问题（case 有效性验证）③ 提 issue 关联修复 | 新 case 在旧失败场景下必 fail、修复场景下必 pass（无此验证 = 沉淀无效） |

### 2.1 验收剧本模板（用户旅程视角）

```md
## 剧本 <ID>：<一句话用户旅程>
被验收对象：<会话 ID 清单 / 功能入口>
环境：<mibao|xiaobu> / <测试|生产> / <版本 sha>
### 场景 S1 <名称>
用户动作序列（含点卡/刷新/切换/离开等真实操作）：
1. <动作>
2. <动作>
...
验收点：
- [ ] L1 <可执行断言>
- [ ] L2 <语义断言，注明需引用哪段 evidence>
- [ ] UA <用户代理判定：声明 persona（如"低学历顾客"）+ 可懂度基准 + 需引用哪段原文>
### 场景 S2 ...
```

### 2.2 "复核 AI 留下的会话"专项（本次复盘的直接教训）

- 范围：开发/评测 agent 在最近 N 天内创建的真实会话（`/api/chat/sessions` 列表、客服工作台可见的会话）；
- 动作：以产品视角（打开会话 → 读历史 → 继续对话 → 点卡片 → 刷新 → 看会话列表/生命周期）逐条检查；
- 断言重点：错误回复是否被持久化、卡片态是否随刷新保持（不一会可操作一会只读）、
  会话是否无故关闭、信息是否前后一致（出现组件 ≠ 卡片语义）；
- 通过判据：**每一条**都能在会话原文中找到证据，且无 P0/P1 遗留。

### 2.3 B 端 UI 旅程验收（v1.2 新增，2026-09-09 知识库 UI 复盘固化）

**触发**：凡涉及 admin-web 页面级改动（新页面 / 改版 / 布局 / 交互流 / 样式）的功能交付或修复回归，
除 agent/API 验收外，**必须**包含本节约的浏览器旅程验收；禁止以「CI E2E + vitest 全绿」替代浏览器证据
（9-09 知识库验收漏掉的 5 个 UI 问题全部需要真实浏览器才能暴露，教训见 §0）。

- **执行**：起本地服务（admin-web:3001 + admin-api:8080，必要时 + ai-agent）→ 登录 →
  AI 扮演「商家运营」persona 逐页走查受影响页面，逐项采集截图 / DOM 几何证据
  （`getBoundingClientRect` 打点即可，无需 Playwright 全家桶）；
- **必查四类**（对应 9-09 五问题的四个类别）：
  1. 面包屑 / 页面标题 / Tab 与侧边栏菜单命名一致性；
  2. 页面样式与全局基准对照（容器内边距、标题字号、Tab 高亮色、控件 focus 态——对照既有标准页）；
  3. **布局遮挡几何断言**：内容不足一屏 + 长列表滚到底两个场景，底部锚定元素（分页等）
     与 fixed 浮动元素（米宝 FAB）矩形无重叠、末页按钮可点击；
  4. **写操作成果物可见性**：每个写操作（套用 / 采纳 / 新建 / 归档 / 删除）后，
     列表刷新 / Tab 跳转 / 弹窗回填，用户能定位到成果物（9-09 模板套用与候选采纳两个 bug 的类别）。
- **判定与证据**：四类逐项 ✅/❌ + 截图 / 几何数值引用；❌ 项按 §5 沉淀（补可执行断言或回归剧本）；
- **与研发侧衔接**：开发提交流程已前置同款验证（migao-dev-flow §15「UI 旅程强制验证」），
  验收时直接引用其证据避免重复走查；剧本模板见 `docs/testing/frontend-acceptance-checklist.md` §7~§9。

## 3. 断言规范（reference）

### 3.1 时序断言（before/after）

- 义务顺序必须显式断言：`interact(choice, multiSelect=true) before order_create`、
  `interact(confirm) before after_sales_manage(create)`；
- 反序命中 = fail（现有"任意一轮"语义下反序照样 pass，必须显式锚定轮次或顺序）。
- 轮次锚定语法（Phase 2 runner 支持）：`@R3 tool: ...` 表示第 3 轮必须命中。

### 3.2 金额/数据正确性断言

- 涉及金额的验收点必须断言**数学关系**：如 `subtotal = 面料小计 + processingFee`、
  `quantity 按计价方式（per_meter=米数 / per_set=1 / per_area=宽×高）`；
- 数据落库断言：create 类 payload 必须断言完整结构（如 `processing_item_configs` 含
  `customPrice=unit_price`、`unit=真实单位`），禁止只断"工具被调用"。

### 3.3 反模式断言（负向）

- "禁止/不得"类行为显式断言：禁止提前弹 confirm、禁止跳过加工项询问（商品绑定加工项时）、
  禁止只取第一个名称、禁止二次询问、禁止重复查询同一商品；
- 负向断言必须与正向断言配对，防止"该做的没做，不该做的做了"两头漏。

### 3.4 final_text 断言

- 关键轮次断言回复内容：正向关键词（如兜底话术含"转人工"出口）+ 反模式禁词表
  （如"抱歉，遇到问题 / 会话太长 / 无法处理"）；反模式词出现 = fail；
- 禁词表按域维护（error 文案、打扰式提示、编造商品名/价格）。

### 3.5 卡片（interactive 事件）断言

- runner 必须采集 interactive 事件并断言：component 类型、options 内容（grounded：
  引用真实商品名+价格）、multiSelect/pageMeta 透传、confirm 卡 confirmValue 语义；
- 前端验收另加：历史重放后卡片渲染态与交互态保持（一会可操作一会只读 = fail）。

### 3.6 生命周期/持久化断言

- 会话关闭（close_idle 时间点 = 最后一条消息时间）、消息持久化完整性、
  刷新后历史含交互卡与最终回复、转人工快照（aiContext）跨会话可见。

## 4. 证据与报告规范

### 4.1 transcript artifact（每次验收必产）

```
acceptance/<日期>/<剧本ID>/<场景ID>.transcript.md
R1 用户: <原文> [📷xN]
   🃏 卡片: <component> <title> <options/fields 摘要>
   🔧 tool: <name>(<args>)
   💬 AI: <原文>
   ⚠️ error: <原文>
R2 ...
```
（由 runner 自动生成；AI 执行时按同格式整理，不得省略任何轮的 AI 原文）

### 4.2 验收报告模板

```md
# 验收报告 <对象> <日期> <被测版本 sha>
## 结论
- 通过 / 有条件通过（列出 P0/P1）/ 不通过
## 验收矩阵
| 场景 | L1 | L2 | UA | 结果 | 证据引用 |
## 问题清单
| # | 级别 | 问题 | 证据（会话/轮次/原文） | 对应 case | 修复 PR |
## 复核验收抽验（独立 AI 视角，零人工）
| 抽验项 | 证据位置 | 复核结论 | 与主验收一致性 |
## 沉淀记录
| 问题 | 新增/修改 case | case 有效性验证（旧失败重放 fail / 修复重放 pass） |
```

---

## 5. 失败沉淀闭环（防止同类问题再漏）

1. 验收发现问题（AI 验收或用户反馈） → 立即定位到机制原因（§0 六条哪一条）；
2. 补 case 时遵守 §1.3 可执行断言铁律：关键行为必须 L1，禁止自然语义 data_checks 冒充覆盖；
3. **case 有效性验证**：拿"出问题的旧会话/旧场景"重放新 case → 必须 fail；修复后重放 → 必须 pass；
   两步缺一，该 case 不算覆盖（这正是 OR-016/AS-007 现状的缺口——断言不可执行，无法证明有效）；
4. 若问题属于 §0 原因 6（前端/生命周期盲区），除补 case 外必须补验收剧本场景（L1 或 L2），
   并在 runner 升级（§6）后纳入自动执行。

## 6. 现有工具差距与升级需求（Phase 2，未实现前按协议以 AI 判定 + 证据执行）

### 6.1 `local_runner.py` 差距清单

| 差距 | 现状 | 升级需求 |
|---|---|---|
| interactive 事件未采集 | send_message 只处理 text/tool_call/tool_result/error/done | 采集 interactive/card 事件并进断言 |

| final_text 无内容断言 | 只判有无 | 正反关键词断言 |
| 金额无断言 | — | 结构化 args 数学断言钩子 |
| 无证据落盘 | 只打印摘要 | 输出 transcript artifact（§4.1）+ 验收报告 JSON/MD |

### 6.2 `acceptance_runner.py` 差距清单

- 已采集 interactive 事件（好），但**无任何断言逻辑**，只渲染不做判定 → 加 L1/L2 判定；
- 场景 JSON 无验收点声明 → 场景格式扩展：`checks: [{level, type, expect, ref}]`；
- 无报告输出 → 接 §4.2 模板。

### 6.3 落地顺序建议

1. local_runner 补 interactive 采集 + 轮次/顺序断言 + final_text 关键词（收益最大）；
2. 把 OR-016/AS-007/PR-014/PR-015 等"关键行为在 data_checks"的 case 升级为可执行断言，
   并做 case 有效性验证（§5-3）；
3. acceptance_runner 加断言与报告；4. 生命周期/前端重放场景入剧本。
