## 0. 结论先行

1. **有赞的「快」不是建站快，是把开店拆成「平台可代办的流水线」**：试用态兜住认证等待 →
   扫码授权让平台代开发代提审 → 行业模板让商品/装修零设计 → 一证多店复用主体 →
   服务商补「最后一公里」人力。五件事缺一件，商户体感都会从「10 分钟」掉回「3 天」。
2. **微信侧交易只有一条官方主干：微信小店**。商户自己开小店（企业店/个体工商户店，
   1–3 天），我们做「**平台小程序导购 + 店铺卡/商品卡 + 微信客服 AI + 订单同步**」，
   **钱进商户自己的商户号，平台不碰钱**（无二清）。
3. **抖音侧不要做「店」，做「线索 + 留资」**：窗帘是「高客单 + 非标 + 要上门量尺」，
   抖音的正解是「**短视频/直播/POI → 线索组件或私信 → 留资 → 回微信成交**」。
   且**私信 API 已停止新增准入**、存量还有 4 项质检指标 —— 所以首版用**官方工具 + 线索组件**，
   米宝接入是拿到资质后的增强项。有赞旧版「抖音点单小程序」已被其官方手册判为下线 ——
   **别把「抖音开店」写进产品卖点**。
4. **架构结论**：渠道做成**适配层 + 开关**，不是一个平台一套代码；
   **商品/库存以 MIGAO 为主、订单以渠道回传为主**；入口统一用「一店一码 / 一场景一参」归因。
5. **对 MIGAO 的最小闭环**：M0 = 微信小店 + 平台小程序店铺页 + 商品卡（**需先建关联关系**）；
   M1 = 微信客服接米宝；M2 = 抖音线索/团购；M3 = 一证多店 + 服务商。

### 0.1 一张表看懂：有赞 vs MIGAO

| 维度 | 有赞 | MIGAO 应该怎么做 |
|---|---|---|

## 1. 有赞把「开店」拆成了什么（可抄的 6 个机制）

### 1.1 官方口径的开店七步

有赞帮助中心《有赞微商城开店七步走》（2025-10-29 更新）把开店定义为：

| 步 | 动作 | 关键事实 |
|---|---|---|
| 1 | **店铺认证** | 主体信息认证（营业执照公示，电商法要求） |
| 2 | **装修店铺** | 直接套用系统「微页面」模板，或用装修组件自定义 |
| 3 | **发布商品** | 商品管理 + 商品分组 |
| 4 | **授权/发布微信小程序** | **把小程序授权给有赞，有赞自动生成店铺小程序并提交微信审核**；功能更新自动提审，失败可一键重提 |
| 5 | 推广店铺 | 发朋友圈/群 |
| 6 | 订单发货 | 批量发货、多仓发货 |
| 7 | 结算提现 | 订单完成（发货 7 天后）→ 提现 |

来源：[有赞微商城开店七步走](https://help.youzan.com/displaylist/detail_4_11710)、
[微信小程序授权发布教程](https://help.youzan.com/displaylist/detail_4_4-2-2832)。

> 注意第 4 步的两条硬约束：**小程序认证主体必须与店铺主体一致，且必须为企业**。
> 这解释了为什么「代开发」能成立 —— 平台代的是**代码与提审**，代不了**主体**。

### 1.2 六个机制（按可抄性排序）

| # | 机制 | 有赞怎么做 | 对 MIGAO 的启示 |
|---|---|---|---|
| 1 | **试用态：体验与认证解耦** | 未认证也能有「试用小程序」店铺，可装修、可预览；要收款才「立即转正 + 法人验证」 | 我们最大的摩擦是经销商「没执照 / 不敢授权」。给「**样板店**」：无认证即可生成带真实面料图册与报价器的店铺，先线下看货下单，认证后再开线上支付。**这是开户率的单点杠杆** |
| 2 | **一证多店：主体认证授权复用** | 总部一次认证，按规则授权给全部/指定下级店；被授权方不得转授权；取消授权则下级失效 | 布艺是「1 厂牌 + N 经销商 + M 门店」。做「**总部认证 → 批量开子店**」，子店继承主体资质但**资金账户独立**。开店从「每家 3 天」变「每家 3 分钟」 |
| 3 | **扫码授权 + 平台代开发代提审** | 小程序管理员扫码 → 有赞生成店铺小程序 → 提交微信审核 → 版本自动更新 | 走微信**第三方平台（服务商）代开发**：商户扫一次码，我们出包、提审、发版。**前提是提前 2–3 个月准备第三方平台资质** |
| 4 | **一套后台 + 多端授权**（不是各平台独立开店） | 同一「多渠道」目录逐端授权：微信小程序、微信小店、快手小程序、支付宝/小红书小程序；卡片状态 = 未授权/审核中/已上线/被拒 | 我们不需要「每个平台开一个店」，需要「**一个商品中心 + N 个渠道开关**」；渠道卡片必须显示三态（授权/审核/上线），否则商家以为已接通 |
| 5 | **行业化批量导入模板** | 按商品类型下载模板批量导入，回显「导入总数/成功/失败」 | 通用 Excel 对布艺无用。给「**面料 / 成品帘 / 辅料**」三套模板：色号、克重、幅宽、成分、可做工艺、按米/平方/窗计价、最小起订量。**导入成功率就是激活率** |
| 6 | **服务商三层体系** | 代理商（0 加盟费 + 保证金 + 续费分成）/ 服务商（2 万保证金 + 3 人考试 + GMV 5 万授牌）/ ISV（有赞云 + 服务市场） | 布艺开店真正的瓶颈不是软件，是「**没人帮商家拍面料、配方案、排安装**」。平台卖软件、城市服务商卖人力，按店收费 + 成交分成 |

## 2. 微信侧：入口矩阵与「能批量复制的只有 4 类」

### 2.1 入口全景（合并为 9 类；只有 4 类可被平台批量复制）

| 入口 | 开通门槛 | 谁必须自己做 | 适合场景 |
|---|---|---|---|
| **微信小店**（店铺卡/商品卡/搜一搜） | 企业店或个体工商户店（**无个人店**），同一执照**最多 30 家店** | 主体入驻、保证金、法人扫码 | **交易主链路** |
| **平台小程序**（含小程序码） | 企业主体 + 认证 + **ICP 备案** + 类目 | 平台自己（一次审核） | 导购/详情/量尺/售后 |
| **微信客服** | 企业微信主体 + 客服账号（单企业 ≤5000 个） | 商户开企微、授权我们 | **米宝对话主入口** |
| **企业微信带参链接** | 同上 | 商户 | 导购 1v1、私域 |
| 公众号（服务号）菜单/模板消息 | 服务号 + 认证（商户主体） | 商户 | 老客复购、通知 |
| 视频号（直播/短视频挂商品） | 小店 + 关联视频号 | 商户 | **窗帘「挂起来的垂感」展示** |
| 朋友圈广告 | 广告主账户 + 行业资质 | 商户 | 付费拉新 |
| 搜一搜 | 随小店/小程序收录 | — | 品牌词拦截（**规则未公开**） |
| 线下二维码 | 小店 `getshopqrcode` / 小程序码 | — | 门店、建材市场、装修公司 |

**关键判断**：公众号、视频号、广告账户**必须商户自己持有并认证**（主体资质不可代持）；
真正能「平台一次建设、复用到 N 个商户」的只有 **小程序（含码）、微信小店（含卡）、
微信客服链接、企微带参链接**这 4 类。

### 2.2 微信小店：开店事实（决定「快速开店」能不能成立）

| 项 | 事实 |
|---|---|
| 店铺类型 | **企业店 / 个体工商户店**（2026-06-17 版入驻规则，**无个人店**） |
| 主体上限 | 同一营业执照**最多 30 家店** |
| 类目 | **家纺属「开放类目」**（普通准入，后台自助开通即可上架）→ 对窗帘批量开店是最大利好 |
| 定制家具类目 | 结算侧特殊规则：**发货起 10 个月未确认收货则自动退款** → 开店引导优先选「家纺」 |
| 支付 | 开通小店时**自动新开一个微信支付商户号**，货款冻结 → 确认收货 +7 天转可提现 → 商户提现到对公户（每日 1 次） |
| 平台角色 | 我们可通过**权限集 129/130/131/132** 代做商品/订单/发货/售后；**主体与资金不可代** |

### 2.3 商品卡 vs 店铺卡：关联关系是分水岭（**更正底稿**）

| 组件 | 最低基础库 | 是否要求「小程序 ↔ 小店」关联关系 | 用途 |
|---|---|---|---|
| `<store-home>` 店铺卡 | 3.5.5 | **不要求** | 展示整店，点进小店首页 |
| `<store-coupon>` 优惠券 | 3.8.3 | **不要求** | 任意小店的券都可在任意小程序调用 |
| `<store-product>` 商品卡 | **3.7.0** | **要求**（小店发起邀请 → 小程序接受，`status=1`） | 单品卡，半屏拉起小店下单页 |
| `<store-gift>` 礼物 | 3.8.10 | 要求，且商家需对小程序创建礼物活动 | 送礼 |
| `wx.openStoreOrderDetail` | — | 不要求关联，但校验「订单来自该小程序」 | 订单详情 |

官方原文：**「小程序连接小店的能力依赖关联关系……先建立小程序与小店的关联关系，
再按需接入小程序组件、小程序 API、定制商品、礼物营销和事件通知」**；
组件表逐项标注「需与小店建立关联关系」/「无关联关系限制」。

来源：[小程序连接小店（开发指南）](https://developers.weixin.qq.com/doc/store/shop/guide/connect/miniprogram)、
[store-product 组件](https://developers.weixin.qq.com/miniprogram/dev/component/store-product.md)、
[store-home 组件](https://developers.weixin.qq.com/miniprogram/dev/component/store-home.md)。

> **这意味着**：一个平台小程序要展示 N 个商户的商品卡，就得**逐户建立关联关系**
> （商户在小店后台发邀请、我们接受）。`<store-home>`/优惠券没有这个限制，
> 可作「未建立关联」时的降级方案。**底稿 §3.2 的「不限制关系」结论对商品卡不成立**，
> 但对店铺卡/优惠券成立 —— 底稿把两者混在一张表里了（见 §8.1）。
> 另外：**定制商品链路**（`uploadec` → `media_id` → `<store-product>` → `getdownloadurl`）
> 官方定位「个性化印刷、定制刻字、3D 打印」，窗帘量尺定制**是否被类目接受未核实**（§8）。

### 2.4 身份打通的天花板：UnionID 只能绑 20 个小店

| 项 | 规则 |
|---|---|
| 一个小店 | 只能绑**一个**开放平台账号 |
| 一个开放平台账号 | 最多 **20 个小店**（5 个同主体 + 15 个关联主体） |
| 小程序侧 | 50 个同主体/关联主体 + 5 个不同主体，**每月最多新增 5 个不同主体** |

⇒ **无法用「一个开放平台账号」给成百上千家无关联商户做 UnionID 打通**。
规模化只有两条路：① 每商户自带主体/小程序（我们只做 SaaS + 代开发，即「旗舰版」）；
② **放弃 UnionID**，用「商户维度 openid + 手机号 / 自建账号」做身份归并
（跨商户不可识别同一人，同商户内可识别）。

来源：[小店开发者指南 · UnionID 机制](https://developers.weixin.qq.com/doc/store/shop/dev_before/guide)、
[腾讯客服 · 绑定规则调整](https://kf.qq.com/faq/180104uY7r2a180104ziqumu.html)。

### 2.5 AI 客服的四个通道（米宝该走哪条）

| 通道 | 谁能调 | 下发额度 | 多租户可行性 |
|---|---|---|---|
| **微信客服（qyapi kf）** | 自建应用 / **第三方应用** | 用户主动发消息后 **48h / 最多 5 条** | ✅ **首选**：第三方应用持「微信客服→管理账号/分配会话/收发消息」权限；`scene_param`（≤128B）可做「一店一码」归因 |
| **小程序客服消息** | 第三方平台（**权限集 19**） | 用户发消息 5 条/48h | ✅ 补充（我们自己的小程序内） |
| 公众号客服消息 | 服务号 / 第三方代调用 | 5 条/48h；菜单/关注 3 条/1 分钟 | ⚠️ 商户账号、额度按商户计 |
| 小店商家客服 `commkf` | **仅商家自研** | 48h / 5 条 | ❌ **官方明确不支持第三方服务商（ISV）调用，无独立权限集** |

**必须写进产品口径的两句**：
1. 米宝**不能**以 ISV 身份接管小店原生咨询（只能商户自研接入，每户配 API 模式，且切换不可逆）；
2. 平台小程序**打不开商户的微信客服**（`wx.openCustomerServiceChat` 要求小程序与企微企业**同主体绑定**）。

> **48h / 5 条的准确语义**（官方原文）：「仅当微信客户在**主动发送消息**给客服后的 **48 小时**内，
> 企业可发送消息给客户，**最多可发送 5 条**；**若用户继续发送消息，企业可再次下发消息**。」
> ⇒ ① 48h 从用户最近一次主动发消息起算；② 5 条是「企业 → 客户」的下发条数；
> ③ 用户再发一条 = **重新计时 + 重置 5 条**；④ 每次 `send_msg` 调用算 1 条（所以要把多段回复合并成 1–2 条）；
> ⑤ 超限/过期的失败码：`4`=超过 48h、`5`=会话已关闭、`6`=超过 5 条、`8`=主体未验证。
> 另外 `send_msg` 仅在会话处于「新接入待处理 / 由智能助手接待」状态时可调 —— **转人工后 AI 不应再发**。

### 2.7 微信小店 × 米宝：能绑到哪一层、怎么落地

#### 2.7.1 先分清「绑定」的三种含义

| 「绑定」对象 | 能不能 | 谁授权 | 能否批量 | 关键限制 |
|---|---|---|---|---|
| **小店原生客服**（商品页「客服」按钮） | ⚠️ **只能商户自研**（商户自己的 AppID/AppSecret 换 `access_token`） | 商户 | ❌ 每户手工配置 | 官方明确**不支持第三方服务商（ISV）**；切 API 模式**不可逆**，聊天记录不互通，工作台欢迎语/自动回复失效 |
| **微信客服**（微信里的客服会话） | ✅ **能**（第三方应用持「微信客服→管理账号/分配会话/收发消息」权限） | 商户扫码授权 | ✅ 一次授权、批量复制 | 48h / 5 条；被动接待；语音只给 `media_id`（需 ASR） |
| **平台小程序客服消息** | ✅ 能（权限集 19） | 平台自己 | ✅ | 用户必须在我们小程序内 |
| **商品/订单数据** | ✅ 能（ISV 权限集 129/130/131/132） | 商户授权服务市场/第三方平台 | ✅ | **商品卡还需要「小程序↔小店」关联关系**（§2.3） |

> **一句话**：微信小店**没有 AI 插件位**。想让客户在「小店商品页点客服」就遇到米宝，只有
> **商户自研接入**这一条路（每户手工、不可逆）；想**批量**，只能把米宝放在**微信客服**里，
> 用商品卡/店铺卡把客户导进小店下单。

#### 2.7.2 推荐组合（默认 + 标杆）

```
默认（可批量）：客户 → 微信客服会话（商户企微，授权给我们）→ 米宝接待
                     → 发小程序卡片（店铺卡/商品卡）→ 小店原生下单/支付
                     → 订单通知回传 → 米宝查单/售后

标杆（1 家）：客户 → 小店商品页「客服」→ 小店商家客服 API（商户自研）→ 米宝接待
              （验证「店内咨询」转化是否显著更好，再决定是否给旗舰版）
```

#### 2.7.3 落地 runbook（M0 一周可验证）

| 阶段 | 商户做什么（约 30 分钟） | 平台做什么 | 失败点 |
|---|---|---|---|
| 1 | 开微信小店（执照 + 法人 + 类目「家纺」+ 保证金），上架商品 | 给图文 SOP + 类目建议 + 商品导出模板 | 类目与经营范围不匹配被打回 |
| 2 | 注册企业微信 → 开通微信客服 → 建客服账号 → 取客服链接 | 生成「一店一码」（`scene_param=tenant:channel`） | 主体未验证 → `fail_type=8` |
| 3 | 授权：MVP 用「自建应用」给 `corpId/secret/agentId`；规模化用第三方应用 | 回调网关 + `sync_msg` 拉取器 | 应用不在「微信客服-可调用接口的应用」→ 48001 |
| 4 | （商品卡）小店发起「合作账号」邀请 → 我们小程序接受 | 接受邀请、落 `tenant_channels` | 邀请超时/拒绝 |
| 5 | 真实客户咨询 1 次 | 米宝回复 + 商品卡 + 查单 | 48h/5 条超限 → `fail_type=6` |

**平台侧 6 个模块**：① 回调网关（验签 + AES 解密 + 幂等）② 拉取器（`sync_msg`，`cursor` **入库持久化**）
③ 租户映射（`open_kfid → tenant_id`，`external_userid → 客户档案`）④ 米宝（复用 LangGraph + 工具）
⑤ 发送器（每条回复 1–2 条，5 条预算状态机，`fail_type` 打点）⑥ 订单同步（合作账号/ISV）。

#### 2.7.4 验收判据（缺一不算走通）

1. 真实客户（非内部账号）完成 1 单，订单号可在小店后台对上；
2. 米宝首响 < 10s，48h 内**不超 5 条**、无重复回复（重复投递同一事件只回一次）；
3. 订单通知 → 落库 < 30s，AI 查单结果与店铺后台一致；
4. 语音/图片不丢（语音走 ASR、图片走 Vision），均能给出可读回复；
5. 断线可恢复：`cursor` 丢失后重拉 3 天内消息不重复、不丢关键会话。

#### 2.7.5 工程量与风险

- **代码现状**：仓库里**没有任何**微信客服/微信小店相关代码（`grep open_kfid|kf_msg_or_event|channels/ec` 为空），
  需从零建：`WechatKfController`（回调）、`WechatKfClient`（sync_msg/send_msg）、`kf_sync_cursors` 表、
  `tenant_channels`（渠道账号）、发送预算状态机。
- **不建议首版做小店原生客服（commkf）**：每户配置 + 不可逆切换 + 无 ISV，ROI 低；
  等微信客服链路跑通、确认「店内咨询」有显著增量再做。

### 2.8 接入「客户的企业微信」是不是一条路？

**是，而且应该作为 L1 的首选载体** —— 但要先分清企微的三层能力，**只有一层能做 AI 自动接待**：

| 层 | 能力 | 米宝能否自动接待 | 说明 |
|---|---|---|---|
| **微信客服**（企微的一个产品） | 客户在微信里点客服链接/扫码 → 会话进企微客服工作台 | ✅ **能**（第三方应用持「微信客服→管理账号、分配会话和收发消息」） | 客户**不加好友、不装 App**；单企业 ≤5000 客服账号；48h/5 条 |
| **企微工作台**（自建/第三方应用） | 员工在企微里打开 H5 应用 | ✅ 能（B 端：黄金策/米宝/客户画像） | 员工侧入口，不是客户侧 |
| **企微外部联系人**（加好友 1v1） | 欢迎语、群发、侧边栏、SOP 提醒 | ❌ **不能**（官方客户联系 API 没有「实时对话自动回复」接口） | 只能做辅助；「企微好友聊天机器人」不是官方能力 |

**为什么企微是好载体**：
1. 商户**本来每天就在企微里工作**，不用新增一个后台；
2. 客服账号可批量建（≤5000），一个租户一套映射；
3. 客户从**客服链接/二维码/小程序卡片**进入，`scene_param`（≤128B）天然做「一店一码 + 渠道归因」；
4. 小店 H5/二维码支持带 `wecom_corp_id` + `wecom_user_id`，**成交可归因到企业/成员**；
5. 服务商模式下**可跨企业接入微信客服**（官方：可接入企业数暂无上限）。

**两条接入路径**：

| 路径 | 商户做什么 | 我们做什么 | 适用 |
|---|---|---|---|
| **第三方应用（推荐，可批量）** | 企微管理员扫码授权 | 拿 `corpId` + 永久授权码，代调用 | 规模化 |
| 自建应用（MVP） | 给 `corpId/secret/agentId` | 配回调、IP 白名单 | 1–2 家标杆 |

**边界（必须写进产品口径）**：
- 微信客服 **48h / 5 条**，只能被动接待；语音只给 `media_id`（需 ASR）；
- **平台小程序打不开商户的企微客服**（`wx.openCustomerServiceChat` 要求同主体绑定）；
- **企微好友私聊不能自动回复**（无官方 API）；「会话内容存档」需付费开通 + 员工/客户告知同意，**首版不做**；
- **个人微信**无官方 API，Hook/协议外挂违反规则，**明确不做**。

## 3. 抖音侧：三条通道互不相通，窗帘只能「线索 → 留资 → 站外成交」

> 一手来源：抖音开放平台、抖店规则中心、抖音生活服务开放平台，抓取 2026-11-25
> （抖音文档站为客户端渲染，用 headless Chrome 取正文；图片表格类信息一律列入 §8，不猜数字）。

**一句话**：抖音里「开店」和「放进抖音」是**三条互不相通的通道** —— 抖店（电商实物）、

**没有任何一条能整链路闭环**。

### 3.3 团购：有流量，但品类不咬合

- 生活服务官方重点行业是**餐饮、到综（休闲娱乐/丽人/足疗）、酒店、景区、度假、交通**；

  **不含家装/家居**。
- 团购的核销模型是「先买券 → 到店核销」，而窗帘是「先量尺 → 报价 → 生产 → 上门安装」，

  （「9.9 元上门量尺抵扣券」—— **类目是否可上架未核实**，§8.2 #5）。

| 载体 | 第三方可接入性 |
|---|---|
| **企业号私信（B2C IM）** | **已停止新增准入**（原文「私信能力已不支持新增准入，相关能力申请不用提单」）；当前仅「**线索投广商家**」；一个用户只能授权一个应用 |
| 抖音 IM 客服（小程序内） | 面向已上线企业主体小程序；官方 web 工作台，**无公开机器人 API** |
| 飞鸽（抖店客服） | 抖店自带智能客服；**商家对 AI 生成答案的夸大/虚假/错误承担全部责任**，须配人工与转人工 |
| 抖音来客 IM 客服 | 仅生活服务商家 |

**AI 客服的量化红线（2026-10-23 起，存量私信 ISV 专项治理，整改窗口 30 天）**：

| 指标 | 要求 |
|---|---|
| 15 秒首次响应率 | **≥75%** |
| 30 秒过程回复率 | **≥56%** |
| B/C 消息收发比 | **2–8** |
| 数据安全合规 | **100%** |

不达标 → **回收私信接口权限并清退**；线索转售/数据外泄 → **永久清退**。

⇒ **MIGAO 的抖音 AI 接待要按「能不能拿到准入」分两种现实**：
① 拿不到私信 API（大概率）→ 只能做「企业号官方自动回复 + 留资组件」+「小程序 IM 客服（人工/工作台）」，
米宝接不进去；② 拿到（存量 ISV/服务商）→ 必须把首响/过程回复/人机比做成可观测指标，否则被清退。

来源：[企业号 B2C IM/线索能力](https://developer.open-douyin.com/docs/resource/zh-CN/dop/ability/enterprise-account-open-ability/leads-b2c-im-ability)、
[公告页](https://developer.open-douyin.com/forum/bulletin)、
[飞鸽智能客服协议（意见征集）](https://school.jinritemai.com/doudian/web/articlev0/aJmtW2jCwsm3)。

### 3.5 支付：商户自己进件，SaaS 不得代收

- 小程序担保支付：**商户必须进件**，**分账方也必须进件**；平台先扣费项
  （技术服务费 + 本地生活软件服务费 + 达人佣金，各自独立计算后求和）再结算到商户/分账方现金户。
- 账期：**到店核销后 3 天** / 其他**支付后 7 天**。
- ⇒ SaaS **不能**「统一收款再分给商家」；正确模型 = **每商户自己进件，MIGAO 作为分账方或服务费收取方**。

来源：[结算规则、费率、周期](https://developer.open-douyin.com/docs/resource/zh-CN/mini-app/develop/server/payment/ecpay/settlements/rule-desc)、
[担保支付简介](https://developer.open-douyin.com/docs/resource/zh-CN/mini-app/open-capacity/guaranteed-payment/introduction)。

### 3.6 窗帘在抖音的最小可行链路

```
MVP（4 周，不依赖小程序备案）：
企业号 + POI（展厅）→ 短视频/直播挂 POI 或小程序 → 线索组件/私信留资
→ 线索进 MIGAO CRM → 米宝回访/报价 → 成交落抖店（标品/定制实物）或微信小店

第二阶段：
C2B 定制小程序（若类目批得下来）→ 量尺预约/定制信息提交 → 跳抖店成交
```

- **不要做**：抖音小程序内直接卖定制窗帘（500 元上限 + 类目邀约 + 禁止自闭环支付）。
- **不要承诺**：「抖音开店」不是卖点 —— 有赞旧版抖音点单小程序已被其官方手册判为下线，
  抖音自身也在 2026-10-08 收紧交易类目。
- **KPI 应是线索成本/到店率，不是 GMV**。

## 4. 对标差距：MIGAO 现在缺什么

| 能力 | 现状（2026-11-25） | 差距 | 最小改动 |
|---|---|---|---|
| **店铺页** | 顾客小程序只有 `chat / auth / profile` 三页 | **没有商品列表/详情/下单页** | 新增店铺页（商品列表 + 详情 + 算料报价 + 下单） |
| **渠道模型** | `tenant_apps` 只有 `wechat_mini / wechat_h5 / web` 三类，`UNIQUE(tenant_id, app_type)` | 没有「小店 appid / open_kfid / 抖音来客门店 / 抖店 shop_id」 | 新增 `tenant_channels`（渠道账号）表 |
| **微信小店** | 无 | 无授权、无商品同步、无订单回传 | 权限集 129–132 + 商品映射 + 订单回调 |
| **微信客服** | 无 `wechat_kf` 通道 | 无回调网关、无 `cursor` 持久化、无 5 条预算控制 | 新增 `wechat_kf` 适配器（回调 → 队列 → Agent → send_msg） |
| **抖音** | 无（代码里只有一处 `TenantAiConfig` 注释提及） | 无私信/团购/来客 | 新增 `douyin` 适配器（私信 + 券核销） |
| **入口归因** | 租户靠客户端传 `tenantId`（设计上要改子域名解析） | 无「一店一码/一场景一参」 | `store_entries` + 场景值/`scene_param` 解析 |
| **试用态** | 无 | 商户必须认证后才能看到店 | 样板店（`preview` 状态，不接支付） |
| **一证多店** | 无 | 每个经销商单独认证 | 总部主体授权表 + 子店继承 |
| **按单计费** | 无（SaaS 年费） | 无订单量计费 | 订单服务费 + 免费额度 |
| **服务商体系** | 无 | 无线下交付 | 城市服务商（量尺/安装/拍照） |

> 一句话：**「店铺入口」在我们这儿是从零起步，不是改造** —— 好消息是没有历史包袱，
> 坏消息是 C 端交易链路（商品 → 算料报价 → 下单 → 支付 → 履约）必须先补齐。

## 5. 推荐架构：渠道适配层 + 开店向导 + 入口服务

### 5.1 分层

```
┌─────────────────────────────────────────────────────────┐
│ 入口层（Entry）                                          │
│  小程序码 / 公众号菜单 / 微信客服链接 / 企微带参链接      │
│  抖音私信 / 团购券 / POI / 短视频挂载 / 抖店商品          │
│  统一：scene_key = tenant + channel + campaign           │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────┐
│ 渠道适配层（ChannelAdapter）                             │
│  authorize() / syncCatalog() / syncOrder() / sendMsg()   │
│  wechat_store · wechat_kf · wechat_mp · douyin_life ·    │
│  douyin_shop · douyin_mini · h5                          │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────┐
│ 领域层（复用现有）                                       │
│  商品/SKU 矩阵（颜色×门幅×售卖方式）· 算料报价 · 订单     │
│  客户档案 · 售后工单 · 物流 · 会话/消息                  │
└─────────────────────────────────────────────────────────┘
```

**三条主数据原则**（有赞踩过的坑）：
1. **商品/库存/价格以 MIGAO 为主**，渠道是「发布目标」；
2. **订单以渠道为主回传**（小店订单、团购券核销记录），避免两边同时维护互相覆盖；
3. **渠道下线不影响主流程**（适配器可摘除），任何「开店能力」不进核心架构。

### 5.2 表设计草案（最小集）

```sql
-- 渠道账号：一个租户在一个平台的一个店/号
CREATE TABLE tenant_channels (
  id            VARCHAR(64) PRIMARY KEY,
  tenant_id     BIGINT NOT NULL REFERENCES tenants(id),
  channel_code  VARCHAR(32) NOT NULL,   -- wechat_store|wechat_kf|wechat_mp|douyin_life|douyin_shop|douyin_mini
  external_id   VARCHAR(128),           -- 小店 appid / open_kfid / 来客门店 id / 抖店 shop_id
  credential    JSONB,                  -- authorizer_refresh_token / corp secret / client_key（加密）
  auth_status   VARCHAR(16) NOT NULL,   -- unbound|authorizing|active|expired|revoked
  category_snapshot JSONB,              -- 平台类目/资质快照
  UNIQUE(tenant_id, channel_code, external_id)
);

-- 店铺入口：一店一码 / 一场景一参
CREATE TABLE store_entries (
  id            VARCHAR(64) PRIMARY KEY,
  tenant_id     BIGINT NOT NULL,
  channel_id    VARCHAR(64) REFERENCES tenant_channels(id),
  entry_type    VARCHAR(16) NOT NULL,   -- qr|url_link|kf_link|poi|store_card|share
  scene_key     VARCHAR(64),            -- tenant:channel:campaign 的短码
  scene_param   VARCHAR(128),           -- 微信客服 ≤128B / 小程序码场景值
  target_path   VARCHAR(512),           -- 小程序 path 或 H5 落地页
  status        VARCHAR(16) DEFAULT 'active'
);

-- 渠道商品映射（MIGAO SKU ↔ 平台商品/SKU）
CREATE TABLE channel_skus (
  id, tenant_id, product_id, sku_id, channel_id,
  external_product_id, external_sku_id, sync_status, last_synced_at
);

-- 渠道订单回传（只存映射与状态，明细仍以渠道为准）
CREATE TABLE channel_orders (
  id, tenant_id, channel_id, external_order_id,
  migao_order_id, status, payload JSONB, synced_at
);

-- 开店向导（五灯）
CREATE TABLE onboarding_steps (
  tenant_id, step_code,   -- subject|catalog|pay|channel|first_order
  status, evidence, blocker, updated_at
);
```

### 5.3 开店向导：把「有赞七步」产品化成 5 个灯

| 灯 | 判据 | 红灯时的动作 |
|---|---|---|
| 主体 | 营业执照 + 法人已认证 | 跳转认证；支持「试用态」先看店 |
| 类目 | 家纺/居家布艺已开通 | 给类目清单 + 资质模板（阻燃/甲醛检测可选） |
| 收款 | 小店商户号已开通 | 引导开小店（自动开商户号） |
| 渠道 | 小程序已发布 / 小店已关联 / 客服已授权 | 一键授权 + 审核状态轮询 |
| 首单 | 有 1 笔真实订单 | 首单体检（商品打不开/不能支付/查不到订单 三段排查） |

> 有赞把这套做成文档里的「排查树」，我们应该做成**产品里的红绿灯** ——
> 把客服工单变成产品流程。

### 6.1 微信侧「商户 30 分钟开店」SOP（目标态）

| 步 | 商户做什么 | 平台做什么 | 失败点 / 兜底 |
|---|---|---|---|
| 1 | 上传营业执照 + 法人身份证（或先跳过，用**样板店**预览） | 主体校验、类目推荐（**家纺**优先） | 经营范围不匹配 → 给类目对照表 |
| 2 | 扫码授权：小店 + 微信客服 + （可选）公众号 | 授权回调、租户绑定、渠道状态置为 `active` | 授权超时 → 重发二维码 |
| 3 | 确认商品（从 MIGAO 商品库导出/映射） | 批量上架小店商品（权限集 129）、SKU 映射 | 类目/品牌资质缺失 → 给资质清单 |
| 4 | 生成「一店一码」（门店/建材市场/导购名片） | `store_entries` 落库，二维码带 `scene_param=tenant:channel:campaign` | 码失效 → 重新生成（永久码用 `getUnlimitedQRCode`） |
| 5 | 首单（自己或朋友下一单） | 订单回传、首单体检五灯全绿 | 支付失败 → 三段排查树 |

> 目标：**商户侧 30 分钟内可上线**，其中等待平台审核的时间用「样板店 + 店铺卡」兜住。

### 6.2 抖音侧「商户 30 分钟冷启动」SOP（目标态）

| 步 | 商户做什么 | 平台做什么 | 失败点 / 兜底 |
|---|---|---|---|
| 1 | 认证企业号（蓝 V） | 提供认证指引与行业资质清单 | 行业资质不匹配 → 换「家居装饰/生活服务」路径 |
| 2 | 绑定抖音来客门店（如做团购） | 来客授权、门店 POI 映射 | 类目未开放 → **降级为纯线索链路**（不依赖团购） |
| 3 | 发 3 条「窗帘效果」短视频 + 挂载 | 给脚本模板/素材规范（垂感、遮光、配色） | 挂载能力按类目审批 → 用个人页挂载兜底 |
| 4 | 私信/线索组件接待 | **拿不到私信 API（已停新增准入）→ 用企业号官方自动回复 + 线索组件**；拿到则配米宝，并按 15s 首响 ≥75% 等 4 指标监控 | 主动私信场景白名单 → 只做被动回复 + 订阅消息 |
| 5 | 团购券上架（可选） | 券码核销回传、对账 | 类目不允许 → 只做「留资 + 到店」 |

> 注意：抖音侧**不要以「米宝接入」为前置**。私信 API 已停止新增准入，先做
> 「官方工具 + 线索组件」也能跑通获客；AI 接入是拿到资质后的增强项。

## 7. 风险与合规

| 风险 | 说明 | 应对 |
|---|---|---|
| **二清** | 平台代收再结算给商户 = 红线 | 小店直收（钱进商户商户号）；要做统一收银只能用「平台收付通」 |
| **平台能力下线** | 有赞抖音点单小程序已下线 | 渠道适配器可摘除；不把「某平台开店」写进卖点 |
| **审核不可控** | 小程序审核约 7 个工作日；小店类目可能被打回 | 用「试用态」兜住等待期；承诺写「审核由平台决定」 |
| **UnionID 天花板** | 一个开放平台账号最多 20 个小店 | 身份主键退回 `openid + 手机号`；跨商户不识别同一人 |
| **客服额度** | 48h / 5 条；超限 `fail_type=6` | 回复合并（1–2 条）；长对话引导到小程序卡片；`fail_type` 打点 |
| **小店客服不可 ISV** | `commkf` 仅自研 | 产品口径写清「不接管小店原生咨询」；走微信客服 |
| **主数据冲突** | 多平台同时维护会互相覆盖 | 商品以 MIGAO 为主、订单以渠道为主 |
| **资质** | 窗帘可能涉及阻燃/甲醛检测 | 类目资质清单产品化（选类目 → 自动列出要传什么） |
| **定制类目账期** | 「定制家具」发货起 10 个月自动退款 | 引导到「家纺」类目；定制单走自有订单 + 线下收款 |

## 8. 待核实与冲突（不进结论）

### 8.1 已解决：`<store-product>` 的关联关系（更正底稿）

- 底稿 §3.2 写「商品卡/店铺卡/优惠券/订单详情**都不要求关联关系**」，并引官方
  「默认商品展示：不限制小程序和小店的关系」。
- **复核结论（2026-11-25，官方开发指南 + 组件文档）**：
  - `<store-product>` **要求**关联关系（基础库 **3.7.0** 起）；
  - `<store-home>`（3.5.5）/`<store-coupon>`（3.8.3）**不要求**；
  - `wx.openStoreOrderDetail` 不要求关联，但校验订单来源。
- 影响：**「一个平台小程序零配置展示任意商户商品卡」不成立**，必须逐户建关联
  （或降级用店铺卡/优惠券）。底稿的路径对比与 §10 链路 3 需按此修订。

### 8.2 仍需实测的项（附验证方法）

## 9. 战略选择：做「有赞」还是做「接入层」

### 9.1 两条路的真实成本差一个数量级

| 维度 | A. 有赞模式（帮企业开店） | B. 米宝接入层（不帮开店，帮接入） |
|---|---|---|
| **核心交付** | 商户的店（小程序/商城）+ 交易 + 运营工具 | 商户**已有店**上的 AI 客服 + 行业能力 |
| **必需资质** | 微信第三方平台 + 服务市场 ISV + 抖音服务商（生活服务代开发审核约 10 工作日）+ 可能 EDI | 微信客服第三方应用（或每户自建应用）+ 小程序客服权限集 19 |
| **工程范围** | 商品/订单/支付/售后/物流/装修/发布/审核/多端适配 | 会话/知识库/工具（查单、报价）/转人工/回调/沙箱/SDK |
| **运营** | 服务商体系、地推、7×24 审核跟进、代运营 | 技术支持 + SLA + 文档 |
| **时间（到能用）** | 12–18 个月 | **2–3 个月 MVP** |
| **收入** | 年费 + 按单 + 服务商分成 | 年费 + 会话量/坐席 + 行业包 |
| **主要风险** | 主体/资金/类目/审核不可控；帮开店溢价被平台免费化 | 平台客服额度（48h/5 条）；小店原生客服接不了 |

**结论：能做出有赞模式，但那是「另一家公司」的活**（牌照 + 地推 + 代运营 + 审核运营），
不是我们当前的最优解。微信小店已经把「开店」免费商品化（商户自己 1–3 天开完），
**「帮开店」的溢价会越来越薄**；而我们的护城河是**行业模型（算料/工艺/批次）+ AI**，
不是「帮人注册小店」。

### 9.2 推荐：B 为主，A 作为「轻陪跑」增值

```
主线 B：米宝接入层（标准接口）
  商户已有：小程序 / 微信小店 / 公众号 / 官网 / 自有系统
        ↓ 一条授权 / 一行 SDK / 一个 API
  米宝：行业知识 + 算料报价 + 查单 + 转人工（复用现有 LangGraph + 工具）

辅线 A'：开店陪跑（不碰主体、不碰资金）
  开店向导 + 商品导入模板 + 店铺装修模板 + 客服配置 + 首单陪跑
  按服务收费，不做代开发、不做代运营、不做代收
```

**关键判断**：「帮开店」不必等于「代开发小程序」。商户自己开小店（免费、1–3 天），
我们做「**接入 + 配置 + 陪跑**」，同样能收「开店服务费」，但**不背主体/审核/资金的锅**。

### 9.3 标准接口能力：分三层，让商户按能力选

| 层 | 形态 | 接入成本 | 适合 |
|---|---|---|---|
| **L1 零代码** | 微信客服授权（商户扫码）→ 米宝接管微信客服会话 | 5 分钟 | 绝大多数商户（默认） |
| **L2 低代码** | Web/H5 SDK（一行 JS）+ 小程序插件 | 30 分钟 | 有官网/独立站/自建小程序 |
| **L3 全量** | OpenAPI + Webhook（会话、消息、知识、订单只读、转人工） | 1–3 天 | 有研发能力的连锁/品牌 |

**OpenAPI 最小面**（草案）：

```
POST /open/v1/sessions              创建会话（external_user_id, channel, tenant）
POST /open/v1/messages              发消息（同步 / SSE 流式）
GET  /open/v1/messages              拉历史（cursor）
POST /open/v1/knowledge/documents   同步知识（商品/FAQ/政策/算料规则）
GET  /open/v1/orders/{order_no}     只读订单（商户授权数据源）
POST /open/v1/handoff               转人工（指定坐席/技能组）
Webhook: message.created / handoff.requested / order.synced
```

**接入体验的硬指标**：5 分钟拿沙箱 key → 30 分钟跑通「咨询 / 查单 / 转人工」→ 一键切生产；
HMAC 签名 + 幂等键 + 限流 + 回调重试；**租户隔离**（A 的 key 查不到 B 的数据）。

### 9.3.1 C 端入口迁移原则：客服做入口，小程序做承载

**不要「用客服替换小程序」，要「换主入口、留承载页」** —— 微信客服是对话通道，
**没有商品列表/详情/购物车/订单列表/支付页**；纯对话 + 5 条额度撑不起「浏览式选购」。

| 层 | 承载什么 | 形态 |
|---|---|---|
| **入口层（改为微信客服）** | 获客、接待、答疑、预约 | 客服链接/二维码、公众号菜单、小程序卡片、短信 |
| **承载层（保留小程序/H5）** | 商品详情、算料报价表单、订单/物流、售后 | 平台小程序页面（可被卡片打开）+ H5 兜底 |
| **交易层（微信小店）** | 下单、支付、退款、结算 | 小店原生页面（店铺卡/商品卡） |

迁移顺序：**双通道并行 → 灰度切入口 → 用数据决定小程序聊天页是否下线**；
小程序至少保留「详情 / 算料 / 订单 / 售后」四类页面（可由会话卡片跳入）。

### 9.4 90 天路线（B 为主）

| 周 | 交付 | 验收 |
|---|---|---|
| 1–2 | OpenAPI 3.1 spec + 沙箱 + API Key/HMAC + 限流 | 用 curl 跑通 3 个场景 |
| 3–4 | 微信客服第三方应用适配（回调/`sync_msg`/发送预算） | 1 家真实商户扫码授权，米宝接管会话 |
| 5–6 | Web SDK + 小程序客服权限集 19 | 官网嵌入一行 JS 可对话 |
| 7–8 | 知识同步 + 查单 + 转人工 | 商户上传商品/FAQ，AI 答对率抽样 ≥80% |
| 9–12 | 开店陪跑向导（轻）+ 2–3 家标杆 | 商户从注册到首条 AI 回复 <30 分钟 |

> 判据一句话：**商户不需要换店、不需要我们碰钱、不需要等审核，30 分钟内让米宝在他的店里说话。**

## 10. 只做企业智能客服：方案与路线（2026-11-25 定位裁定后）

### 10.1 边界：做什么 / 不做什么

| 做 | 不做 |
|---|---|
| 多渠道 AI 客服（**微信客服为主** + Web SDK + 商户自有小程序） | 店铺/商品列表/购物车/支付/订单页 |
| 行业知识库（商品、算料规则、售后政策、话术） | 微信小店/抖店代运营、帮开店（仅作付费陪跑） |
| 行业工具（算料报价、查单、售后受理、留资） | 平台代收/分账（二清） |
| 转人工 + 坐席工作台 + 会话质检 + 报表 | 个人微信 Hook/协议外挂 |

> 一句话：**商户不需要换店，我们也不碰交易；我们只让米宝在他的客服窗口里说话。**

### 10.2 三条通道（按优先级）

| 通道 | 角色 | 接入方式 | 客户门槛 |
|---|---|---|---|
| **微信客服（企微）** | **主入口** | 商户扫码授权第三方应用（或自建应用给 `corpId/secret`） | 点链接/扫码即聊，不加好友、不装 App |
| **Web/H5 SDK** | 官网/独立站 | 一行 JS + API Key | 打开网页即可 |
| 商户自有小程序 | 补充 | 权限集 19 / 小程序自研客服消息 | 在小程序内 |

抖音：**不做 AI 接管**（私信 API 已停止新增准入），只做线索组件/官方工具。

### 10.3 架构（渠道无关的会话内核）

```
入口（客服链接/二维码/公众号菜单/Web SDK/小程序）
        ↓
ChannelAdapter（wechat_kf · web · mini）  ← 授权、收消息、发消息、媒体
        ↓
Conversation Core（会话/消息/幂等/预算/转人工）
        ↓
Agent（LangGraph）+ Tools（知识检索、算料报价、查单、售后、留资）
        ↓
坐席工作台 / 质检 / 报表 / 知识运营
```

**关键设计**：
- **会话内核不认渠道**：`Conversation/Message` 与 `wechat_kf` 解耦，新增渠道只写 adapter；
- **预算账本**：`open_kfid + external_userid` 维度持久化 48h 窗口与 5 条计数，发送前扣减；
- **媒体统一**：入站 `media_id` → 下载 → Vision/ASR；出站图片先上传素材（3 天有效）；
- **身份**：`external_userid`（按企业隔离）→ `customer_profiles`，手机号做跨渠道主键。

### 10.5 8 周路线与验收

| 1–2 | 会话内核抽象 + `wechat_kf` adapter（回调/`sync_msg`/发送预算）+ 沙箱 | 用 curl/脚本跑通「收消息→米宝→发消息」 |

**硬验收**：扫码→首响 < 10s；5 条内完成「咨询 + 一张卡片」；重复事件只回一次；
订单查询与商户后台一致；断线重拉 3 天消息不丢；A 租户 key 查不到 B 的会话。

### 10.6 商业化（不碰交易）

- **SaaS 年费**（按坐席/客服账号数）+ **会话量包**（超出按条）；
- **行业包**（算料规则、售后政策模板、话术库）作为增值；
- **陪跑服务**（开店/装修/商品上架）单次收费，**不抽交易佣金**。

### 10.7 智能客服 ↔ 人工：官方状态机（这是微信客服的隐藏优势）

微信客服把「谁在接待」做成了**会话状态**，可用 API 查询与变更（`kf/service_state/get` / `trans`）：

| 状态 | 含义 | AI 能否发消息 | 可变更到 |
|---|---|---|---|
| **0 未处理** | 客户刚发消息，新会话 | ✅ | 1（AI）/ 2（排队）/ 3（指定人工） |
| **1 由智能助手接待** | AI 接待中 | ✅ | 2 / 3 |
| **2 待接入池排队中** | 等人工接入 | ❌ | 3 |
| **3 由人工接待** | 人工接待中 | ❌（API 发不出，天然防抢话） | 3（转交）/ 4（结束） |
| **4 已结束/未开始** | — | ❌ | **不可变更**；客户再发消息 → 0 |

**结论：AI → 人工可以随时切；人工 → AI 不能直接切回**（3 只能转人工或结束），
要等人工结束会话（4）后、客户再发消息（回到 0）时重新设为 1（AI）。
`trans` 在目标状态为 2/3/4 时会返回 `msg_code`，可用来给客户发「正在转接 / 会话已结束」的响应语。

**推荐策略（AI 优先 + 人工兜底）**：

```
新会话(0) → 自动置 1（AI 接待）→ send_msg
  ├─ 命中转人工：客户说「人工/投诉/退款」、情绪负面、连续 N 次答不上、涉金额/合同、客户要求
  │     → trans 3（指定坐席）或 2（排队），用 msg_code 发「正在为您转接人工」
  ├─ 非工作时间 / 无坐席：留在 1，AI 接待 + 留资，不转 2/3
  └─ 人工接待(3)：AI 静默（send_msg 不可用），sync_msg 仍记录；人工可结束(4)
客户再发消息 → 0 → 重新置 1（AI）
```

**前置条件**：接待人员必须在客服账号的接待人员列表里、且**已激活企业微信**（否则 `95014`）；
第三方应用传的 `servicer_userid` 是密文 `open_userid`。

来源：[变更会话状态](https://developer.work.weixin.qq.com/document/path/94669)、
[接收消息和事件（`session_status_change` / `servicer_status_change`）](https://developer.work.weixin.qq.com/document/path/94670)、
[接待人员管理](https://developer.work.weixin.qq.com/document/path/94662)。

### 10.8 人工介入时，AI 怎么保证不回复

**两层保障，缺一不可**：

| 层 | 机制 | 作用 |
|---|---|---|
| **平台硬约束** | `send_msg` 只在状态 **0/1** 可用；状态 2/3/4 调用会被接口拒绝 | 人工接管后**物理发不出去** |
| **我们软约束** | 发送前 gate + 事件驱动 + 二次确认 | 省 LLM 成本、省 5 条额度、避免「生成中被人接管」的竞态 |

**判定顺序（伪代码）**：

```
on_message(msg):
  st = session_state(open_kfid, external_userid)      # 本地表 + 事件更新
  if st not in (0, 1):                return SILENT   # 排队/人工/已结束
  if recent_human_msg(within = 90s):  return SILENT   # sync_msg 里 origin=5
  if human_assigned(servicer_userid): return SILENT
  reply = agent(msg)                                   # 只有通过 gate 才调 LLM
  if refresh_state() not in (0, 1):   return DROP     # 生成期间被接管 → 丢弃
  send(reply)                                          # 失败 → 落 pending，转人工
```

**三个判定信号**：
1. **状态事件**：`session_status_change`（`new_servicer_userid` 非空 → 人工）；
2. **人工消息**：`sync_msg` 的 `origin=5` = 接待人员在企业微信客户端发的消息（带 `servicer_userid`）；
3. **本地状态表**：`open_kfid + external_userid → state/servicer`，事件驱动更新，查询优先读本地。

**兜底原则：fail-closed** —— 状态查不到/接口报错/未知，一律**不发**，落「待人工」队列。

**验收**：人工接管后 AI 发送 **0 条**（含「AI 正在生成时被接管」的并发场景）；
人工回复后 AI 不再插话；人工结束 + 客户新消息 → AI 恢复；状态未知 → 不发。

来源：[变更会话状态](https://developer.work.weixin.qq.com/document/path/94669)、
[接收消息和事件（`origin` 3/4/5、`session_status_change`）](https://developer.work.weixin.qq.com/document/path/94670)。

#### 10.8.1 怎么判定「人工介入结束了」

权威信号是 `session_status_change` 事件的 **`change_type`**（均为接待人员在企微客户端操作触发）：

| change_type | 含义 | 是否算「人工结束」 | 附带字段 |
|---|---|---|---|
| 1 | 从接待池接入会话（人工接入） | ❌ | `new_servicer_userid`、`msg_code` |
| 2 | 转接会话（人工 → 另一人工） | ❌ **不是结束** | `old_` + `new_servicer_userid` |
| **3** | **结束会话** | ✅ **是** | `old_servicer_userid`、`msg_code`（可发结束语） |
| 4 | 重新接入已结束/已转接会话（人工又在已结束会话里发消息） | ❌ **是「重新开始」** | `old_` + `new_servicer_userid` |

**四个判定信号，按可信度排序**：

1. **`change_type=3`（结束会话）** —— 最权威，立即把会话置 `closed`、记录 `close_reason=human_end`；
2. **`service_state/get` 返回 4** —— 对账用（事件丢失时兜底）；
3. **48h 无消息** —— 会话自然过期（`send_msg` 会报 `fail_type=4`），本地 TTL 兜底置 `closed`；
4. **客户发新消息 → 状态变 0** —— 这是「AI 可以恢复」的信号，不是结束信号。

**两个必须避开的误判**：
- `change_type=2`（转接）**不是结束** —— 只是换了个人，AI 仍然不能发；
- `change_type=4`（重新接入）说明**人工又回来了** —— 不能因为状态曾是 4 就恢复 AI。

**AI 什么时候恢复**（可配置策略）：

| 策略 | 行为 | 适用 |
|---|---|---|
| `auto_ai` | 客户新消息进入状态 0 后，立即置 1 由 AI 接待 | 默认 |
| `cool_down(N)` | 人工结束后 N 分钟内客户再发，仍转人工（同一问题未解决） | 投诉/售后场景 |
| `manual` | 结束后不自动恢复，等人工或客户明确要求 | 大客户 / VIP |

**数据模型**：`kf_sessions(open_kfid, external_userid, state, servicer_userid, started_at, closed_at, close_reason, msg_count)`；
`close_reason ∈ {human_end, api_end, expired_48h}`，供质检/CSAT/坐席绩效使用。

来源：[会话状态变更事件 · change_type](https://developer.work.weixin.qq.com/document/path/94670)、
[变更会话状态](https://developer.work.weixin.qq.com/document/path/94669)。

### 10.9 AI 介入判定（Intervention Policy）：不是「能不能发」，是「该不该 AI 接」

平台状态机解决的是**发送权限**；这一层解决的是**介入决策**。两者独立，策略层可单测、可回放、可配置。

#### 10.9.1 四层 gate（从硬到软）

| 层 | 判什么 | 失败动作 |
|---|---|---|
| **L0 硬约束**（不可协商） | 状态 ∈ {0,1}、48h 内、5 条未用完、主体已验证、非黑名单 | 不发 / 转待处理 |
| **L1 会话上下文** | 人工最近发言时间、是否刚被接管/刚结束、当前轮次、历史转人工次数 | 静默等待 |
| **L2 语义与风险** | 意图、情绪、涉钱/合同/投诉/法律、是否明确要人工、知识置信度 | 转人工 / 先澄清 / 加护栏回复 |
| **L3 策略** | 租户配置：模式（shadow/suggest/auto）、阈值、时段、VIP 规则 | 按配置降级 |

#### 10.9.2 决策枚举（不要只有「回/不回」）

| 决策 | 含义 | 典型触发 |
|---|---|---|
| `AI_REPLY` | AI 直接回复 | 常规咨询、报价、查单 |
| `AI_REPLY_GUARDED` | 回复但加护栏（免责/需确认） | 报价区间、时效承诺、定制可行性 |
| `ASK_CLARIFY` | 先澄清再答（不调用工具） | 信息不足、多意图混杂 |
| `SILENT_WAIT` | 静默观察，不回复 | 人工 10 分钟内说过话、AI 刚被接管 |
| `HANDOFF_QUEUE` | 转人工排队 | 人工忙、非紧急 |
| `HANDOFF_AGENT` | 转指定坐席 | 投诉、退款、大客户、明确要求人工 |
| `BLOCK` | 不回复 + 告警 | 广告、骚扰、违规内容 |

#### 10.9.3 判定信号（规则 + LLM 混合）

| 信号 | 来源 | 用法 |
|---|---|---|
| **人工活跃度** | `sync_msg` `origin=5`、`session_status_change` | 人工 N 秒内说过话 → `SILENT_WAIT` |
| **情绪** | LLM/词典 | 负面/愤怒 ≥ 阈值 → 转人工 |
| **风险** | 规则（涉钱/合同/退款/赔偿/法律/媒体）+ LLM | 命中 → 转人工或加护栏 |
| **明确要人工** | 规则（「人工/投诉/找你们领导/退款」） | 立即 `HANDOFF_AGENT` |
| **知识置信度** | 检索得分 / 工具返回 | 低于阈值 → `ASK_CLARIFY` 或转人工 |
| **客户价值** | 客户档案（VIP/大客户/欠款） | 高价值 → 优先人工 |
| **会话轮次** | 本地计数 | 连续 3 轮未解决 → 转人工 |
| **时段/坐席在线** | 租户配置 + 坐席状态 | 非工作时间 → AI 接待 + 留资 |

> 原则：**规则管硬边界（毫秒级、可解释），LLM 管语义（低温度、JSON 输出、超时兜底）**。
> 不要用 LLM 判「能不能发」——那是状态机的活；LLM 只判「该不该接、接了怎么说」。

#### 10.9.4 判定输出必须可解释

每次决策落一条 `intervention_decisions`：

```
conversation_id, message_id, decision, scores{risk, emotion, confidence},
rule_id, model_version, reason, latency_ms, created_at
```

用途：① 审计（为什么没回/为什么转人工）；② 回放调参；③ 与人工真实处理对比（shadow 模式）。

#### 10.9.5 三种运行模式（灰度必备）

| 模式 | 行为 | 用途 |
|---|---|---|
| **shadow** | 只判定、不发送，记录「本会怎么判」 | 冷启动对比人工，调阈值 |
| **suggest** | 生成草稿给坐席，人工点发送 | 高风险行业/新商户 |
| **auto** | 直接发送 | 成熟商户 |

#### 10.9.6 验收指标

- **抢话率 = 0**（人工接待时 AI 发送条数）；
- **误转人工率**（本可 AI 解决却转了）< 10%；
- **漏转人工率**（该转没转）< 3%；
- **静默误判**（该回没回）< 2%；
- 判定耗时 P95：规则 < 50ms、含 LLM < 800ms；
- shadow 模式与人工判断一致率 ≥ 85% 后再切 `suggest`。

来源：本层为 MIGAO 自研策略，无外部依赖；信号来源见 §10.7/§10.8。

### 10.10 前置条件：商户必须有自己的企业微信（附开通时长）

**是硬前提，且不能由平台代持**：微信客服是企微的产品，客服链接、会话、客户关系都归属**商户主体**；
用我们的企微代替 = 客户在跟平台聊，不是跟商户聊。

| 条件 | 说明 | 谁做 |
|---|---|---|
| 企业微信已注册 | 免费、在线，营业执照 + 管理员微信 | 商户（5–10 分钟） |
| **企业微信已认证（主体验证）** | 未验证主体发消息会 `fail_type=8` | 商户（**1–3 个工作日**，官方口径：支付后收到派单起） |
| 微信客服已开通 | 企微后台 → 微信客服，认证后即时开通 | 商户（1 分钟） |
| 客服账号 + 接待人员 | 接待人员须激活企微 App（否则 `95014`） | 商户（10 分钟） |
| 授权我们的第三方应用 | 管理员扫码 | 商户（1 分钟） |

**时间账**：

| 商户状态 | 到「米宝能接待」的耗时 |
|---|---|
| **已有认证企微** | **约 30 分钟**（开微信客服 + 建账号 + 授权） |
| 未注册企微 | **1–3 天**（卡在认证审核；资料不齐会延长） |
| 认证被驳回（名称/资料不符） | 再 +1–3 天 |

**降低门槛的四招**：
1. **先查有没有企微**——布艺/窗帘商家不少已经在用，直接授权；
2. **认证等待期先用 Web SDK**（官网/H5）把 AI 跑起来，认证后再切微信客服；
3. **开户向导 + 材料清单**（营业执照、法人身份证、对公账户、企业名称须与执照一致）；
4. **「认证中」状态可见**：onboarding 五灯里单独一盏，避免商户以为卡死。

**没有企微的商户**：备选通道 = Web/H5 SDK、商户自有小程序客服（权限集 19 / 自研）、
公众号客服消息（需认证服务号）——体验都弱于微信客服（要进小程序/关注公众号/加好友）。

来源：[企业微信认证审核说明](https://open.work.weixin.qq.com/help2/pc/19735)、
[认证审核时间（官方 FAQ：1–3 个工作日）](https://kf.qq.com/touch/apifaq/160415F3mmYV1604153QfIvu.html)、
[注册企业微信](https://open.work.weixin.qq.com/help2/pc/15422)。
