# 窗帘生产与计件规则清单（生产模块真值来源）

> 标注：【标】= 行业标准值（可直接编码为默认常量）；【默】= 经验默认值（需商家可配置）。
> 来源：2026-09 客户提供的行业 ERP 系统截图（堡达/壁达软件管理系统 5.40.0 加工单/工序维护/订单录入）+ 客户逐项确认。
> 与 [curtain-fabric-quote-rules.md](curtain-fabric-quote-rules.md) 配套：算料/报价口径见该文档，本文件管生产/工序/计件/物流。

## 1. 订单 → 加工单

- 【标】已确认（含加工项）订单生成加工单，可**一套一单或一单多套**（第 N 套/共 M 套，工程单按楼层/项目拆套）。
- 【默】**两套编号**：内部加工单 ID 与对外单号（日期+流水，如 `CSO260915-02615`，打印给车间）。
- 【标】加工单**打印物含二维码**（单号+套号+部位，token 化、可撤销、记录打印次数）——二维码是扫码报工的入口。
  - **形态与粒度（用户裁定，2026-09-21）**：打印物 = **洗水码**；
    **按部位（= 商品行）出码 —— 一个商品一张纸**（加工单有 3 个商品 ⇒ 打 3 张、生成 3 个二维码，各自对应本商品那套工序）。
    理由（用户逐字）：「当前生产环节都是按单个商品工序去生产」「工人扫码更新生产状态&计件也是按各套工序分别操作和推动的」。
  - **纸型与版式（用户裁定 2026-09-21，issue #4964 —— 改判 #4946 的 60mm × 30mm 横向；
    🔴 纸宽再改判：用户 2026-09-26 逐字「洗水码宽是50，长度根据我们实际需要来定」⇒ issue #5646
    把纸宽 30mm 改成 **50mm**，长度 60mm 经实测确认保留）**：
    **竖版 50mm × 60mm、单列**，照**真实工单**（亿家纺织「成品定制」58mm 竖排小票：单号/客户/第N套共M套/宽高/加工方式/用料表/备注/QR）的信息顺序。
    理由（用户逐字）：「这是加工单的实际打印的洗水码，参考这个来设计吧，我们现在的有问题」。
    实测依据：横向双列把纸面切成「左约 41mm 文字 + 右 17mm 码列」，左列**只用了一半高度**（实测 10.15mm / 19.89mm）
    而文字四处被截断（交期 `2026-09-…`、色号、工序只印 3 道）⇒ 是**版式切错**，不是纸小。
  - **字段面（用户 2026-09-21 字段裁定）**：加工单号 / 客户 / 第 N 套 · 共 M 套 / 部位 / 件名 / 色号 /
    **用料米数** / **成品宽高** / **加工方式**（工艺 · 加工类型 · 打开方式 · 定型）/ 订单号 / 交期 /
    **备注**（特殊选项 + 快照备注）/ **算料公式** + 二维码与**大字**人可读短码。
    其中色号 / 用料 / 加工方式 / 算料公式的**取值一律走** `frontend/admin-web/src/lib/craft-display.ts`
    的单一真值（§4.9「一份 spec，三处渲染」），纸面不另写一份推导。
  - **退场两项（同一次字段裁定未选，勿"顺手加回"）**：**工序摘要**（工人扫部位码后在 H5 看该部位工序清单，纸面不印）
    与**完整套号**（与加工单号重复，纯占纸面）。
  - **纸面高度预算**（🔴 **issue #5646 在 50mm 新几何下重新实测 —— 30mm 时代的 27.6mm 版心 / 17 行上限 / `@page size: 30mm 60mm` 全部作废**）：
    60mm − 上下各 1.2mm ⇒ 可用 **57.6mm**；6pt / 行高 1.2 ⇒ **每行 2.538mm**；版心（宽）= 50 − 2×1.2 = **47.599mm**；
    二维码行 45px = **11.906mm**。最坏构成（长件名 2 行 + 备注 2 行 + 算料公式 2 行 + 色号 + 其余单行）⇒ 正文总高
    **56.337mm ≤ 60mm**（保守上界 —— 加工方式也折满 2 行 —— 为 58.878mm）；标签长度逐值扫描（50…62mm）给出
    「中部文字块不被裁」的最小值 **57mm**（56mm 实测被裁 0.265mm）⇒ 取 **60mm**。
    随之重算的字段折行预算：**件名不再 clamp**（旧 2 行妥协退场）、加工方式 `line-clamp-2`（仅预算上界，实测 1 行）、
    备注 `line-clamp-2`、**算料公式 2 行**（旧 3 行口径退场；容量 2×22.5em = 45em > 旧 3×13em = 39em，是容量迁移不是放宽）。
    底部「二维码 + 短码」行必须 `shrink-0` —— 空间不够时**只裁补充文字**，绝不裁码与短码：
    短码是设计里明写的**手输降级入口**（`docs/design/worker-h5-scan-and-report.md` §1.4「不是可选项」），
    #4949 实测过一次它被裁 1.25mm。
  - **码的内容** = `https://<稳定域名>/s/<短码>`（**唯一形态** —— 只有 URL 能让任意扫一扫工具可用）；
    短链的稳定性红线与 302 重定向见 `docs/design/worker-h5-scan-and-report.md` §1.2 / §1.3。
- 【标】部位行字段：部位(布帘/纱帘/帘头) · 类型 · 型号(货号-色号) · 批号 · 单价 · 用料 · 褶数 · 幅数 · 折扣 · 小计；下单行另有：宽 · 高 · 工艺(韩褶/打孔/四爪钩/穿杆) · 打开方式(单开/双开/三开/四开…) · 加工类型(定高买宽|定宽买高) · 是否定型 · 货号 · 总褶数 · 褶距 · 理论褶倍/实际褶倍 · 是否对花。
- 【默】**特殊选项清单**（下单勾选，影响用料/工序/计件系数）：余料带回-布、余料带回-纱、布绑带、纱绑带、加logo条、加立边、加花边、拼1/2/3次、加铅块、接高、双眼皮接高、扣环、抱枕、防翘扣、一分为二、余料做绑带、余料做帘头。
  - ⚠️ **选项名 = 行业 ERP 订单录入页的逐字写法**（issue #4389，用户裁定 R-e「以 ERP 为准改」，2026-09-19）。
    它是「订单选配 → 车间工序 / 计件系数」的 **join key** —— 错一个字 ⇒ 查不到 ⇒ 条件工序不加、
    计件系数静默退回 1.0（**少发工人钱**）。本清单此前的写法（`一分二`、`余料带回(布)/(纱)`）
    是同一批选项的**旧拼法**，已作废，不得再写回。
  - ERP 截图里「余料带回」另有**第三种形态** `余料带回`（无后缀），**不在**上列 19 项里 ⇒
    归属（加工序 / 加系数 / 不计件）**待客户确认**；代码侧已显式登记在
    `app/production/routing.py::PENDING_CUSTOMER_CONFIRMATION_OPTIONS`（既不是「忘了映射」，
    也不假装已定论）。
- 【默】保证金机制：保证金余额 / 保证金使用 / 本次收款 / 收款备注（定金制，配合企业收款二维码）。

## 2. 工序库

- 【标】**工序分组**：`裁剪 / 车位 / 后道 / 其他`（不是按阶段，是车间工位分组）。
- 【标】**工序按部位分设**：同一道工序在布/纱/帘头上单价各自不同（韩褶-布、韩褶-纱…）。
- 【默】工序属性：名称、工序分组、单位（米/套/件/个）、排序、部位、距离交期天（排期用）、计件单价（版本化）、特殊选项系数。
- 【标】工序开关：**标记生产开始**（首工序报满 ⇒ **加工单**进入生产中，见下）、完成时打印水洗标/条码标签/余料用途标签（外贸标签等）、车间电视大屏是否显示。
  - 🔴 **「标记生产开始」的落地对象 = 加工单，不是订单**（2026-09-26 收口，issue #4695；用户裁定「落 D13」）。逐字口径：
    **首工序**（该加工单里 `is_start_marker = TRUE` 的那道工序实例）**报满**（`done_qty ≥ qty`）⇒ 该加工单
    `issued → in_processing` + 落 `processing_orders.in_processing_at`。
    - **走状态机**：合法性取自加工单状态机（
      `backend/admin-api/src/main/java/com/migao/admin/service/ProcessingOrderService.java` 的 `STATUS_TRANSITIONS`），
      落库走条件更新（谓词 = 本次被状态机授权的那一个起始态），**不裸 UPDATE 绕过**
      （#4117 的教训：绕过状态机 ⇒ 订单既发不了货也回不去）。
    - **幂等**：重复报工 / 重报 / 并发报工**只转一次**，且**不改写**首次开工时刻（`COALESCE`）。
    - **`generated` 不得直达** `in_processing`（状态机只允许 `generated → issued`）⇒ 尚未「发加工」的单
      **不动它**，仍需先发加工或走手工端点 —— 这一半**尚未裁定**（A6），本次按**保守读法**实现（不直达）；
      登记见 `docs/design/set-code-and-scan-loop.md` 的 §8 A6。`cancelled` / `completed` 同理不动。
    - **手工端点保留**：`ProcessingOrderService.updateStatus` 的 `action = "start"` 仍是同一条迁移的
      **手工入口**（存量单补开工 / 自动路径不适用的兜底：单里没有任何 `is_start_marker` 工序、首工序报工时
      该单尚未发加工、或首工序早在自动路径上线前就报满了）。已是 `in_processing` 时它照旧被状态机拒
      —— 两条路径**同一个目标态、同一张状态机**，不是两套口径。
    - **自动路径的边界（有意，都有兜底 —— 不是缺口被忘掉）**：① **不追溯存量单** —— 首工序在本次上线
      **之前**就已报满的在产单**不会被回溯转态**（本单零迁移、零回填；猜一个历史开工时刻比留空更糟）
      ⇒ 这类单走手工端点补开工；② **单里没有任何 `is_start_marker` 工序**（商家自编路线 / 工序库改过）
      ⇒ 自动路径**不触发**（该单保持 `issued`），**不回落**成「按 `seq` 最小推一道」——
      触发器就是那道标记工序，这是 D13 的定义（实测种子：`精裁-布` / `精裁-纱` 是标记工序，
      三条纱帘路线也都以 `精裁-纱` 起头）。
  - 🔴 **订单侧的时点已改判**（issue #4305，用户裁定）：**发加工是订单 `confirmed → producing` 的唯一时点**
    （生成加工单不再推进订单）⇒ 本行原写的「（首工序触发**订单**进入生产中）」**已作废**。
    ⚠️ 历史口径（防假真值回填）：该括注源自 2026-09 客户 ERP 截图口径（把「标记生产开始」理解成**订单级**事件）；
    #4305 把订单级时点收窄到「发加工」，#4695 再把「标记生产开始」落到**加工单级**（上一条）。**不得**按旧口径写回。
  - 🔴 **本条随 issue #4961 改判**（2026-09-21）：原写的「**此工序必须完成才可打包**（完工门槛）」
    这个开关**已退场**。口径来源 = **用户裁定（逐字）**：「**完工 = 全部工序全绿**」⇒ 加工单完工判据 =
    **全部**活跃工序实例完成（`done_qty ≥ qty`），不再有「必完工序全绿」这一档。
    落码：列 `production_operations.is_must_finish` **保留为历史载体**（值恒 `FALSE`，存量行由
    `backend/admin-api/src/main/resources/db/migration/V107__retire_must_finish_flag.sql` 收敛）；
    写面（`POST` / `PUT` `/api/admin/production/operations`）收到该字段一律 **422 + 可行动 hint**；
    读面键**保留但恒 `false` / `null`**（冻结键集，不破既有消费者）。

## 3. 工艺路线（布帘·韩褶，行业实证 11 道）

```
精裁-布 → 布三边 → 韩褶-布 → 上车布-布 → 熨烫-布 → 定型-布 → 复烫-布 → 布帘车被 → 外帘打卷 → 外帘装袋 → 外帘发货
```

- 【默】其他工艺路线按 部位 × 工艺 实例化（韩褶/打孔/四爪钩/穿杆/纱帘/帘头/罗马帘），**条件工序按特殊选项插入**（拼N次→拼-布、加花边→花边工序、定型=是→定型-布等）。
- 【默】工序实例的**应做数量 = 算料引擎输出**（褶数/孔数/用料米数/幅数），报工只确认，不手工心算。

## 4. 计件（工资计算）

- 【标】**计件工资 = Σ(报工数量 × 工序单价)**；**单工序一人制**（2026-09 客户确认，无计件人数分摊）。
- 【默】数量口径结构化（非公式字符串）：用料米数 / 成品宽 / 成品高 / 褶数 / 孔数 / 幅数 / 套数 / 固定值；条件系数表：特殊选项 → 工序 → 系数（如 一分为二 ×1.7）。
- 【默】**「个 / 件」类单位的应做数量 = 兜底 1（是兜底口径，不是真值）**（2026-09-25 用户裁定，关联 #4228 · 关联 #5496）：
  上一行的清单里**没有**「个 / 件」的数量定义（§2 只把「个 / 件」列进**单位取值域**：`单位（米/套/件/个）`）
  ⇒ 引擎**不产出**该数量 ⇒ 工序实例的**应做数量一律兜底 1**，与「缺键 / 非正数（显式 0 与负数）一律兜底 1」
  同一条红线（**绝不落 0**：0 ⇒ `done_qty ≥ qty` 恒真 ⇒ 工序一开工就算完成 = **假完工**）。
  🔴 **禁止**回落到「按米读 `fabric_meters`」：那会把 12.3 米的单算成「帘头制作 应做 **12.3 个**」
  （改前实测，issue #4228 ①）—— 数量口径按单位**二分且穷尽**，**没有第三条路**。
  代码侧登记表 = `backend/ai-agent-service/app/production/routing.py` 的 `FIXED_ONE_UNITS = ("个", "件")`
  （引擎不产出 ⇒ 兜底 1）vs `KNOWN_QTY_UNITS`（引擎有口径 ⇒ 读对应键）；未登记单位**一律红**
  （判据 = `backend/ai-agent-service/tests/test_production/test_operation_qty_unit_fallback.py` 的
  `TestUnitRegistrationCensus` 与 `TestTruthSourceRegistration`）。
  **现取读数**（2026-09-25 现取；**数字由登记面判据钉住 ⇒ 腐烂即红**，不是可以随手写死的值）：
  `unit=个` **5** 道 / `unit=件` **0** 道（工序库种子 `OPERATION_CATALOG`；真库 = SQL
  `select unit, count(*) from production_operations where coalesce(deleted,0)=0 group by unit order by 2 desc;`）。
  ⚠️ **真值仍缺**：一「个」到底算多少（一幅成品帘头？一只抱枕？）本仓无从判定 ⇒ 待业务/客户给出后补进
  上一行清单，并把该单位迁进 `KNOWN_QTY_UNITS`、给 `_qty_keys_for_unit` 补候选键（登记表是唯一改动点）。
- 【默】单价 = 工序 × 部位定价，**版本化**（调价只影响新报工，历史报工按当时价，逐笔可追溯）。
- 【标】**两套账分离**：内部计件（per 工序，给工人）vs 对外加工费（per_meter 按米打包含辅料，收顾客，issue #3005）——互不污染。
- 【默】工资报表 = 报工事件聚合（按人/按期/按单下钻：报工 → 工序实例 → 部位 → 套 → 加工单 → 订单）。

## 5. 扫码报工闭环（核心流程）

```
打印加工单（含二维码）→ 工人扫码 → 工人端显示本部位待做工序（含应做数量）
  → 点「完成」报工（人/工序/数量/时间）→ 工序条推进 + 计件金额累计
  → 全部工序完成后 → **加工单**自动置「生产完成」（completed）→ 订单进入「已发货」等后续态
```

> 🔴 **本条随 issue #4961 改判**（2026-09-21，口径来源 = **用户裁定（逐字）**：「**完工 = 全部工序全绿**」）：
> 改前那一行写的是「全部『必须完成才可打包』工序完成后 → **订单**自动进入『生产完成』态」——
> 两处都已过期（**#4117 起**第 ② 处就过期了，本次一并改判）：
> ① **门槛集合不再存在**（#4961）：「必完工序」概念整体退场 ⇒ 判据 = **全部**活跃工序实例完成
>    （`done_qty ≥ qty`），与 `is_must_finish` 无关；只要还有**任何**一道没做完就不算完工
>    （含此前**不参与**判定的非必完工序）。
> ② **完工落在加工单，不是订单**（#4117）：「生产完成」= `processing_orders.status = 'completed'`
>    （活跃态条件更新 + `completed_at`），**订单保持 `producing`** —— 订单状态机没有
>    `producing → completed`（`completed` 是终态），直写订单会让含加工项的订单**既发不了货也回不去**。
> 真值源落点（两侧**同口径**，分叉即错）：Python `backend/ai-agent-service/app/production/piecework.py`
> 的 `is_production_done`，Java `backend/admin-api/src/main/java/com/migao/admin/service/ProductionService.java`
> 的 `allInstancesDone`（同一份数量口径 `done_qty ≥ qty`，Java 侧不新造第二份）。

- 【标】防呆：幂等（重复扫提示已报）、越站提示（非本工序）、数量上限校验（≤应做数量+合理损耗）、非本部位码提示。
- 【标】一次扫码同时干两件事：**推进工序进度 + 记录个人计件**。
- 【默】弱网降级：扫码页缓存待做清单，离线报工补传。
- 【标】操作记录 = 报工明细（实证：`蒋雪云-定型 11.00`、`李红梅-韩褶 11.00`… 带时间戳）。
- 【标】**报工明细去重不靠 DB 唯一约束**（边界登记，issue #4845）：`production_work_logs` **全库零 UNIQUE**（建表迁移只有两条**非唯一**索引，`backend/admin-api/src/main/resources/db/migration/V49__create_production_operations_and_work_logs.sql`；全库迁移 + `docs/sql/schema.sql` 对该表无任何唯一索引/约束）—— **这是有意的**：**分段完成**（同一工序两次合法提交之和 = 应做数量）本来就是**合法的多行**，加唯一约束会把合法写入判死。⇒ 幂等/去重**全靠应用层判据**（三道判据的落点、红证与复算命令见 `docs/design/set-code-and-scan-loop.md` §5.3.2）。

## 6. 物流（客户常用物流/快递）

- 【默】**物流类型枚举**：`express`（快递：顺丰/圆通/中通等）/ `logistics`（物流/专线：四季安等）。POC 客户更多选择物流专线。
- 【默】**客户常用物流档案**：客户基本固定选同一家承运商，下单/加工单自动带出、可改。
- 【默】订单/加工单字段：货运方式（类型+承运商）、货运单号；发货动作 = 录入货运单号 → 订单进入已发货，C 端查物流（customer_logistics_track）只查本人已发货订单。

## 7. 客户工艺画像（客户记忆，2026-09 客户强调）

- 【默】客户级工艺偏好档案：`craft_mode ∈ { standard 跟随企业固定工艺算料 / economy 主动省料 / self_quoted 自报用料 }`，连带 开数/定型/档位/物流 等默认值。
- 【默】来源：AI 在报价协商中自动学习（客户自报用料 → 标记 self_quoted）＋ 商家可手动标注；报价时按画像出默认方案并标注「按您上次的习惯」，可改。
- 【标】不同客户差异化：有些客户愿遵守企业固定工艺算料，有些懂工艺的主动报省料方案——由商家裁定最终档位（权限+留痕）。

## 8. 术语表（AI 词汇底座，跨模块统一）

| 术语 | 含义 |
|---|---|
| 打开方式 | **开数（正整数）**：单开（一片）/ 双开·对开（两片）/ **三开（三片）** / 四开（四片）…—— **不是固定枚举**（`V64` / issue #4387/#4430）；对开总褶数为偶数 |
| 部位 / 帘种 | 布帘 / 纱帘 / 帘头 —— **工序路线的索引键**；「外帘」是加工单打印行部位，**不是**路线键。⚠️ **2026-09-21 事实订正（两条，方向相反，别混读）**：① **取价 / 矩阵**那一侧的「部位维」已整体退场（issue #4937 / #4951，母单 #4936）—— 价目表按**一道逻辑工序一行**收敛（`production_operation_positions.position` 恒 `通用`，**不再是配置概念**）；② **「适用条件」（条件工序规则）**那一侧的**规则级**部位限定**加回**（issue #4962，用户裁定「如果有一些工序只能布帘有或者纱帘有，可以在适用条件上设置」）—— `production_route_rules.position` 为空 = 不限部位，否则**逐字**匹配当前部位（26 条种子里只有 `韩褶 → insert 上车布` 一条 = `布帘`）。⇒ 「部位」仍是**实例化输入**（订单行 `curtain_type` / 加工单 `position_name` 照旧），但**不再**索引价目矩阵 |
| 部件 / 明细行 | 主布 / **配布边** / 纱 / 加工项 / 加工费（报价与加工单的**明细行粒度**） |
| 加工类型 | 定高买宽（买宽度米数）/ 定宽买高（按门幅幅数×高度）。🔴 **2026-09-21 改判（用户裁定，issue #5030）**：订单行 `width` = **净窗宽**、`height` = **净窗高** ⇒ **成品宽 = 净窗宽、成品高 = 净窗高**（无任何覆盖 / 离地 / 轨道换算）—— 故**宽方向没有余量**（`用料 = 窗宽 × 褶倍`；常量与配置键 `side_margin`、概念「左右覆盖余量」**整体退场**），**高方向仍用上下卷边 `HEM_MARGIN`**（脚位+止口，超高判据与定宽买高每幅长用它）。公式真值源 = `docs/curtain-fabric-quote-rules.md` §3 |
| 定型 | 部位级开关：打褶后蒸烫固定褶形；联动价格/工序/计件/质检/包装 |
| 款式 | 单色 / 拼色（拼色 = 主布+配布分料、按折加价） |
| **工艺 / 安装工艺** | 打褶或悬挂方式，**单值**，取值须与 `production_routings.craft` **逐字一致**：`韩褶`（口语 韩式褶/S钩/调节钩）/ `打孔`（口语 罗马圈/眼环/纳米圈）/ `穿杆`（口语 穿管）/ `平幔`（= 罗马帘）/ `四爪钩`（见下行：口语说法指向主线 `韩褶`）。**顾客/商家的口语说法必须先译成这里的内部值再落库**（issue #4454）——落原话（如「韩式褶」「纳米圈」）会让工序路线取不到、加工单与计件工资全错 |
| **四爪钩 / 四叉钩** | **加工项（配件）**，不是打褶方式：口语「四爪钩 / 四叉钩 / 普通挂钩」指向**主线工艺 `韩褶`**（V63 起不再作独立路线键，见 §3 注）；「要不要穿钩」由加工项携带。⚠️ 存量路线 `布帘×四爪钩` 原样保留（存量加工单要能回溯），**新单不得再把它当工艺维度写** |

| 精裁 | 裁剪工序（含裁床输出），布/纱分设（精裁-布/精裁-纱） |

| 工艺价 | 对外加工费单价（元/米，含辅料打包） |
| 特殊选项 | 下单勾选、影响用料/工序/计件系数的选项集合（§1 清单 19 项） |

| **接高** | 面料高度不足时接一段补高；按**明细行**归属（主布接高 / 配布边接高）。🔴 **2026-09-22 改判（用户裁定，母单 #5200）**：缺口**上限 0.1 米**、且**不参与算料**（不另买布、不改米数）；**只出现在「定高买宽」**（高方向受门幅约束）。旧口径「缺口多大都行 + 加高条按片宽另买布」**退役** |
