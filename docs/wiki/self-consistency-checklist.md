# 功能自洽性检查清单（闭环谓词）

> 来源：issue #2968 · 复盘 PR #2966（加工项「适用商品分类」无消费方，#2964）
> 定位：**CRUD 闭环 ≠ 业务闭环**。本文档把「功能不自洽」分解为可判定的谓词，
> 分三档：P0 可全自动（确定性脚本）/ P1 半自动（脚本定位 + 人工确认）/ P2 语义审查（不可算法化）。
> 用途：① 写检查前对照「该问题的谓词是哪一档、能否脚本化」；② 审计工具覆盖缺口；③ 指导自动化落地顺序。

## 0. 触发案例（为什么要有这份清单）

加工项「适用的商品分类」（`processing_items.applicable_product_categories`）五段链路：

| 环节 | 状态 | 自洽观感 |
|---|---|---|
| 表单写入（admin-web 加工项页） | ✅ | 校验/保存正常 |
| DB 存储（JSONB 列 + 迁移） | ✅ | 结构完整 |
| API 返回（Response DTO 透传） | ✅ | 契约在 |
| 编辑弹窗回显 | ✅ | 能勾选回填 |
| **消费方（谁用它推荐/筛选/展示）** | ❌ | **归零** |

- 单独看每一段都「自洽」，测试也全绿（CRUD 测试齐全）→ 形成功能完整的假象。
- 真实缺口只在「**数据生命周期：被创建 → 被消费**」视角下可见。
- 该案例同时命中三档谓词：**P0 死数据字段**（可脚本化）+ **P1 设计意图无落点**（设计文档 §6.1.1 写明「适用商品分类 + AI展示」）/ **P2 流程连接语义**（该关联应被哪些下游消费的判断）。

## 1. P0 可全自动（确定性脚本，可进 CI）

| # | 谓词 | 判定条件 | 现有工具 | 实现成本 | 实例 |
|---|---|---|---|---|---|

| P0-2 | **三端枚举漂移** | 同一语义枚举 Java/Python/TS 值集不一致 | contract-check.sh 已覆盖订单/售后状态，其余枚举为缺口 | 低（扩展词表） | 订单状态 producing/processing（历史统一，#2613 域） |
| P0-3 | **文档-代码状态漂移** | wiki/DB 文档记录的枚举 ≠ 代码真值 | truths.py（case truths_ref）部分覆盖 | 低 | CONTRACT-LEDGER 状态枚举 |

| P0-5 | **schema 列无映射** | DB 列既无实体字段也无任何代码引用 | 无 | 中（schema.sql vs entity/lambda 引用对比） | — |

| P0-7 | **测试弱断言/假绿** | 断言不含目标值、恒真断言 | growth_gate.py `--check-weak`（仅扫新增测试） | 已覆盖 | — |

## 2. P1 半自动（脚本定位 + 人工/AI 确认）

| # | 谓词 | 判定条件 | 定位手段 | 确认手段 | 实例 |
|---|---|---|---|---|---|
| P1-1 | **prompt 规则 vs 工具能力** | prompt 要求的行为（interact 选择/展示字段）工具返回数据不支持 | 扫描 prompt 中「展示/选择/推荐」动词 → 对齐工具输出字段 | 人工读工具返回样例 | product_skill prompt 要求 interact 但 tool_names 无（agent-clarification-capability-research.md G6）；PR #2966 前 prompt 问「需要加工项」但数据不带适用分类 |
| P1-2 | **设计文档意图无落点** | 设计文档意图词（推荐/AI展示/多选/自动计算）在实现中无消费方 | 意图词索引（docs/design/ 16 篇）→ 全仓 grep | 人工确认 | admin-dashboard-design.md §6.1.1「适用商品分类 + AI展示」vs 仅 CRUD（PR #2966 前） |
| P1-3 | **前端读取字段 vs 后端返回** | TS 类型声明的字段不存在于实际响应 | TS 类型字段集 vs 契约快照字段集 diff | 人工复核误报 | — |

## 3. P2 语义审查（不可算法化，需专项深挖）

| # | 谓词 | 内容 | 触发时机 | 实例 |
|---|---|---|---|---|
| P2-1 | **业务计算口径** | 金额/计价/费用计算自洽（含/不含、口径统一） | 涉及金额改动必审 | 下单漏加工费（#2613）；订单列表含加工项筛选恒空——子查询投影漏 processing_info（#2615）；采购明细漏加工费展示（#2916） |
| P2-2 | **状态机完整性** | 状态流转合法性、前置条件、跳转 | 状态枚举改动 | 订单状态机跳转（pending→completed 等） |
| P2-3 | **多轮交互协议** | choice 翻页/多选/一次性提交、prompt 与前端组件协议一致 | 交互组件/prompt 改动 | 加工项多选只取第一个（#2894）；翻页后选择丢失 + 二次询问（#2896） |
| P2-4 | **行业合规** | GB/T 47746-2026 写操作确认闸 | 新增写操作 | 写 Tool 必须 validate_input + confirm 卡 |
| P2-5 | **环境假设** | 本地/CI/生产行为差异 | 环境相关改动 | 云库泄漏进单测（#2957）；Taro dotenv 白屏（#2693）；部署后验证端点到非（nginx 404 是预期） |
| P2-6 | **流程连接语义** | 配置字段应被哪些下游消费（业务判断，本次核心） | 跨模块改动 / 新配置字段 | 适用商品分类 → AI 按分类推荐加工项 |

## 4. 现有工具覆盖映射

| 工具 | 覆盖 | 缺口 |
|---|---|---|
| contract-check.sh（6 项） | P0-2（部分枚举）、端点存在性、payload 蛇形 | 其余枚举、参数级契约 |
| growth_gate.py | P0-7（case_ids/覆盖/弱断言，仅新增测试） | 存量测试弱断言不扫 |
| render_cases.py + truths.py | P0-3（cases 单一源 → 生成物同步） | 业务层不自洽不覆盖 |
| test_tool_schema_consistency.py | P0-8（write tool 参数→payload） | 只覆盖写工具，read tool 输出字段不做消费方校验 |
| 契约快照（tests/contracts/snapshots/） | P0-4 响应保真 | 不校验调用方引用 |
| check-ui-regression.sh | UI token 回退（专项模式） | 只查 neutral token 关键文件 |

**现状**：P0 8 项中已覆盖 2 项（P0-7/P0-8）+ 部分覆盖 3 项（P0-2/P0-3/P0-4）；P1/P2 全部靠人工。本次加工项案例中「死数据字段」（P0-1）与「意图无落点」（P1-2）在自动化后本可在 PR 前被检出。

## 5. 落地路径（Phase，按投入产出排序）

1. **Phase 1 · P0-1 死数据字段扫描**（性价比最高）：schema.sql 枚举列 → 全仓引用索引（Java/Python/TS/prompt）→ 输出「写+读存在但消费=0」疑似清单 → 人工复核后打「死数据」标签或补消费方。为避免误报，先只扫「配置类」表（categories/processing_items/settings 等），业务主表（orders/order_items）后续。
2. **Phase 2 · P0 扩展**：P0-2 枚举词表扩展、P0-4 消费方引用 diff、P0-6 迁移对比，挂 contract-check.sh，进 CI（合并前必跑）。
3. **Phase 3 · P1 意图扫描**：设计文档意图词索引 + prompt 工具能力对账，输出半自动报告。
4. **P2 沉淀为专项**：不改算法，改为「跨模块改动 review 模板」+ 每双周自洽性专项（带着本文档 P2 表逐项过）。

## 6. 触发时机建议

| 时机 | 执行 |
|---|---|
| 每次跨模块改动 | P0-1（新增字段时）+ P0-2/3（枚举/文档同步）+ P2-1（涉及金额） |
| 每个 PR | contract-check.sh / growth_gate（现有）+ Phase 2 后 P0 全量 |
| 每双周 / 大版本 | P1 意图扫描 + P2 专项审查 |

## 7. 与本项目既有红线的衔接

- `tdd-iron-law` §1 QA Gate、`migao-dev-flow` §2 三把工具：本文档 P0 项落地后可挂到同一提交前命令链。
- 新「配置类字段」验收红线（建议）：新增字段必须显式回答「谁消费它」，写进 PR 描述；消费方=0 的字段不得合入（本文档 P0-1 是其自动检验）。
