# 领域建模规范（防 ERP 化）

> **这是什么**：本仓**数据库与领域模型**该怎么长的规范 + 三条机械判据。
> 与 [Code-Minimalism](Code-Minimalism.md) 的分工：那份管**代码**写得少，本份管**模型**长得慢。
> 触发场景：新增表 / 新增列 / 新增状态 / 新增 JSONB 字段之前；以及看 `db/init/schema.sql` 觉得"哪里不对"的时候。

## 为什么要有这一页

用户的判断（2026-10-20，逐字）：「传统 ERP 软件就是堆积各种单据，最后显得臃肿庞大，
一个单据几十几百个字段，领域建模很弱，我们的项目如何规避这种情况」。

臃肿的根因不是「单据多」，是三个**演进方式**：

1. **把单据当表** —— 数据库直接承担纸质台账的字段（打印抬头、审核人、统计项），于是列数跟着表单长；
2. **加列式演进** —— 新需求 = 加一列，因为加列最便宜；十年后 300 列，每一列都「有存在理由」；
3. **用布尔堆状态** —— `status` / `follow_status` / `is_x` / `x_at` 并存，每来一个场景加一个。

三者共同点是：**没有任何东西会因此变红**。所以本页除了纪律，还配了会红的判据。

**实测基线**（`backend/admin-api/src/main/resources/db/init/schema.sql`，2026-10-20）：
**84 张表 / 1140 列 / 平均 13.6 列**；最宽 42（`customer_profiles`）；**孤儿列 0**；JSONB 48 列。
形状是健康的 —— 但已经有**两处**在往 ERP 的方向走（§二）。

## 一、六条纪律

### 1. 事实 / 派生 / 视图 三分

- **事实**落库：窄行、以追加为主、尽量不可变（订单行、批次、事件时间）。
- **派生**（毛利、RFM 分、应收余额、缺料需求）**不手填**：要么现算，要么物化成「可重算」的快照。
- **视图**（列表列、表单字段、打印模板、导入模板）是 **DTO 投影**，永不反推成数据库列。

> 判据问句：**「这个值能不能由别的数据算出来？」** 能 ⇒ 不入库，或入库时必须是「物化 + 重算命令」。

### 2. 一表 = 一个聚合，一张单据 ≠ 一个聚合

一张单据的**界面**可以由 3 个聚合拼成，但**不共享一张宽表**。
> 判据问句：**「这些字段会一起变吗？」** 不会 ⇒ 它们不属于同一个聚合。

### 3. 扩展点，不是扩展列

行业标准属性写**列**（可索引 / 可约束 / 可聚合）；客户与场景的定制写 **JSONB**，且必须
**登记 + 有校验归属**（`custom_fields` 是正确先例，`schema_health_ledger.json` 的 `jsonb_columns` 是登记面）。

> 判据问句：**「这属性要排序 / 聚合 / 唯一约束吗？」** 要 ⇒ 列；不要 ⇒ JSONB。
> 反模式：为了「不加列」把所有东西塞进一个 JSON 桶 —— 那只是把「300 列」换成「200 个没人知道含义的 key」。

### 4. 状态机单一真值

每张单据一份「枚举 + 合法迁移表」，状态只能通过**一个迁移函数**改；
`is_x` 布尔一律改由状态派生；`_at` 是**事件时间**，只由迁移写入。
反例已清：`orders.payment_status`（V126 删除）—— 与 `paid_at` 并存就是双真值。

### 5. 投影层隔离（最关键的一条）

页面字段 = **投影字段**，不是表字段。本仓的 `dto/*Response` 结构天然支持这一点，要当成**硬约束**：
禁止宽 SQL 直映射实体、禁止前端表单字段直接对应列名。

> 这是 ERP 臃肿的**第一病因**：页面字段 = 表字段 ⇒ 改一次界面就是一次迁移。

### 6. 准入判据（PR 面）

新增表 / 列时，PR body 写**三行**：**领域归属 / 维护的不变量 / 读面（谁读）**。
机械面（会红）：

| 判据 | 载体 | 红形态 |
|---|---|---|
| 单表列预算 ≤ 30 | `tests/unit_ci_workflows/test_schema_health_guards.py` + `schema_health_ledger.json` | 超限且未登记 / 台账宽度失真（增宽或已收窄未删条目） |
| 孤儿列零增长 | 同上（生产代码语料，`snake_case` 与 `camelCase` 都算引用） | 出现无人读写的列 / 台账里的死列已被引用却没缩短 |
| JSONB 必须登记 | 同上 | 新增 JSONB 未进台账 / 台账陈旧 |

## 二、我们现在真实的两处漂移（具名，不是假设）

**① `customer_profiles`（42 列）= 四类对象挤一张表**
微信身份（`wechat_*`）+ RFM 派生快照（`r_score` / `f_score` / `m_score` / `total_*` / `repurchase_rate`）
+ 默认收货地址（`default_receiver_*`）+ 工艺偏好（`craft_mode` / `craft_profile`）。
收敛方向：身份 → `user_identities`；默认地址 → 地址簿实体；RFM → 物化快照表；`craft_*` → 版本化 JSONB。
**未排期**（台账 `column_overrides` 已具名登记，收敛后必须删除该条目）。

**② `order_items`（28 列）= 订单行 + 窗帘工艺参数**
`fullness` / `pleat_spacing` / `pleat_count` / `has_pattern` / `corner` / `cutting_mode` / `is_shaped` …
—— **每新增一种工艺就加一列**，这是最危险的演化路径。
领域本质是：**产品 = SKU + 工艺配置 + 算料输入**。工艺是**可扩展集合**，不是固定列集
⇒ 收敛为一个 `item_config`（JSONB + schema 版本），只把高频可检索/参与计价的字段留作列。

## 三、什么时候**才**该新增一种单据（正判据）

同时满足下面**三条中的至少两条**才新增实体：

1. 有**新的不变量集合**（如「采购承诺价」必须被约束）；
2. 有**新的责任主体或时点**（谁签字、何时生效）；
3. 需要**独立生命周期与编号**（能单独作废、单独审批、单独对账）。

否则它只是现有实体的一个 **source 值 / 一类事件 / 一个投影**。
正面例子（本仓做对了，别改回去）：**没有「采购单」**，入库单只记 `source = purchase | opening` ——
在没有「先下单、后收货、价格承诺、审批」之前，它不是实体。

## 四、三个健康指标（复算命令，不写死数字）

```bash
# ① 表数 / 列数 / 最宽表
python3 - <<'PY'
import re
s=open('backend/admin-api/src/main/resources/db/init/schema.sql',encoding='utf-8').read()
blocks=re.findall(r'CREATE TABLE(?: IF NOT EXISTS)?\s+"?([\w]+)"?\s*\((.*?)\n\);', s, re.S)
print('tables', len(blocks))
# 列数按行首标识符近似，精确值以 test_schema_health_guards 的解析器为准
PY
# ② 三个判据（含注入式红证）
python3 -m pytest tests/unit_ci_workflows/test_schema_health_guards.py -q
```

| 指标 | 观测 | ERP 病征阈值 |
|---|---|---|
| 平均列宽 / 最宽表 | 13.6 / 42 | > 25 / > 60 |
| 孤儿列 | 0 | 持续增长 |
| **新增列 ÷ 新增表**（季度） | 现取 | > 3 ⇒ 正在「加列式演进」 |

## 五、与既有规范的关系

## 六、边界（照实登记）

- **判不了设计判断**：本页给的是**形态**（列宽 / 孤儿 / JSONB 无主）与**问句**（会一起变吗 / 能算出来吗），
  不是「这个字段该不该存在」的自动判定。后者仍是评审。
- **列预算单位是聚合**：合法宽表（路由版本快照等）可走台账例外，但必须写**收敛计划**，且**只许缩短**。
- **孤儿列语料是冻结清单**（`test_schema_health_guards.py` 的 `CORPUS_ROOTS`）：新增服务目录要同 PR 加进语料，
  否则会假红 —— 这是有意的 fail-closed 方向。
- 本页**不新增 required check**；判据跑在既有 `ci workflow helper unit tests` 腿里。
