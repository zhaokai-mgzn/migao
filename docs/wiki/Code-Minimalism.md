# 最少代码规范（ponytail 集成版）

> 来源：开源技能 [ponytail](https://github.com/DietrichGebert/ponytail)（"懒惰资深工程师"，The best code is the code you never wrote）。
> 本页是它在米高项目里的**调和版：只简化实现代码，不降测试门禁**。背景调研见工作区根目录 `ponytail-开源仓库调研.md`。

## 一句话

最好的代码是你根本没写的那行。写码前爬**最少代码阶梯**，停在第一个成立的台阶；懒在方案，不懒在理解。

## 阶梯（先理解，再爬梯）

写任何代码前，先完整读懂任务与被改代码、追踪真实流程；然后停在第一个成立的台阶：

1. 需要存在吗？→ 不需要就跳过（YAGNI）
2. 代码库已有？→ 复用，不重写
3. 标准库已做？→ 用它
4. 平台原生特性覆盖？→ 用它
5. 已装依赖能解决？→ 用它
6. 一行够？→ 写一行
7. 都不行 → 写最小可行实现

## 规则

- 不加未被要求的抽象、依赖、样板代码；删除优先于添加，平庸优先于炫技，文件数最少
- 最短可行 diff 胜出，但**先理解再动手**——最小改动放错位置不是懒，是第二个 bug
- 修 bug 修根因：grep 全部调用方，一次修共享函数；只补 ticket 点名的那条路径 = 兄弟调用方继续坏
- 质疑复杂需求：「你真的需要 X，还是 Y 就够了？」
- 故意砍真实角落（全局锁 / O(n²) / 朴素启发式）时打 `ponytail:` 注释，写明已知上限与升级路径
- 两个 stdlib 方案同规模时，选边界正确的那个——最简 ≠ 更脆的算法

## 与米高铁律的边界（本页最重要的调和）

- **只简化代码，不降测试**：QA Growth Gate（case_ids、按变更类型的测试要求、覆盖率）、TDD 红绿循环、E2E「结果可见」断言、写操作 confirm 守卫、契约检查全部照旧。ponytail 原版「非平凡逻辑留一个自检即可」在本项目仅作**最低兜底**，米高有更高要求时按米高执行
- **顺序**：先爬梯定「最小该写什么」→ 再按 TDD 写失败测试 → 最小实现 → 绿
- **安全护栏永不砍**：信任边界校验、防数据丢失、安全、无障碍、合规（GB/T 47746-2026）与明确要求的东西，不在阶梯上
- **不得破坏既有结构**：复用/删减不违反 docs/wiki/Architecture.md 与 CONTRACT-LEDGER.md 定义的架构分层与契约；阶梯管实现代码，不管架构决策
