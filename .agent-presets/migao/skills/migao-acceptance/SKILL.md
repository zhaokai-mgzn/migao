# MIGAO 可执行验收（acceptance）

## 何时必须加载

- 要下任何**「验收通过 / 评测 OK / 交付完成 / 已达标」**结论之前；
- 需方要求**验收 agent 会话 / 功能交付 / 修复回归**；
- **写或改评测 case（cases/*.yml）/ 验收场景**时（保证断言可执行，不制造"看起来有覆盖"）；
- 评测/验收 agent 期间**创建了真实会话**（它们留在系统里，就是被测物）。

## 铁律（违反任一条 = 本次验收无效，必须重做）

1. **不自我验收**：开发者 ≠ 验收者。验收要换独立视角（用户视角 + 复核 agent 留下的会话），
   禁止用自己写的场景、自己的话术、自己的判定标准给自己盖章。
2. **可执行断言 + 红证**：关键行为（必须/禁止/金额/时序/内容）**禁止只写进自然语义 data_checks**——
   那是不计分的"看起来有覆盖"。必须是 L1 机器可判断言，或 L2/UA 带证据引用。
   每条断言还要有**红证**：一个负向夹具（把被测行为改坏 / 喂一条错误轨迹）证明**它会红**。
   真值与被测行为无关的断言是**空断言**——最常见是**永远不会红**（花通过率买"看起来测过了"），
   也有一半是**永远不会绿**（期望与真实链路对不上 → 恒不满足，同样什么都没测）。
3. **判定必须引证据**：每条通过/问题都要给出 `R<轮次> / 事件 / 原文片段`，无引用 = 无判定。
4. **UA 用户代理判定（替代旧"L3 待人工"）**：话术可懂度/表达自然等体验类判定，**由 AI
   扮演用户代理完成**——① 声明扮演 persona（如"低学历顾客"）② 判定必须引用原文
   ③ 对照可懂度基准（短句/给例子/给出口/不编造）逐条给分。**通过线（#3492 双裁判试点
   校准）**：信息准确 + 给出口 + 不编造即通过；密度/长度/风格列为观察项（不阻塞），
   禁止为"短句"字面把合格话术判红。**禁止把验收点写成"待人工"**。
5. **修复必须重放**：修复后必须重跑同一验收剧本，交 before/after 成对证据；没有重放 = 没修复。
6. **复核自己留下的会话**：验收范围必须包含 agent 在开发/评测期间创建的真实会话——
   以产品视角打开看（历史/卡片态/生命周期），这是 2026-09-08 翻车的直接原因。
7. **零人工执行**：验收流程任何步骤不得依赖人执行（AI Native 原则）；人的角色仅剩
   标准定义与对双 AI 不一致的裁定（仲裁），且都不算验收执行动作。

## 假绿 / 假红：断言自身会双向骗人（v1.2 新增，2026-09-15 实证）

评测集**红了不等于行为坏了，绿了更不等于行为对了**。一次实战里 12 个"问题"中 11 个属
**断言自身的缺陷**，且全部是确定性、零 LLM 可判的：

| 类 | 形态 | 实证 |
|---|---|---|
| **假红** | 断言实现**窄于**用例声明 | 用例声明「文本询问亦可」，runner 文本分支却要求字面「加工项」三字 → 合格行为判红 |
| **空断言**（双向） | 真值与被测行为**无关** | **恒绿**：散文 `data_checks` 不计分；`db_verify` 按 keyword 取首条 → 被同名种子商品顶替；声明了该工具没有的 `action` → 整条**静默跳过**；同轮取错 payload。**恒红**：期望的工具与**真实链路对不上**（期望 `product_detail`，agent 实际调 `product_search`）→ 恒不满足 |
| **同轮不精确** | 同名工具的**别的 action** 顶替 | `must_succeed[action=X]` 统计该轮全部同名工具结果 → 别的 action 成功也算过 |

**治法（能下层不上层，migao-dev-flow §16.1）**：

1. **红证**（L0，零 LLM，最优先）：每个断言核对器配一个负向夹具 → 没有红证的断言在 CI 阻塞；
2. **声明层静态一致**（L0）：声明的 `action` / `fetch` / args 键必须存在于该工具 schema 或已注册 fetcher；
3. **失败可归因**（L1）：summary 带「case × 轮次 × 断言」级判定 —— 否则 `score=0` 无从定位
   （实证：一条 reproducible 失败因缺逐断言判定而长期无法归因）；
4. **LLM 只覆盖语义残留**：UA 判定、证据复核、以及**用例语义审计**（"这条断言真在测它声称的东西吗"）。
   ⚠️ **空断言在第二个模型眼里同样是绿的** —— 换更强的裁判**解决不了** 1~3，别把 GLM 复核当主防线。

**写/改断言时的完成判据**：把被测行为改坏，**它会红吗**？按真实链路喂一遍，**它会绿吗**？
两问都答不上来 = 这条断言还没写完（只答得上第一问 = 可能恒红）。

## 假红形态：「基线快照晚于被测事件」（v1.5 新增，2026-09-14 实证）

**同一件事可以用两种完全不同的写法都假红 —— 错误是同一个：基线快照取晚了。**

实证：小程序 e2e 的「AI 第二条回复」断言，连续两版都假红，根因同一个：

| 写法 | 为什么假红 |
|---|---|
| 比较**文本** `aiReply2 !== prevAiText` | `prevAiText` 快照取在**发送之后** ⇒ 快照到的"旧文本"**就是**新回复本身 |
| 比较**数量** `assistantCount > prevAiCount` | 助手气泡在**流式一开始就被创建**（TypingIndicator 靠它显示）；`prevAiCount` 取在"用户气泡上屏之后" ⇒ 新气泡**可能已经建好** ⇒ 数量永不增加 |

两次假红的**表象完全不同**（一个比文本、一个比数量），**根因完全相同**。
⇒ **判据**：任何"等新增 / 等变化"的断言，**基线必须在触发动作之前取**；取完再断言「非空 ∧ ≠ 基线」。

**为什么单列**：它证明"**换个判据写法不构成修复**" —— 没找到"基线取晚了"这个共同根因，下一版仍会假红；
而每次假红都会让人去查错方向（本次为一条假红先后查了后端 502 与流式超时，全是无效功）。
配套教训：**修复假红后必须重放**（本次正是被坚持要求的重放抓出来的）。

## 空跑：绿了但没跑（v1.3 新增，同一会话三次实证）

**先核「它真的跑了吗」，再读它的结论。** 三类"看起来跑过了"——都发生在**评测链路自身**，不在用例断言里：

| 形态 | 实证（2026-09-14/15） |
|---|---|
| **验了陈旧产物** | 小程序 e2e 驱动的 `dist/` 是 **10 天前**的构建（输入条早已重设计）→ 旧脚本配旧构建**自洽地绿**；重建后才暴露真问题 |
| **失败不可归因** | 结论档 `eval-summary-*.json` 每个用例只有 `id/score/classification`，**无失败原因** →「6 条确定性失败」只是一个 ID 列表，只能手工挖 2705 行日志 |
| **静默空转** | 手动触发的评测被抑制：**每个评测步骤 `skipped`、artifact 为 0、整体却 `success`**（注释还写着"永不抑制"，据此漏掉了 `force_eval` 逃生口） |

**核对动作（引用任何 run 的结论前，三条都要过）**：

1. **步骤级** —— 真正干活的那一步（`Run <persona> …` / `判定（completion_verdict…）`）结论**不是 `skipped`**；
2. **产物级** —— artifact **存在且能读出 verdict**（`gh api …/actions/runs/<id>/artifacts` 非 0；summary JSON 可解析）；
3. **新鲜度** —— 产物对应的源码/构建**就是当前版本**（如 e2e 前先核 `dist` 不比 `src` 旧）。

⇒ 三条**任一不满足 = 本 run 不构成结论**，不得引用、更不得据此下"已验证"。
一句话：**「绿」是 run 的状态，「跑过」才是证据。**

## 假绿形态：重放未复现缺陷的前置条件（v1.7 新增，2026-09-15 实证）

**run 真跑了、也真绿了，但缺陷的「前置条件」不在 ⇒ 被修复的那条路径根本没被行使。「绿」≠「测到了」。**

**实证（PR #3746，更正评论 `#issuecomment-5665464912`）**：该 PR 修 OR-014「改价不落 SKU」——
`product_update(price=X)` 只写**商品级** `products.base_price`，**SKU 级** `product_skus.price` 留旧价；
而**下单取价的权威来源是 SKU 级**（`OrderService.validateAgentItemUnitPrice`：
`List<ProductSku> skus = productSkuMapper.selectList(...)` @ `OrderService.java:1639`
→ `BigDecimal authoritative = skus.get(0).getPrice();` @ **`:1650`**
→ 与请求单价不一致即拒 @ `:1654-1656`）
⇒ 客户按旧价成交。主会话随后用 `case_ids=OR-014,AS-004` 重放（run `34853616766`）**绿了**，
并据此写下「缺陷已修复」—— **该结论对 OR-014 过强**：

| run | 用途 | OR-014 的 R1 trace 读到的 `price` | 说明 |
|---|---|---|---|
| `34849029334` | 结论档（**红**） | **`198.0`** | PR-010「把价格改成 198」已改**商品级**、SKU 仍 168 ⇒ 栈内**存在分叉态** |
| `34853616766` | 修复后重放（**绿**） | **`168.0`** | 该 `case_ids` 把**制造分叉的 PR-010 排除在外** ⇒ 栈内**无分叉态**（读到的是**种子原值**） |

⇒ 商品库**没有分叉**，该 PR 新增的分支（`ProductService.java:433`
`} else if (request.getBasePrice() != null) {` → 把价同步到 SKU @ `:445-449`）**在那次运行里从未被触发**；
那次绿只证明「**干净栈上 OR-014 通过**」，**不构成对修复的判别性验证**。

**判据（写重放结论前必须回答的两问）**：

1. **本次运行是否复现了缺陷的前置条件？** 必须给出**前置条件的观测值** ——
   本例是 OR-014 的 R1 trace 里 `price` 的读数：**`198.0` 才说明分叉态存在**（`168.0` = 无分叉）；
2. **若未复现 ⇒ 该次绿不构成判别性验证**：必须**如实标注**（不得写成「已修复」），并以
   **确定性层证据**兜底 —— 本例是 `ProductServiceTest#updateProduct_BasePriceSyncsToSkus`
   （`ProductServiceTest.java:559`）：**改前** `Wanted but not invoked: productSkuMapper.update(...)`
   （改价从不落 SKU，即分叉本体）→ **改后** `Tests run: 80, Failures: 0`
   （两个读数为 PR #3746 更正评论记录的改前/改后结果）；确定性层与 LLM 方差、调度顺序**无关**。

**与既有形态的区分（三者判据互不替代）**：

| 形态 | 特征 |
|---|---|
| 空跑（v1.3） | **根本没跑**（步骤 `skipped` / artifact 0 / 整体却 `success`） |
| 陈旧产物（v1.4） | 跑了，但跑的是**旧构建**（产物与「被断言的那一刻」不一致） |
| **本节（v1.7）** | **跑了、也绿了，但缺陷的「前置条件」不在 ⇒ 修复路径未被行使** |

**操作口径**：用 `case_ids` 收窄重放时**必须一并问**：
**「这条缺陷的前置条件由谁制造？那条用例在这次选择里吗？」**
凡「缺陷由**另一条用例的行为**制造」（如本例的商品级 / SKU 级改价分叉，或任何需要先跑某条前置用例的场景），
漏掉它就会得到一次**无判别力的绿**。补充做法：把前置用例放回**同一条腿**
（如 `case_ids=OR-014,PR-010,AS-004`；PR-010 带 `full_lifecycle` / `id_reuse` 标签 ⇒ runner 的
`_needs_serial_lane` 判其走**串行独占道**，不与 OR-014 重叠，见 `tests/agent_eval/local_runner.py`
的 `_needs_serial_lane`（当前 main `:4939`，分流点 `:4959-4960` —— **行号随文件增长会漂移，按函数名检索**）），
并**以前置条件的观测值**（本例 `price=198.0`）作为判别性证据的判据。

## 证据层假绿：证据自己会骗人（v1.4 新增，2026-09-14 实证）

**断言绿 + 产物存在 ≠ 证据可信** —— 产物本身可能与**被断言的那一刻**不一致：

| 形态 | 实证 | 治法 |
|---|---|---|
| **过渡帧 / 滞后帧** | 小程序 `mp.screenshot()` 抓到过渡帧：run1 的 `chat/03` 与 `chat/04` **字节完全相同** → 截图与此刻断言的 DOM 状态对不上（点发送后连抓 3 帧各不同，**3~4.5s 才稳定**） | 截图/快照/导出物**连抓直到连续两帧一致**才算稳定帧；引用前核哈希（修复后 `03≠04` 已验） |
| **陈旧产物** | e2e 驱动 **10 天前**的 `dist` → 旧脚本配旧构建**自洽地绿**；重建后才暴露真问题 | e2e 前置**新鲜度守卫**（失败关闭、**不自动构建**以免掩盖"忘了构建"），且守卫自己要有红证（陈旧 / 缺失 / 构建后 三场景） |
| **失败即丢证据** | `if-no-files-found: warn` 的 upload：**step success + artifact 为 0** —— 而失败腿恰恰最需要这份证据 | 非抑制状态下"该有产物却没有"必须**红或至少告警**，不能只 `warn` |

**推广**：任何"截图 / 快照 / 导出件 / 报表"当证据时，先问 **①它稳定吗（连续两次一致）②它是当前版本吗（新鲜度）③它真的产出了吗（产物级）** —— 三条都过才可引用。

## 断言形态：四种写法，两种"修好即红"（v1.4 新增）

写"门禁 / 清单 / 不变式"类断言时先认清形态——**选错会让测试在完成使命的那一刻自毁**：

| 形态 | 长什么样 | 评判 |
|---|---|---|
| **注入式红证**（首选） | 测试内**构造**一条坏数据 → 断言判据**必报出** | ✅ 与被测真值解耦，永远有效 |
| **关系式断言** | `门禁报出的 == 不变式报出的` | ✅ 与仓库真值无关；⚠️ 但**空集上恒真**（无判别力）→ 需注入使前提**非空**才算加强 |
| **真值主张**（自毁式） | `assert 仓库当下恰有该缺陷`：如 `assert invariant, "仓库应有 ≥1 处悬空声明"`、`assert 集合 == [("order_query","detail")]` | ❌ **修好即红**，且报错**指向错误方向**（挡住无关 PR）。实测 Case Coverage Gate 有 2 处 |
| **登记表 + 陈旧即红** | burn-down 白名单（`_KNOWN_DANGLING`），销账未删即红 | ✅ **对的设计**（报错正确可行动："你修好了，请删条目"）；⚠️ 但条目**清空后循环体不执行 ⇒ 恒真（vacuous）** → 改注入式自证"守卫还能响" |

⚠️ **关键区分 —— "修好即红"有两种，别把好的那个当缺陷改掉**：
- 报错说「**仓库应有该缺陷**」= 真值主张 = **自毁，要改**；
- 报错说「**登记已销账但条目未删**」= 陈旧守卫 = **有意设计，保留**。
判据只有一条：**报错信息是否指向正确的行动**。

## 部分闭环：关单 ≠ 病灶消除（v1.4 新增，2026-09-14 实证）

**只有"防新增"没有"清存量"，症状会一直在。** 实证 #3615（迁移非幂等噪音）：

- 关单 PR 标题**自己写着**「**不修已发布迁移**」——它只加了 **L0 前向防护**（保证**新**迁移不再犯，做得对）+ 一张 `_LEGACY_NON_IDEMPOTENT` 登记表；
- **真正加守卫的那笔 commit 从未合入 main**；关单 **6.5 小时后**的 run 仍逐字打印同一条 ERROR（含「请立即修复并在修复后重跑」—— 一句**必然为假**的行动指令）。

**核对动作**：读到"某 issue 已关闭"先问 **①病灶（现象）还在吗？②关单 PR 动的是"防新增"还是"清存量"？** 两者都有才算闭环。
（同族危害：**永久噪音让真失败与噪音同形** → 告警疲劳 → 归因层失效，正是本项目自认的最大失败模式。）

## 注释漂移 = 假绿来源（v1.4 新增，同一会话实证）

**注释里的错误真值与错误代码同等危险。** 实证：`post-deploy-eval.yml` 抑制段注释写着「**workflow_dispatch … 永不抑制**」，而实现对 `workflow_dispatch` 同样走 deploy 判据 → 主会话**正是读了这句注释**才没传 `force_eval=true`，于是拿到一个**绿的空跑**（每个评测步骤 `skipped`、artifact 0、整体 `success`）。

⇒ ① 改行为**必须**同步改注释（dev-flow §17.3）；② 注释里的"断言"至少与代码**同源核对**一次；③ **引用注释作为判断依据前，先核实现**。
操作口径：**手动补跑评测在 #3709 修复后默认免抑制**（要抑制须显式 `-f force_eval=false`）；被抑制时 run 上有 `::warning::` 标注 + summary 抬头「本 run 未评测」——**别把"绿"读成"评测通过"**。（历史口径「必须 `-f force_eval=true`」已失效，见 migao-dev-flow v1.20。）

## 执行流程（每步有完成判据）

| 步 | 动作 | 完成判据 |
|---|---|---|
| 1 | **定对象**：枚举被验收对象（会话 ID / 功能点），标注环境与版本 sha | 对象清单可枚举；无"待定/都行" |
| 2 | **写剧本**：按用户旅程写验收剧本（含点卡/刷新/换窗口/打岔/中途离开等真实动作） | 每个验收点有期望的用户可见结果（verbatim 或可判定谓词）；出现"表现正常/差不多"即不合格 |
| 3 | **声明矩阵**：每条验收点标注 L1/L2/UA | 出现"待人工" = 不合格；全 UA = 不合格（没机器断言） |
| 4 | **执行采集**：跑剧本，产出完整 transcript（每轮 用户输入→全部事件→最终文本/卡片） | 证据可复现；任何一轮的 AI 原文不得省略 |
| 5 | **判定**：L1 机器结论；L2/UA 逐条引用证据原文（UA 附 persona 声明与基准对照） | 每条判定都有证据引用 |
| 6 | **出报告**：按协议模板（结论/矩阵/问题清单含证据/复核验收抽验/沉淀记录），问题分级 P0/P1/P2 | 报告五项齐全 |
| 7 | **双 AI 交叉验证**：主验收 + 复核验收（不看 spec 独立抽样）对比；不一致 → 证据引用充分者为准，仍不一致 → 标记待裁定 | 差异清单已输出 |
| 8 | **沉淀**：每个问题 → 补/改 case（断言必须可执行）+ **case 有效性验证**（旧失败会话重放该 case 必 fail、修复后重放必 pass）+ 关联 issue | 无有效性验证 = 沉淀无效 |

## 产出物

- 验收报告（模板见协议 §4.2）：结论 / 验收矩阵 / 问题清单（证据引用）/ 复核验收抽验 / 沉淀记录；

## 结论档机器判定（completion_verdict，#3483 T2）

- 评测完成判定由 runner 输出（日志 + summary JSON 的 `completion` 字段）：
  **确定性失败 = 0 + 关键旅程（KEY_JOURNEYS_MIBAO/XIAOBU）全过 + 已知波动
  （**仅 `llm-noise`**）在 flake 台账放行**（v1.6 口径变更：`unstable` 不再放行，见下节）。完成 ≠ 全量 100% 绿
  （追 LLM 方差边际收益为负，B 端 80 轮差距分析实证）。
- 结论档引用该判定作为「是否可以下结论」的前置条件；PR 门禁（_ci_verdict 全绿）
  另行生效，两者各司其职。
- **验收证据可以取自「合并后的一次统一验证」**（一次全量档 + 独立盲审），**不必每个改动各跑一次** ——
  批量派发 / 批量合并 / 统一验证的范式与其代价见 `migao-dev-flow` §17.4。**但**：
  ① 必须标注该证据对应的 **SHA / 批次**（否则无法回溯到具体 commit）；
  ② **不得**用批合并掩盖单体回归 —— 批内 PR 需同主题、红了按提交序二分、单个 PR 的 required 门禁照旧；
  ③ 全量档覆盖不到某前置条件时才退回窄重放，且**必须回答「本次运行复现了缺陷的前置条件吗」**（见上「假绿形态」节）。

## 结论档口径：放行只适用于「重试通过」（v1.6 新增，2026-09-14 裁定）

**放行档只看「这条红灯有没有通过过」，不看「两次失败像不像」。**

口径锚点（代码单一事实源）：`tests/agent_eval/local_runner.py` 的
`_COMPLETION_RELEASED_CLASSES = frozenset({"llm-noise"})` —— **只放行 `llm-noise`**
（= 首次失败、新 session 重试**通过**）。裁定载体：issue **#3738**（decision）+ PR **#3739**（`5c058311`，
主会话裁定原文「批准两处口径变更，可以合并」）。分类事实未变，变的是**放行政策** —— 故由
`_COMPLETION_RELEASED_CLASSES` + 台账 `released` 字段**显式表达**（两者同源，有契约守卫锁一致），
不再靠"分类名"推断处置。

| 分类（`_classify_attempts` 判定顺序） | 含义 | 结论档处置 |
|---|---|---|
| `pass` | 首跑通过 | ✅ 通过 |
| `llm-noise` | 首败 + 新 session 重试**通过** | ✅ **唯一放行档**（记 flake 台账） |
| `infra` | 传输/超时/5xx | ⏸ 运行级分流（不属结论层；workflow 整跑重试 1 次） |
| `reproducible` | 两次指纹**相同**，或**真子集**且共有部分**非空** | ❌ 确定性失败 → 阻塞（禁止 rerun 掩盖，按签名排查） |
| `unstable` | 两次皆败、成因不同、无包含关系 | ❌ **不再放行** → 默认阻塞 |
| `no-retry-budget` | 重试预算用尽，未做第二次尝试 | ❌ 结论未验证 → 阻塞 |

**为什么 `unstable` 不再放行**：它只证明「两次失败**不是同一件事**」，**没有**证明「其中有一次是对的」。
放行的语义前提是「**确实通过过**」；两次都没通过时，唯一诚实的结论是「**这个用例当下不工作**」。

**实证（口径变更直接影响的历史结论）**：离线重放 6 个真实 run 的 `agent-eval-flakes.json` +
`eval-summary-*.json`（台账去重 43 条）——
- 放行条目 **29 → 21**（8 条 `unstable` 移出；21 条 `llm-noise` **全部保留放行**，档位不受影响）；
- 3 条分类修正 `unstable → reproducible`（PG-016 / AS-004 / PR-005）；
- **2 处 run×persona 结论翻转 —— 都是假绿被堵上，不是真波动被刷红**：
  - `34846098440` mibao：`ok=true`（`flake_released=["PG-016"]`）→ `ok=false`；
  - `34849029334` xiaobu：`ok=true`（`flake_released=["OR-026"]`）→ `ok=false`。
- `OR-026` 的 `ok=true` 完全建立在对 `unstable` 的放行上，而它两次都是「**声称完成但零写工具成功**」
  （独立盲审判其 `ok` 不可信）；`OR-014` 两次皆败（一次金额错 168≠198、一次 `order_create` 从未被调用）
  也被放行；`AS-004` 因「首败指纹是次败的**真子集**」被机械规则洗成 `unstable`
  —— 真回归被洗成波动，且 `deterministic_failures` **漏计**。

**⚠️ 不要过度收紧**：**不是**「凡失败即阻塞」—— `llm-noise` 必须保留放行，否则真实 LLM 波动会被判成阻塞
（那才是假红）；`infra` 仍走运行级分流。口径变更的代价是「**该 run 的结论不可信**」（需重跑该用例或先归因），
**不是**「永久红灯」—— 已知实例：`PR-005` @ `34806843585` 归 `unstable` 后，后续 3 个 run 均通过。

**判别口诀**：**指纹回答「是不是同一件事」，分类回答「这条红灯怎么处置」** —— 两者是分开的
（`unstable` 分类仍准确，只是不再属放行档）。改口径时**必须同时**改本节、`_COMPLETION_RELEASED_CLASSES`
与台账 `released` 语义，缺一处即「注释漂移 = 假绿来源」（见该节）。

## 复核裁判模型独立性（#3483 T5，协议 §1.7）

- 双 AI 交叉验证（协议 §1.5 防同谋）：主验收默认 DeepSeek（DSH 主会话），
  **复核验收默认 GLM-5.3-Flash**（provider `scnet-token-plan`，settings.yaml 已配置）——
  不同模型族，系统性同源偏差最小化；
- 机制照 migao-dev-flow §15.5 的模型路由：workflow 工具开子代理
  `agent(prompt, { provider: 'scnet-token-plan', model: 'GLM-5.3-Flash', label: '复核验收' })`；
  复核只看 transcript 证据 + 断言规范，**不看 spec**（§1.5 独立视角）；
- 判定铁律不变：每条判定必须引 `R轮次/原文片段`，引用缺失 = 判定无效；
- 试点校准：首次启用前用 10 条历史 transcript 做双裁判比对（结论一致率 +
  证据引用完整率）；不一致以证据引用充分者为准；仍不一致 → 标记待裁定（仲裁非执行）。

## 证据来源与环境（#3503/#3506）

- **结论档的评测证据取自"独立栈"（CI docker 标准考场）**，不取云测试环境——
  干净数据才可归因（详见仓库 `docs/testing/eval-environments.md`）；
- 云测试环境（SWAS）的产物用于**冒烟与真实存量验证**；生产未部署，上线门禁已预定义
  （发布前：独立栈全量 + completion_verdict ✅ + 双裁判无未裁定分歧）；
- **部署后自动回归**（#3503）会产出独立栈全量结果 + completion_verdict —— 结论档可直接
  引用该 run 的证据（transcript/summary），不必重跑；仅当需要剧本级（点卡/打岔/换窗口）
  证据时才补跑验收剧本。

## 验收问题的并行分流（migao-dev-flow §17）

验收一次暴露多个问题时，**先冻结清单再并行修复**（发现即并行，合并串行）：
- 每条问题写清 **证据引用 + 五层归因 + 验收判据**，然后按**文件所有权**切成互不冲突的任务包
  （同文件改动同包；改 `cases/*.yml` 的包独占生成物）；
- 每包 = issue + 分支 + 独立 worktree + 后台 subagent；**验收者不参与实现**（不自我验收铁律），
  只做集成与复核；
- 并行度上限：评测型流水线同时 ≤3（runner 竞争 + 真实 LLM 成本）；
- 合并后按受影响档位重跑验证（静态 → 迭代档 → 全量），并做 §5 的 case 有效性验证。
