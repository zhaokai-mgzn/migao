### 9.3 另一条：竞态形态的**判定口径**（防误伤）

### 11.1 订正 §7 第 1 条与 §3 的理由：「无浏览器环境」**不成立**

**原判**（§7 第 1 条；§3 的 UA-1 / UA-2「证据」列）：UA 未做的原因是「**无浏览器环境**」。

**订正**：该理由**被证伪** —— 本机浏览器侧一直是齐的（只是**当时没人去试**）：

### 11.2 订正 §7 第 3 条：`type="number"` 的判定从「Chromium **推断**」改为「真浏览器**实测**」，结论**推翻** jsdom 那条

**原判**（§7 第 3 条 + §4 末行）：「独立复核者同样无浏览器 ⇒ 其对 `type="number"` 站点
（`ProductForm` / `OversizeThresholdPreview` / `routings`）的判定是**代码 + jsdom 实证 + Chromium 推断**」；
§9.2 也如实记下了那场**谁也没说服谁**的分歧（修复侧：真浏览器 `0→.→5` 得 `0.5` ⇒ 无缺陷；
复核侧：jsdom 实测 `0.` ⇒ `""`（吞））。

**订正**：这条分歧**已有真浏览器判定** —— 见 **issue #5228 的最后一条评论**（本报告成文时作者 `zhaokai-mgzn`；
**内含自带源码、可直接重跑**的探针）：四种形态（非受控 / 受控按 React 真实写入规则 / 受控 + falsy 映射 /
受控 + 数值化回写）各敲 `0` → `.` → `5`，逐击读 `el.value` 一律为 `"0" → "0" → "0.5"`，
**终值一律 `0.5`** ⇒ **`0.5` 打得出来**。

- **jsdom 那条读数不能当真浏览器证据**：同一输入序列下 jsdom 把 `"0."` 归一成 **`""`**，

- ⚠️ **同一条评论还订正并撤回了它自己上一轮的一条读数**：第一版探针的 B 形态用了
  「**无条件**把 `e.target.value` 写回 `el.value`」—— 那**不是** React 的真实规则

- **仍未翻案、也不受本判定影响的部分**（防顺手扩大战果）：#5228 缺口 1（**静态扫描只认 `: null` 一种写法**）

### 11.6 ② 的原始投诉在真浏览器下的收口读数

用户原始投诉（②）的原话是「**不能直接输入 0，所以导致无法输入 0.？**」。
在同一套真浏览器栈上补做一条探针（`ua/probe-typing-zero.mjs`），**逐字符**敲入并在**每一击后**读 DOM 值：

```
窗宽（米）逐字符：'0'→"0"  '.'→"0."  '5'→"0.5"      终值 = "0.5"   ✅
窗宽（米）第二轮：'0'→"0"  '.'→"0."  '6'→"0.6"      终值 = "0.6"   ✅
```

- **站点** = 下单页「**窗宽（米）**」（`NumberField` / 共享 `NumberInput`：`type="text"` + `inputMode="decimal"` + 字符串草稿）。
- **只报实测**：两轮逐字符输入的**终值分别为 `0.5` / `0.6`**，中间态 `"0."` **未被吞**。
- 现场截图 `ua/05-逐字符输0.5.png`：`窗宽（米）` 上正是**第二轮终值 `0.6`**（同帧可见 窗高 2.6 / 用料 1 / 商品「遮光窗帘 浅灰」）。
- **与 11.2 的对照价值**：`"0."` 中间态在**本组件里被逐字保留**（字符串草稿），而**原生 `type="number"`** 在真 Chromium 下
  会把 `"0."` 归一成 `"0"`（小数点字符被吞，但 `0.5` 仍打得出来）⇒ 两条并列正好把「② 到底修了什么」钉死：
  修的是「**中间态不再被吞 / `0` 不再被清空**」，而**不是**"以前完全打不出小数"。
- ⚠️ **不许推广**：本次只跑了这**一个**站点；其余数字输入站点的护栏在 **#5228 / #5237**，本次**一个都没跑**。
