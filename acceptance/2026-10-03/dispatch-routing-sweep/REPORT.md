## 三、问题清单（P0/P1/P2/P3，含证据引用与归因）

### 🔴🔴 F8（P1 · 涉钱 · 静默）**保存一次工序设置就会改写计件单价**（未定价 → 0 元 / 商家改过的价被回退）

- **触发动作**：工序管理页抽屉里任何一次保存（改分组 / 单位 / **作用域** / 「标记生产开始」）——
  本轮是 P6 的 W-09/W-10 触发后追查出来的（**不是**改价动作）。
- **证据（P9，双向复现，`out/p9-price-drift.json`）**：
  | 形态 | 保存前 | 保存后（`PUT /operations/{id} {scope}`，HTTP 200） |
  |---|---|---|
  | A：该工序**未定价** | 读面 `NULL(未定价)`、派工实例价 `NULL(未定价)` | 读面 **`0`**、派工实例价 **`0.00`** ⇒ **未定价被静默顶成 0 元** |
  | B：商家在「工艺项」把价改成 **0.77** | 读面 `0.77`、派工实例价 **`0.77`** | 读面 **`0`**、派工实例价 **`0.00`** ⇒ **商家改过的价被静默回退成工序库价** |
  还原（软删探针新建行 + 通用行价归 NULL）后：读面与派工**都回到 `NULL(未定价)`** ✅
- **机制（三段，均可逐字复核）**：
  1. `ProductionOperationCommandService.update()`（第 295 行）→ `attachPositions(...)`（第 315 行）：
     body 省略 `positions` 时按**取价来源部位**兜底，**新建** `position='布帘'` 的价目行，
     价 = **工序库价** `production_operations.unit_price`（seed 工序多为 `0.00`）；
  2. 价目读面/取价一律走 `ProductionOperationQueryService.collapseToLogical(...)`（第 460 行），
     其选行比较（第 482~491 行）**`COLLAPSE_PRICE_SOURCE_POSITION = "布帘"` 列优先**（第 162 行，用户裁定「取布帘价」）；
  3. seed 期这些工序的价目行经 V104 塌缩后 position 是 **`通用`** ⇒ 新冒出的 `布帘` 行**盖住**原 `通用` 行
     ⇒ 有效价从「未定价 / 商家改价」变成「工序库价」。
- **影响**：商家**保存一次设置**（哪怕是改个分组）就可能把「未定价」变成 **0 元**（工人白干）或把改好的价**回退**掉；
  页面**没有任何提示**，读面看起来"正常"。
- **旁证（本轮实测污染）**：我自己的 P3-W-08 / P6 两次 PUT 就在库里留下了两条 `布帘` 价目行
  （`三边` 0.40、`打包` 0.00）；`打包` 的实例价因此从 `NULL` 漂到 `0.00`，**导致 P4b 的一条红证门先"失效"**
  （因为期望价也跟着漂了）—— 这条自我污染反而是本缺陷的**活体证据**，已全部还原（见 §六）。
- **修复方向**：① `attachPositions` 兜底建行时，**继承已有「通用」行的价**（或宁可 `NULL`）而**不是**拿工序库价；
  ② 或让 `collapseToLogical` 不因「新出现布帘列行」改变有效价（**同价才可覆盖**）；
  ③ 加一条判据：**任何工序设置写面调用后，该工序的有效价必须逐字不变**（除非该写面显式带 `unit_price`）。

  逐像素可见三处同源读数 —— ① 顶部 toast「**status 仅支持 active/disabled**」；

  **均正常渲染** ⇒ 故障面精确落在「停用」这一条写面上，**不是**整页不可用。
- **证据（接口级，P3/W-08）**：`PUT /api/admin/production/operations/{id}` body `{"status":"inactive"}` ⇒
  **HTTP 422** `status 仅支持 active/disabled`；body `{"status":"disabled"}` ⇒ 200。
- **归因（机制级，可逐字复核）**：前端 `frontend/admin-web/src/app/(dashboard)/production/routings/page.tsx`
  的 `disableOpByName` 逐字发送 `{ status: 'inactive' }`；后端
  `backend/admin-api/src/main/java/com/migao/admin/service/ProductionOperationCommandService.java`
  的 `STATUSES = Set.of("active", "disabled")` ⇒ **两处枚举各写一份，值不同且不会变红**。
- **影响**：工序的「软下线」手段只剩删除；而删除有护栏（见 P3/W-05 的 422：须先解除矩阵格/主线引用），

- **类级射程（照铁律 8「修一处 = 没修」）**：
  - **词表在上游就分裂**：`ProcessingItemStatus = 'active' | 'inactive'`（**加工项**域，

    ⇒ 同一屏上「停用」有两个词，UI 抄了**加工项**那一个。
  - **编译器也看不见**：`ProductionOperationUpdateParams.status?: string`（**裸 string**，非联合类型）
    ⇒ `tsc --noEmit` 不红、`check-ui-regression.sh` 也不红；且 `ProductionRouteParityType` 一类跨端守卫
    只比字段名不比**取值域**。
  - ⇒ 真正的固化点是「**跨端状态词表单一出处**」+ 一条**会红的跨端一致性守卫**，
    而不是把 `routings/page.tsx` 那一行改成 `'disabled'` 就完事（下一处抄错照旧进不来也照旧没人拦）。

### 🟠 F2（P2 · 涉钱 · 静默口径）自建工序的「应做数量」恒为 1（单位是米也一样）

- **证据（P3/W-01b）**：新建工序「验收探针工序382359」（`unit=米`，`unit_price=0.9`）挂进默认主线后派工，
  `processing_position_operations.qty = 1.00 米`、`qty_source = fallback`；
  **同一张加工单**里既有工序 `精裁-布` 读 `fabric_meters = 12.30 米`。
- **归因（机制级）**：数量口径按键目录取自 **Python 侧静态工序目录**
  `backend/ai-agent-service/app/production/routing.py` 的 `OPERATION_CATALOG`（`_qty_for` 用它查单位），
  商家自建工序不在目录里 ⇒ 落「引擎不认识的工序 ⇒ 兜底 1 + fallback」分支
  （该分支在 `POST /api/internal/production/operation-qty` 的 docstring 里是**已知口径**）。
- **影响**：自建工序（`unit=米/折/孔/幅/套`）派工后应做数量按 1 计 ⇒ 报工与**计件工资按 1 计量**
  （实测 0.9 元/m 的工序，一单 12.3 m 只算 0.9 元），且商家界面没有任何「数量口径不可用」的提示。
- **修复方向**：① 建工序时若单位 ∈ `KNOWN_QTY_UNITS` 且不在引擎目录 ⇒ **写面显式告警/读面标记**（不静默）；
  ② 或把「工序 → 数量键」的口径从静态目录改为可下发/可派生（`unit` 即可决定键，见 `_qty_keys_for_unit`）。

### 🟡 F5（P3 · 观察项）两本价格账分叉：工序库改价不影响派工取价

- **证据（P3/W-02c）**：`PUT /operations/{id} {unit_price: 2.5}` ⇒ **HTTP 200**，库里
  `production_operations.unit_price = 2.50`，但派工实例单价仍为**矩阵格价** `1.75`
  （`production_operation_positions.unit_price` 未同步）。
- **归因**：派工取价只读 `production_operation_positions`（经 `collapseToLogical` 塌缩）；`PUT /operations` 只写工序库 + 版本账。
- **现状风险**：UI 的改价入口是矩阵格（P3/W-02 绿，1.75 生效），**新增工序**表单写工序库价且会同时建矩阵行

  集成方/后续 UI 一旦用它改价，就会出现「改了价、工钱不变」的静默分叉。

### 🟡 F6（P3 · 登记）默认配置下不可达的工序

`裁剪-纱`（§2.2）。与 `质检/腰靠垫`（有意挂起、`pending_confirmation=true`）不同，它**没有任何登记**，

### 🟡 F7（P3 · 一致性缺口）路线「适用帘种」写面**没有**值域校验（同维度的规则写面有）

- **证据（P8/R-05）**：`POST /api/admin/production/routings {positions:['火星帘']}` ⇒ **HTTP 200**，
  库内 `production_route_templates.positions = ["火星帘"]`（探针已软删）。
- **对照（同维度、另一写面有护栏）**：规则的部位维受**闭词表**保护 —— `ProductionRoutingCommandService`
  对 `trigger_kind='position'` 的 `rulePosition` 逐字校验 `ProductionOperationQueryService.POSITION_LIMIT_VOCABULARY`
  （`布帘/纱帘/帘头/布料`），越界 ⇒ **422**；其注释明写这条护栏的理由：「收下一个**永不可能等于任何实例化部位**的
  『部位』，那就是『规则已落库但永不生效』的黑洞（本仓明令要显式失败的形态）」。
- **同一句话对路线成立**：`createRouting`/`updateRouting` 只校验「非空」，不校验值域
  ⇒ 商家可建出**永不可能被选中**的路线，**没有任何读面/提示会说它是死配置**。
- **修复方向**：路线写面的 `positions` 复用同一份 `POSITION_LIMIT_VOCABULARY`（一处判据两处用，别新造词表）。

## 八、结论

1. **派工（取路 → 变体解析 → 条件工序落位 → 数量 → 单价 → 套级作用域 → 开工标记）本身是准的**：
   44 条派工场景（覆盖 37/40 道工序、全部 5 条工艺规则、16 条选项规则、3 条加工项触发、形态开关、
   套级防双付、数量按单位口径、未定价必须 NULL）**全绿**，并由 P4b 用**矩阵自己的判据**逐门证明会红。
2. **「工序设置」面查出 3 个产品缺陷（6 条 fail 条数 ⇒ 3 个缺陷，F1 双证）+ 3 个口径缺口 + 1 个一致性缺口**：
   - **F8（P1·涉钱）= 本轮最重要的发现**：**保存一次工序设置就会改写计件单价** —— 未定价被顶成 `0` 元、
     商家改过的价被回退成工序库价（P9 双向复现 + 干净还原）。
   - **F1（P1·用户可见）**：停用按钮 100% 失效（接口层 + UI 层双证）。
   - **F2（P2·涉钱）**：自建工序应做数量恒为 1（单位是米也一样）。
   - 口径缺口：F3 缺口清单 20/22 误报 + 有害建议 + 1 处漏报；F4 默认配置下纱帘单会被整单卡死（解药已验证）。
   - 一致性缺口：F7 路线「适用帘种」写面**没有**规则部位维那样的闭词表保护。
3. **没有发现「工序算错了」的缺陷** —— 所有派工结果的工序集合、顺序、数量、作用域都与商家配置**逐字相符**；
   问题集中在**设置面**（改不动 / 改完悄悄改价 / 清单骗人 / 默认配置卡单 / 写面护栏不齐）。
4. **方法论结论（值得固化）**：P2 的单价断言取期望自**被测系统自己的读面** ⇒ 它**看不见读面本身被改坏**；
   真正抓到 F8 的是 P9 的「**改一处 → 前后对比**」口径。凡是「配置写面」的验证，必须带**前后对比**，
   否则「自洽」会冒充「正确」。
4. 本轮**未做**：真实 LLM 评测（#4262 用户裁定）、拍照导入、跨模块契约门禁（`contract-check.sh`，本轮零代码改动）。
   **未创建 AI agent 会话** ⇒ 铁律 6「复核自己留下的会话」不适用（范围排除已登记）。
