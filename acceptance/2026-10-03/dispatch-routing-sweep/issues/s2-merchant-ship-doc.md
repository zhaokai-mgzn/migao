## 集成方的实现口径（AI 裁定，包须先核可行性；核不成立就停下回报）

1. **实发数量从哪来**：该端点请求体只有**运单号 / 承运商**，**没有数量** ⇒ 按「**订单未发余量**」落：
   逐 `order_item` 记 `订单量 − 已发合计`（正是 S1 立起的不变量 `Σ已发 ≤ 订单量` 的另一半）。
   若实现层发现该口径与既有 `order_shipment_items` 的形状/语义不符（如单位/规格列必填）⇒ **停下回报**，别自造形状。
2. **`source`**：用 schema 既有的 `admin`（全仓零代码写它，正是为这条路预留的）——**不许新造取值**。
3. **必须与 S1 的不变量共存**（同文件族，别推翻）：
   - `Σ已发（含本次）≤ 订单量`，超发 ⇒ 4xx 且不落库；余量为 0 时再发 ⇒ 4xx（不是静默建空单）；
   - **幂等**：同一 `X-Client-Request-Id` 重复调用 ⇒ 回放首次结果、**不得多建第二张发货单**；
   - 精度：越界精度（如 `0.001`）⇒ 4xx。
4. **读面一致**：发货成功后该订单在「发货单」列表**可查**，且列表里的**实发数量 = 写面写入值**（跨读面 join，**别只判写面**）。

## 验收判据（冻结，必须会红）

1. 商家发货成功 ⇒ `order_shipments` **新增 1 行**、`order_shipment_items` 的实发数量 = 订单未发余量（逐行核对，直连 DB）。
2. 「发货单」**列表读面**能查到该订单，且数量与写面一致（**跨读面**判据）。
3. 幂等：同键两次 ⇒ 仍**恰一张**发货单、运单号不被覆写（复用 `ClientRequestIdService`，别新造）。
4. 余量 0 再发 ⇒ 4xx；超发 ⇒ 4xx；**均不落库**（字段级快照）。
5. **红证**：注入式两侧夹住（不建单 ⇒ 判据当场红；建单 ⇒ 绿），读数逐字进 PR body。
