## 三、现场定名：那次 422 的服务端原因

同一次点击（勾 12 行 → 一键合并派单）在本机复现，服务端逐字：

```
HTTP 422  {"success":false,"error":{"code":"VALIDATION_ERROR",
  "message":"「2699系列雪尼尔窗帘面料」这行需要 2 米，库存里没有能裁出它的批次（按「先到先用」也补不上）—— 请先把这批布入库，或核对库存里对应门幅与颜色的余量后重试"}}
```

- 复现命令（真登录拿 token 后直打接口，读面/写面都是真库）：
  `POST /api/admin/production/pool/preview`，`{orderIds:[…14], batches:[…14], assignmentRule:"fifo", pooled:true}` ⇒ **422**；只勾 1 行 ⇒ 同一条（**同一行是固定的**：订单 `20261014166330020`）。
- 性质：**数据条件**（该物料 = 商品 × 颜色 × 门幅 下没有可用库存批次能裁出这 2 米），不是缺陷；缺陷是「只在你点完之后才说」⇒ 行为面新需求 **#7091**（口径 A/B/C 待裁定，安全默认 = 不动）。
- 用户环境 = 本机同库同租户（本机 `:8080` 读的就是云 dev RDS 的 `米高测试环境`；本机复现出的「待派订单 14 单 / 超时未派 12 单」与用户截图逐字一致）⇒ 这条定名对用户那次报错成立。
